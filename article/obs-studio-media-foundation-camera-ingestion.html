OBS Studio Media Foundation Camera Ingestion

This article examines how OBS Studio utilizes the Windows Media Foundation (MF) API to discover, configure, and ingest video feeds from hardware cameras. It breaks down the initialization pipeline, from hardware enumeration and media source activation to media type negotiation, asynchronous sample capture, and frame conversion for the OBS rendering pipeline.

Device Enumeration and Activation

OBS Studio interfaces with Windows camera hardware primarily through the Windows Media Foundation framework when configured for modern capture drivers. The process begins with hardware enumeration:

  1. Attribute Setup: OBS creates an attribute store using MFCreateAttributes and sets the source type attribute to MF_DEVSOURCE_ATTRIBUTE_SOURCE_TYPE_VIDCAP_GUID to target physical video capture devices.
  2. Device Discovery: It calls MFEnumDeviceSources to return an array of IMFActivate pointers, representing connected Universal Video Class (UVC) cameras, capture cards, and virtual video devices.
  3. Hardware Selection: OBS inspects symbolic links and human-readable device names (MF_DEVSOURCE_ATTRIBUTE_FRIENDLY_NAME) to match the user's selected camera source.
  4. Source Instantiation: Once identified, OBS calls IMFActivate::ActivateObject with the IID_IMFMediaSource interface identifier to create the concrete IMFMediaSource instance for the device.

Initializing the Source Reader

Rather than managing direct topology nodes or manual pipeline construction, OBS Studio employs the high-level IMFSourceReader interface to simplify ingestion:

  • Low Latency Attributes: Before creating the reader, OBS constructs an attribute dictionary enabling low-latency operation (MF_LOW_LATENCY) and configuring internal buffering behavior to minimize frame delivery delay.
  • Reader Creation: OBS calls MFCreateSourceReaderFromMediaSource, passing the active IMFMediaSource and configured attributes.
  • Stream Selection: The reader enables the primary first video stream (MF_SOURCE_READER_FIRST_VIDEO_STREAM) and deselects all other auxiliary or audio streams provided by the video capture source.

Media Type Negotiation

To support flexible user configurations (resolution, framerate, and color format), OBS queries and selects suitable media formats directly from the hardware:

  1. Querying Native Formats: OBS iterates through available formats using IMFSourceReader::GetNativeMediaType. It enumerates supported combinations of dimensions (width/height), frame rates (expressed as rational fractions via MF_MT_FRAME_RATE), and pixel formats (such as NV12, YUY2, or MJPEG).
  2. Matching Properties: When a user specifies custom capture parameters, OBS searches for the exact media type match. If the user selects "Device Default", OBS retrieves the hardware's preferred native format.
  3. Setting the Target Format: OBS locks the stream configuration by calling IMFSourceReader::SetCurrentMediaType. If the camera supplies compressed streams like MJPEG, Media Foundation can automatically bind an internal hardware- or software-accelerated decoder transform (MFT) to output uncompressed video buffers.

Frame Acquisition and Asynchronous Processing

OBS configures capture execution to avoid blocking the main rendering or encoding threads:

  • Callback Mechanism: OBS initializes the IMFSourceReader in asynchronous mode by providing an implementation of the IMFSourceReaderCallback interface within the reader attributes.
  • Sample Request Loop: When IMFSourceReaderCallback::OnReadSample triggers, OBS processes the newly arrived frame and immediately issues a request for the subsequent frame via IMFSourceReader::ReadSample, maintaining a continuous capture loop.
  • Timestamp Handling: Hardware timestamps attached to each IMFSample (IMFSample::GetSampleTime) are mapped to the high-resolution OBS internal monotonic clock to maintain audio-video synchronization and detect dropped frames.

Data Extraction into the OBS Graphics Pipeline

Once an IMFSample arrives via the callback, OBS maps the underlying media buffer to its internal rendering engine:

  1. Buffer Access: OBS calls IMFSample::ConvertToContiguousBuffer (or retrieves the primary IMFMediaBuffer) and locks the memory using IMFMediaBuffer::Lock (or IMF2DBuffer::Lock2D for strided image data).
  2. Format Translation: The raw memory pointers, stride offsets, and dimensions are mapped into an obs_source_frame struct. Formats like NV12 or YUY2 are linked to their corresponding OBS internal color types.
  3. Pipeline Ingestion: OBS hands off the populated frame structure to the OBS core engine via obs_source_output_video.
  4. Buffer Release: The media buffer is unlocked, the reference count on the IMFSample is decremented, and the memory returns to the Media Foundation driver pool for reuse.
