OBS Studio Lua Crash Log Diagnostic Data

When an unhandled exception occurs within an OBS Studio Lua script hook, the application's built-in crash handler generates a detailed crash log file to diagnose the point of failure. This article covers the specific diagnostic data written to the OBS Studio crash log during such an event, explaining the sections recorded by the crash reporter, including system metadata, exception codes, thread call stacks, register states, and loaded modules.

Distinction Between Script Errors and Crash Exceptions

Standard Lua syntax or runtime errors (such as attempting to index a nil value) are typically handled internally by the obs-scripting module via protected calls (pcall), outputting error messages and stack traces directly to the standard OBS application log. An unhandled exception that generates an OBS crash log occurs when a Lua hook triggers a native-level fault—such as an invalid memory access via LuaJIT's Foreign Function Interface (FFI), a stack overflow, or memory corruption.

Exception Information

At the top of the crash log, the handler outputs the primary technical attributes of the failure:

  • Exception Code: The platform-specific exception identifier (for example, 0xC0000005 for an Access Violation on Windows).
  • Fault Address: The exact memory address where the instruction attempted an illegal operation.
  • Execution Flags: Indicators regarding whether the exception is continuable or fatal.

Faulting Thread Stack Trace

The crash log isolates the thread executing the Lua hook at the time of the fault and generates a reverse call stack. This section contains:

  • Module Names and Offsets: The binary files executing code, typically referencing obs-scripting.dll, luajit-5.1.dll (or lua51.dll), and core engine binaries like obs.dll.
  • Symbolic Function Names: If debug symbols (PDBs) are accessible, the trace resolves function calls, highlighting the internal C-wrapper functions responsible for dispatching Lua hooks (e.g., call_func, obs_lua_callback, or custom FFI target functions).
  • Instruction Pointers: The exact offsets within the involved dynamic link libraries.

CPU Registers

The state of the CPU registers at the exact millisecond of the crash is dumped in the log:

  • Instruction Pointer: RIP (64-bit) or EIP (32-bit), identifying the exact assembly instruction that faulted.
  • Stack Pointers: RSP/ESP and RBP/EBP, detailing the stack memory boundaries.
  • General-Purpose Registers: Values for RAX, RBX, RCX, RDX, RSI, RDI, and extended registers (R8–R15), which help identify malformed pointers passed between the Lua state and native C functions.

Loaded Modules List

A complete inventory of all shared libraries and executable modules loaded into the OBS Studio process space is appended. Each entry includes:

  • Base Address and Memory Range: The start and end locations of the module in memory.
  • File Path and Version: The exact disk path to the executable or DLL, verifying whether custom Lua runtime binaries, external C extensions, or specific OBS plugin versions were loaded.

Environment and System Metadata

The log header provides contextual system details to establish the operating environment:

  • OBS Studio Version and Architecture: The exact build version (e.g., 30.x.x) and bitness (x64/arm64).
  • Operating System Details: The OS version, build number, and kernel release.
  • Hardware Information: CPU model, physical thread count, and available system memory.
