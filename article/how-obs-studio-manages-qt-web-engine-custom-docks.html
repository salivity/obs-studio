How OBS Studio Manages Qt WebEngine Custom Docks

OBS Studio manages custom dock windows built with Qt WebEngine by embedding web views inside native Qt dock widgets, overseeing their lifecycle from initial creation and configuration to runtime visibility and teardown. Through a combination of Qt's native widget architecture, chromium-based process isolation, and internal configuration management, OBS coordinates state restoration, background resource throttling, and clean process termination for custom browser docks.

Initialization and Registration

Custom browser docks in OBS Studio are encapsulated as instances of QDockWidget containing a child QWebEngineView. When OBS initializes or when a user defines a new dock via the interface, the application constructs the QDockWidget container, designates its object name for state tracking, and instantiates the underlying QWebEnginePage.

During this phase, OBS configures the dock's specific QWebEngineProfile. The profile establishes storage paths for cache, persistent cookies, and local storage. Docks can be assigned shared sessions or dedicated profiles depending on implementation requirements. Once the page environment is ready, OBS Studio connects signal-slot bindings to monitor page loading events, title updates, and close requests, subsequently integrating the dock into the main window's layout via standard Qt docking routines.

State Persistence and Restoration

OBS Studio relies on Qt's layout serialization features alongside its own configuration system to maintain dock states across application restarts:

  • Layout Geometry: The position, dimensions, docking area, and floating status are serialized using Qt’s saveState() and restored during startup using restoreState().
  • Dock Metadata: Titles and URLs entered by the user are stored within OBS Studio’s JSON configuration files (such as basic-main.json).
  • Session Persistence: When OBS launches, it reads the saved dock definitions, instantiates the required Qt WebEngine components before applying the saved layout, and begins loading the registered target URLs.

Runtime Visibility and Resource Management

Web pages can be resource-intensive, so the lifecycle during active execution is largely driven by visibility and focus states:

  1. Visibility Events: OBS Studio monitors showEvent and hideEvent signals emitted by the QDockWidget. When a dock is closed, minimized, or covered in a tabbed dock stack, the underlying WebEngine widget is notified of its occluded state.
  2. Chromium Engine Throttling: Qt WebEngine utilizes Chromium’s internal power-saving mechanisms. When a dock is hidden, Chromium throttles JavaScript execution, reduces timer frequencies, and halts render passes to minimize CPU and GPU overhead.
  3. Audio and Focus Handling: OBS oversees page muting states and input focus, ensuring that background docks do not unintentionally capture global keystrokes or output unmanaged audio streams during live broadcasts.

Destruction and Teardown

The termination lifecycle occurs either when a user deletes a custom dock or during OBS Studio’s global shutdown sequence:

  • Individual Dock Removal: When a user removes a dock via the "Custom Browser Docks" dialog, OBS triggers a deletion sequence. The parent QDockWidget is unregistered from the main window, its pointer is removed from the active dock collection, and deleteLater() is called. This signals the QWebEngineView to abort ongoing network requests, execute window unload hooks, and destroy the associated DOM tree.
  • Application Shutdown: During the main window's closeEvent, OBS saves the current window geometry and dock configuration. It then proceeds to safely teardown active child widgets. Because Qt WebEngine relies on auxiliary render processes, OBS permits the WebEngine context to cleanly flush data caches to disk and terminate IPC connections before releasing the WebEngine profile and freeing allocated memory.
