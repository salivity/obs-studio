OBS Studio macOS Sandboxing: Accessing Local Files

This article examines how OBS Studio navigates macOS security restrictions, specifically App Sandbox policies and the Transparency, Consent, and Control (TCC) framework, when reading local media files stored in external directories or removable drives. It details the underlying system permissions, the technical challenges of persistent file access across app relaunches, and the configurations required to ensure seamless media playback during live production.

macOS Security Architecture: Sandbox and TCC

macOS enforces strict boundaries between applications and local storage using two primary mechanisms: the App Sandbox and the Transparency, Consent, and Control (TCC) subsystem. Although OBS Studio distributed outside the Mac App Store operates outside the strictest App Sandbox profile to maintain plugin and hardware capture compatibility, it must still comply with Apple's Hardened Runtime and TCC requirements.

TCC protects specific user directories, including ~/Documents, ~/Downloads, ~/Desktop, iCloud Drive folders, network volumes, and external removable drives. When OBS Studio attempts to load media assets—such as video overlays, stingers, or background audio—from these protected locations, macOS intercepts the file system call and checks the application's current privilege state.

Explicit User Consent via System Open Panels

Under macOS security rules, an application gains read access to an external directory through user-driven interactions. When you add a Media Source or VLC Video Source in OBS Studio and click "Browse," OBS invokes the native NSOpenPanel.

Selecting a file through this native dialog grants OBS temporary, system-approved access to the chosen file or folder. macOS considers this an explicit grant of permission by the user. If the file is located on an external drive or network share, the operating system registers that OBS has been authorized to interact with that path for the duration of the current session.

Persistent Access and Path Traversal Issues

Problems commonly arise when OBS Studio restarts or when automated scripts load scenes containing assets from external storage. While an active session retains the temporary permission granted by NSOpenPanel, security scopes can expire upon application termination unless properly retained:

  1. Broken File Pointers: If an external drive remounts under a different mount point (e.g., /Volumes/DriveName 1 instead of /Volumes/DriveName), OBS cannot resolve the path, triggering missing media errors.
  2. Permission Revocation: If OBS attempts to read a saved file path on launch without an active user prompt, macOS may block the background file access call, causing the media source to appear black or silent.
  3. Subfolder Access: Authorizing a single media file does not automatically grant OBS permission to read sibling files or parent directories unless the entire directory structure was selected during the initial dialog.

Resolving Restrictions with Full Disk Access

To avoid manual permission confirmations and prevent dropped assets during live broadcasts, users frequently bypass targeted TCC checks by granting OBS Studio elevated system storage permissions.

Assigning Full Disk Access (FDA) to OBS Studio exempts the application from individual folder prompts and external volume access dialogs. With FDA enabled in macOS System Settings under Privacy & Security, OBS can traverse all connected volumes, secondary internal partitions, and external drives seamlessly. This setup ensures that scene collections referencing complex folder structures across multiple drives load consistently upon startup without being blocked by macOS security daemons.
