Interpreting OBS Studio C++ Plugin Memory Leaks

This article provides a technical guide on interpreting memory leak stack traces generated by third-party C++ plugins running within OBS Studio. It explains how to load proper debug symbols, distinguish between OBS core allocation calls and plugin-specific code, decipher the layers of a leak trace (from tools like AddressSanitizer or Visual Studio CRT), and identify common leak patterns such as unreleased reference counts and graphics buffer mismanagement.

Understanding the OBS Execution Context

OBS Studio is a modular host environment where the core executable (obs64.exe) loads the primary runtime library (libobs.dll) alongside various third-party binary dynamic libraries (.dll, .so, or .dylib).

When a third-party plugin creates a memory leak, runtime diagnostic tools—such as Clang/GCC AddressSanitizer (ASan), Visual Studio CRT Debug Heap, or Valgrind—produce a stack trace representing the allocation site of the unreleased memory. Because the plugin executes inside the OBS process space, the generated stack trace contains a mixture of OS-level loader threads, OBS subsystem calls, and your plugin's C++ routines.

Prerequisites for Accurate Traces

A stack trace is unreadable without proper symbol resolution. If memory leak outputs display raw memory addresses (e.g., 0x7ff7a12b4e80) instead of function names and source line numbers:

  1. Compile with Debug Info: Ensure your plugin is compiled with -g (GCC/Clang) or /Zi / /DEBUG (MSVC).
  2. Match PDBs/Dsyms: Keep matching symbol files (.pdb on Windows, .dSYM on macOS) in the same directory as your compiled plugin binary inside the OBS plugin directory (e.g., obs-studio/obs-plugins/64bit/).
  3. OBS Debug Symbols: For deeper context into whether an allocation was triggered by the core framework, download the official OBS Studio debug symbols matching your exact OBS runtime version.

Deconstructing the Memory Leak Stack Trace

A typical memory leak trace reads from top to bottom, where the top frame is the raw allocator and the bottom frame is the originating thread entry point.

Consider this example generated by AddressSanitizer:

=================================================================
==12048==ERROR: LeakSanitizer: detected memory leaks
Direct leak of 1024 byte(s) in 1 object(s) allocated from:
    #0 0x7fff201a4e12 in malloc (asan_rt.dll+0x34e12)
    #1 0x7fff12341050 in bzalloc D:\obs-studio\libobs\util\bmem.c:35
    #2 0x7fff12389a42 in obs_data_create D:\obs-studio\libobs\obs-data.c:85
    #3 0x7fff04561a2b in CustomFilter::UpdateSettings() D:\plugin\src\filter.cpp:112
    #4 0x7fff04562100 in filter_update D:\plugin\src\filter.cpp:180
    #5 0x7fff1235de89 in obs_source_update D:\obs-studio\libobs\obs-source.c:1450
    #6 0x7fff1235e120 in video_thread D:\obs-studio\libobs\obs-video.c:640

To read this trace efficiently:

1. Identify the Boundary of Responsibility

Look for the transition point between libobs (or OS libraries) and your plugin binary.

  • Frames #6 and #5 originate inside obs-video.c and obs-source.c. This demonstrates that the allocation was initiated by OBS's render loop calling into your plugin.
  • Frame #4 (filter_update) marks the entry into the plugin boundary.
  • Frame #3 (CustomFilter::UpdateSettings) is the last plugin frame before handing execution to the core OBS memory utilities. The bug is almost universally located within this function.

2. Differentiate the Allocation Mechanism

Frame #1 shows bzalloc, which is the base zero-allocation utility in libobs, called inside obs_data_create (Frame #2).

  • If the allocation is standard C++ (operator new or std::make_shared), the trace will point directly into standard library templates.
  • If the allocation originates from libobs helper functions (bmemdup, bstrdup, obs_data_create), the allocation follows OBS's internal memory semantics, not native C++ semantics.

Common OBS Plugin Leak Patterns

Stack traces pinpoint where memory was allocated, not where it failed to be freed. Use the allocation site to check for these standard OBS API mistakes:

Leaked obs_data_t Structures

If the top frames show obs_data_create, obs_data_create_from_json, or obs_source_get_settings, an obs_data_t reference was incremented.

  • The Fix: In OBS C/C++, obs_data_t objects are reference-counted. Every call to obtain settings or create a data container requires a corresponding obs_data_release(data). In modern C++, wrap these pointers inside OBSData RAII wrappers (obs-data.hpp).

Leaked Source and Scene References

If the trace shows allocations inside obs_source_create or obs_get_source_by_name:

  • The Fix: Functions that look up or create sources increment the internal reference count of the target source. If your plugin caches these pointers inside member variables, ensure obs_source_release(source) is invoked during cleanup or when reassigning the variable.

Graphics Texture Leaks

Traces showing allocations via gs_texture_create, gs_vertexbuffer_create, or gs_stagesurf_create signify that GPU resources were allocated on the graphics thread.

  • The Fix: Graphics memory allocations must be freed within an active graphics context using obs_enter_graphics() followed by the corresponding gs_*_destroy() function, and finalized with obs_leave_graphics(). If the stack trace shows the creation occurred inside your video_render callback, verify that the plugin is not re-creating static textures per frame.

Mixed Allocator Mismatches

If a trace displays a leak involving standard allocations (malloc or new[]) interacting with OBS routines:

  • The Fix: Never free a pointer allocated by bmalloc/bzalloc using the standard C++ delete operator or standard C free. Always use bfree. Mixing native runtimes with OBS memory allocators causes heap corruption or silent leaks depending on the platform's CRT implementation.
