Prevent OBS Studio Lua Script Memory Leaks

Dynamically loading and unloading hundreds of media files in OBS Studio using Lua requires careful management of the boundary between the Lua runtime and OBS Studio's C-based core architecture (libobs). OBS Studio prevents memory leaks not through automated garbage collection alone, but through explicit reference counting, media decoder eviction policies, and dedicated C-API cleanup bindings exposed to Lua. Understanding how to correctly manipulate these mechanisms ensures both system RAM and GPU VRAM are reclaimed immediately when media assets are cycled.

C-Level Reference Counting (obs_source_release)

OBS Studio's core tracks every media source via an internal reference counter. When a Lua script creates a source using obs_source_create or retrieves a handle to an existing source, the core increments this counter.

Lua scripts must explicitly pair every creation or retrieval call with obs_source_release. Setting a Lua variable to nil does not immediately free the underlying C source. If obs_source_release is omitted, the C object remains pinned in memory indefinitely, along with its associated audio buffers and video contexts, even if the Lua garbage collector removes the wrapper object.

The Lua Garbage Collection Disconnect

Lua’s garbage collector (LuaJIT in standard OBS builds) monitors only the memory allocated inside the Lua state. A pointer to an OBS media source consumes negligible memory inside Lua (often just a few bytes for a userdata wrapper), while the native C-side object may consume hundreds of megabytes of decoded frames and texture allocations.

Because Lua does not perceive this heavy memory pressure, its automatic garbage collection cycle will not trigger aggressively enough to clean up cycled media files. While OBS provides __gc metamethods on its userdata wrappers as a fallback, relying on automatic garbage collection during high-volume file turnover causes rapid out-of-memory crashes. Scripts must explicitly invoke removal routines rather than waiting for Lua to collect orphaned wrappers.

Data Settings Management (obs_data_release)

Loading new files requires interacting with OBS data containers (obs_data_t) to set properties such as the file path (local_file). Like sources, data objects are reference-counted.

A common vector for memory leaks when cycling media is failing to release data containers:

  • Calling obs_data_create() or obs_source_get_settings() increments the reference counter.
  • The settings must be applied to the source via obs_source_update().
  • The data container must immediately be freed using obs_data_release().

Failing to call obs_data_release leaves configuration dictionaries allocated in memory, which compounds into significant leaks across hundreds of file swaps.

Modifying Existing Sources vs. Recreating Sources

To eliminate the overhead and leak risks of constantly allocating and freeing full source structures, scripts can reuse a persistent ffmpeg_source or image_source instance:

  1. Create a single static media source during script initialization.
  2. Dynamically update the local_file property using obs_data_set_string to point to the new asset.
  3. Call obs_source_update to signal the underlying FFmpeg demuxer to flush existing frame queues, terminate the current read thread, and open the new target file.

This approach bypasses the creation and destruction of graphics pipelines and scene items, keeping allocation churn to a minimum.

Decoder Eviction and Texture Cleanup

When a media source must be removed completely, removing it from a scene via obs_sceneitem_remove does not destroy the source if references remain elsewhere. The complete teardown sequence requires:

  1. Removing the scene item to detach it from the rendering tree.
  2. Calling obs_source_remove to signal that the source is pending deletion.
  3. Invoking obs_source_release on any local references held by the script.

Once the internal reference count drops to zero, libobs triggers the destructor for the underlying plugin (such as the FFmpeg decoder). This halts decoding threads, unloads cached audio packets, flushes rendering swapchains, and frees the associated Direct3D 11 or OpenGL textures from VRAM.
