OBS SRT Listener Latency vs Packet Recovery

Configuring an SRT (Secure Reliable Transport) listener connection in OBS Studio requires balancing transmission delay against stream stability over unreliable networks. This article examines the core parameters—primarily latency and rcvbuf—that dictate the trade-off between real-time responsiveness and the time allocated for Automatic Repeat reQuest (ARQ) packet recovery.

The Primary Parameter: latency

When setting up OBS Studio as an SRT listener (srt://0.0.0.0:PORT?mode=listener), the single most critical parameter governing this trade-off is latency (specified in milliseconds). In listener/receiver scenarios, you can also specify this as rcvlatency.

  • How It Works: SRT enforces a fixed delay buffer before passing audio and video frames to the OBS decoder. If a packet is dropped in transit, the receiver detects the missing sequence number and sends a negative acknowledgment (NAK) back to the sender. The sender then retransmits the missing packet.
  • Low Latency (< 120 ms): Minimizes delay, which is ideal for interactive scenarios like live interviews or remote commentary. However, if the round-trip time (RTT) plus processing time exceeds this value, missing packets cannot be recovered before playout time, resulting in dropped frames, macroblocking, or stutter.
  • High Latency (> 500 ms): Provides a robust safety margin. The receiver can request multiple retransmissions of missing data, ensuring perfect stream continuity over high-jitter, high-loss connections (such as public cellular bonding or intercontinental routes), at the expense of real-time interactivity.

Calculating the Ideal Latency Setting

To establish an optimal balance, the configured latency must be proportional to the Round-Trip Time (RTT) and the packet loss percentage of the link:

  • Good Network (Loss < 1%): latency = RTT * 2.5 (Minimum recommended: 120 ms)
  • Average Network (Loss 1%–5%): latency = RTT * 3 or RTT * 4
  • Poor/Unstable Network (Loss > 10%): latency = RTT * 5 or higher

In OBS Studio, append this parameter directly to the stream or media source URL:

srt://0.0.0.0:9998?mode=listener&latency=200

Supporting Parameter: rcvbuf (Receive Buffer Size)

The rcvbuf parameter sets the socket receive buffer size in bytes.

  • The Trade-off: By default, the underlying SRT library calculates this dynamically based on the configured latency and maximum flight window. However, when streaming at high bitrates (e.g., 4K or high-framerate 1080p) combined with high latency settings, the default OS or library buffer may become a bottleneck.
  • Impact on Recovery: If rcvbuf is too small, incoming out-of-order packets and retransmitted data will overflow the buffer and be dropped by the operating system kernel before the SRT recovery layer can process them, completely undermining high latency configurations.

Playout Delay Management: drift_tracer and tsbpd

SRT uses Timestamp-Based Packet Delivery (tsbpd=1, enabled by default) to reproduce the exact timing of the source stream.

  • Packet Recovery Deadline: Packets that do not arrive before their playout deadline are considered "too late" and are permanently skipped by the receiver to maintain synchronization.
  • Trade-off Impact: Setting a lower latency parameter shortens this deadline window, directly sacrificing packet recovery capability in favor of lower time-to-glass delay.
