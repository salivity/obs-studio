Why Looping WebM Videos Leak Memory in OBS Studio

Running transparent WebM animations on an endless loop in OBS Studio often leads to significant memory accumulation over days of uninterrupted streaming. This progressive memory leak stems from the interaction between OBS Studio’s media engine, FFmpeg’s decoding pipeline, alpha-channel pixel buffer allocation, and texture memory management during video loop resets. Understanding how these components process transparent VP8 and VP9 video reveals why these leaks occur and how to resolve them.

Dual-Stream Alpha Channel Decoding in libvpx

WebM supports transparency primarily by encoding two separate video streams inside a single Matroska container: a standard color stream (encoded in YUV420p using VP8 or VP9) and an auxiliary alpha plane (encoded as a grayscale stream representing opacity).

When OBS Studio decodes this file via FFmpeg and the underlying libvpx library, it must synchronize and composite these two independent streams into a single RGBA or BGRA surface for every rendered frame. During continuous multi-day playback, the reference frame buffers and pixel conversion contexts allocated for this dual-plane merging process are not always fully reclaimed. Small, byte-level allocations remain retained in unmanaged heap memory during the demuxing phase, gradually expanding system RAM usage over millions of decoded frames.

Texture Allocation Failures on Loop Boundary Resets

When a standard Media Source in OBS hits the end of a video stream and loops back to timestamp zero, it triggers a seek event or a demuxer flush.

During this loop transition:

  • The decoder flushes its internal frame buffers to prepare for the incoming keyframe.
  • OBS must synchronize the CPU-decoded software frames with the GPU rendering context (Direct3D 11 on Windows or Metal/OpenGL on macOS/Linux).
  • If the rendering thread fails to release the previous loop's GPU staging textures before allocating new ones for the incoming frames, orphaned texture handles persist in VRAM and shared system memory.

Because transparent video frames require twice the buffer management (color plus alpha) compared to opaque videos, any dropped deallocation instruction at the loop boundary compounds rapidly when looping short animations (such as 3- to 10-second alerts or overlays) thousands of times per day.

Incomplete Hardware Acceleration Fallback

Most consumer GPUs lack dedicated hardware decoding support for VP8/VP9 video streams containing an alpha channel. While standard VP9 decodes cleanly on modern NVDEC or Intel Quick Sync hardware, alpha-layer WebM files force OBS Studio to fall back to software decoding on the CPU.

Software decoding in OBS runs through FFmpeg's multithreaded slice decoders. Over days of execution:

  • Thread pools maintain internal scratch buffers that expand dynamically to accommodate difficult-to-decode intra-frames.
  • Memory allocators like Windows' default heap manager often suffer from heap fragmentation when handling continuous dynamic buffer allocations of alternating sizes.
  • Even if the decoder marks the memory as free, fragmented heap structures prevent the operating system from reclaiming the reserved memory pages, causing the OBS process size to climb indefinitely.

Mitigation Strategies

To maintain long-term stability for 24/7 broadcast environments without memory exhaustion, apply the following adjustments:

  • Switch to Native Browser Sources: Render the transparent animation inside an OBS Browser Source using an HTML5 <video> tag or WebGL canvas. Chromium's embedded rendering pipeline handles VP9 alpha garbage collection differently than the native Media Source, often releasing stale textures more reliably.
  • Convert to Alternative Codecs: Use formats that support transparency natively without complex dual-stream syncing, such as QuickTime ProRes 4444 (higher disk footprint, but significantly lower CPU and memory overhead during long runs).
  • Automated Scene/Source Refresh: Utilize an OBS Lua or Python script to toggle the source visibility or restart the media source context once every 24 hours, forcing the operating system and graphics driver to purge all orphaned texture handles and accumulated decoder heap.
