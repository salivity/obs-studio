How OBS Studio Hooks DirectX Swap Chains

This article explores the internal mechanism OBS Studio uses to capture video from high-performance games via DirectX swap chain hooking. By injecting a dedicated dynamic-link library into the target game’s process, OBS intercepts the graphics rendering pipeline right before frames are pushed to the monitor. This process enables direct GPU-to-GPU memory copies, ensuring minimal performance degradation and low latency during high-resolution, high-framerate gameplay recording.

Process Injection and Initialization

OBS Studio cannot intercept game frames from an external process boundary due to operating system memory isolation. To overcome this, OBS utilizes a 32-bit or 64-bit helper service (such as inject-helper.exe) that injects a capture library—commonly named graphics-hook.dll—directly into the target game's address space. This injection typically occurs via Windows APIs like CreateRemoteThread or window hook procedures (SetWindowsHookEx). Once loaded inside the game's memory, the hook DLL identifies the active graphics API used by the executable, such as DirectX 9, DirectX 11, or DirectX 12.

Locating and Hooking the Swap Chain

In modern DirectX applications (DirectX 10 through 12), rendering occurs on an off-screen back buffer managed by the DirectX Graphics Infrastructure (DXGI). When a frame is ready to be drawn to the screen, the game calls the swap chain method:

HRESULT IDXGISwapChain::Present(UINT SyncInterval, UINT Flags);

Because the swap chain is a COM (Component Object Model) interface, its functions are indexed in a Virtual Method Table (VMT). The injected OBS hook locates the memory address of the IDXGISwapChain virtual table by either creating a temporary, dummy DirectX device/swap chain to read the table addresses or by scanning memory patterns.

Once the address of the Present function (and Present1 for newer DXGI versions) is identified, OBS applies an inline detour or replaces the pointer in the VMT. This detour redirects execution of the Present call to an OBS-defined capture callback before the real frame is finalized.

Intercepting the Frame in VRAM

When the game calls Present at the end of a render loop, execution transfers immediately to OBS's custom hook routine. Inside this hook, OBS gains direct access to the IDXGISwapChain pointer:

  1. Back Buffer Retrieval: The hook calls GetBuffer on the swap chain to obtain a reference to the active DirectX surface/texture containing the completed frame.
  2. Texture Copying on the GPU: To prevent the severe performance penalties of copying raw 4K or high-refresh-rate pixel buffers across the PCIe bus into system RAM, OBS keeps the data entirely within video memory (VRAM). It utilizes the GPU's copy engine (such as CopyResource) to transfer the back-buffer texture into an internal shared texture.
  3. Cross-Process Sharing: The shared texture is exposed to the main OBS Studio process using DXGI shared handles (CreateSharedHandle or OpenSharedResource). This allows the primary OBS rendering engine to access the texture directly from its own DirectX context on the GPU without CPU intervention.

Synchronization and Frame Hand-off

DirectX operations are asynchronous. To ensure that OBS does not read a texture while the game is still drawing to it, or vice versa, the hook uses synchronization primitives. In DirectX 11 and 12, this is managed via DXGI Keyed Mutexes or DirectX fences. These lightweight hardware sync objects alert the primary OBS composition thread when the copy is complete.

After scheduling the copy and managing the synchronization state, the OBS hook invokes the original, unhooked IDXGISwapChain::Present function. The game's back buffer flips to the front buffer and displays on the user’s monitor as intended, with the capture overhead restricted to a fraction of a millisecond.
