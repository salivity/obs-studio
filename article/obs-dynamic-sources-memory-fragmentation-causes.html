OBS Dynamic Sources Memory Fragmentation Causes

Repeatedly creating and destroying dynamic sources through OBS Studio scripts often leads to severe memory fragmentation, degrading streaming performance and eventually causing software crashes. This article examines the core architectural causes behind this issue, focusing on low-level heap behaviors, scripting language garbage collection mismatches, graphics API resource allocation, and the absence of native dynamic pooling mechanisms.

Heterogeneous Heap Allocation Sizes

An OBS Studio source is not a single, uniform block of memory. When obs_source_create is invoked, the core engine and its dependent plugins allocate dozens of separate memory segments of wildly varying sizes. These include:

  • Small metadata objects (names, settings, channel references).
  • Medium-sized audio ring buffers and parameter structures.
  • Large staging textures, color format conversion buffers, and frame caches.

Because standard C runtime allocators (such as Windows Heap Manager or glibc's ptmalloc) assign memory from a shared heap, alternating the creation and destruction of differently sized buffers leaves isolated, non-contiguous "holes" of free memory. Over time, while the total free memory may appear sufficient, contiguous memory blocks become too small to satisfy new multi-megabyte allocations, leading to out-of-memory errors.

Scripting Layer and Garbage Collection Desynchronization

When writing OBS scripts using Python or Lua, dynamic sources are controlled via foreign function interface (FFI) bindings. Memory management between the scripting engine and the underlying C codebase is inherently decoupled:

  • Delayed Destructors: Languages like Python and Lua rely on automatic garbage collection. Even if a script explicitly drops a reference to a source, the wrapper object may not immediately trigger obs_source_release().
  • Interleaved Lifetimes: Because native memory is released at unpredictable garbage collector intervals rather than immediately when a scene or layout changes, allocations and deallocations become heavily interleaved, compounding heap fragmentation.
  • Reference Leaking: If signal handlers, property references, or event callbacks within the script retain implicit pointers to a source, the source transitions into a "zombie" state where partial teardown occurs, but associated structures remain pinned in memory.

GPU and Graphics Driver Resource Churn

Dynamic sources frequently instantiate textures and shaders on the GPU via Direct3D 11 (on Windows) or OpenGL/Metal (on other operating systems). Repeated source creation stresses graphics driver-level memory managers:

  1. VRAM Fragmentation: Just like system RAM, video memory suffers from fragmentation when render targets and intermediate textures are created and released rapidly.
  2. Asynchronous Resource Freeing: Graphics APIs often defer the physical release of GPU resources until current rendering commands in the pipeline are flushed. Rapid script loops can request new texture memory faster than the driver cleans up discarded resources, resulting in temporary allocation spikes and fragmented address space.

Lack of Built-in Object Pooling

OBS Studio is architected primarily for stable, static broadcast setups where sources are configured once and persist throughout a production. The native API does not feature an automatic object pool for dynamic sources.

When a script treats OBS like a transient graphics engine—generating, rendering, and destroying sources on the fly—it bypasses the performance advantages of reuse. Without an explicitly implemented pooling layer, the underlying memory manager must repeatedly split and coalesce memory blocks, accelerating heap degradation.
