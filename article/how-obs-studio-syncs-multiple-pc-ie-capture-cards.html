How OBS Studio Syncs Multiple PCIe Capture Cards

This article explains how OBS Studio maintains frame order consistency when capturing asynchronous video inputs from multiple PCIe capture cards. It details how the software processes independent hardware streams using internal presentation timestamps (PTS), dedicated source buffers, master clock synchronization, and a decoupled graphics rendering loop to eliminate frame drift and visual stuttering.

Hardware Timestamps and Ingestion

Each PCIe capture card operates on its own independent onboard pixel clock and analog-to-digital converter. Because these hardware clocks drift relative to one another and the host system, inputs are inherently asynchronous.

When a video frame arrives via the PCIe bus, the capture driver (utilizing APIs such as DirectShow, Media Foundation, or vendor-specific SDKs like Blackmagic DeckLink) attaches a Presentation Time Stamp (PTS) to the frame. OBS Studio reads these timestamps to identify precisely when each frame was captured relative to the operating system’s high-precision monotonic clock (such as Windows' QueryPerformanceCounter or Linux's CLOCK_MONOTONIC).

Input Buffering and Thread Decoupling

To prevent capture thread bottlenecks from stalling the application, OBS assigns each video input to an independent capture thread.

Frames received from each PCIe card are placed into a thread-safe circular FIFO (First-In, First-Out) queue. This queue serves as a de-jitter buffer that absorbs variations in PCIe bus bandwidth allocation, thread preemption, and minor micro-stutters from individual cards. By decoupling capture ingestion from the rendering pipeline, OBS ensures that a momentary delay on one PCIe lane does not block other capture devices.

The OBS Reference Clock

OBS Studio synchronizes all sources against a global reference clock. In standard configurations, OBS uses the audio output subsystem as the master timing clock, as the human ear is far more sensitive to audio gaps and pitch variations than the eye is to frame adjustments. If no audio is active, the system monotonic clock acts as the fallback reference.

Incoming video frames are mapped from their source capture timestamps onto this shared master timeline. This creates a unified temporal baseline where frames from Card A and Card B can be evaluated together, regardless of their native frame rates or clock divergence.

The Fixed-Rate Render Loop

The OBS rendering pipeline runs on an independent graphics thread tied strictly to the user’s target output framerate (for example, exactly every 16.66 milliseconds for a 60 FPS canvas).

During each render tick, the compositing engine queries the frame buffer of each capture card:

  • Frame Selection: OBS inspects the timestamps in the buffer and selects the frame whose timestamp is closest to, but does not exceed, the current render tick timestamp.
  • Frame Dropping: If a capture card delivers frames faster than the OBS render rate, any intermediate frames that have been superseded by a newer valid frame are discarded to prevent input lag from accumulating.
  • Frame Duplication: If a card experiences a latency spike or operates at a lower refresh rate, the rendering engine holds and re-renders the most recent valid frame, preventing blank spaces or tearing.

By evaluating every PCIe source against the master timeline during each discrete graphics tick, OBS Studio guarantees that all inputs are displayed in their correct chronological sequence on the final composited canvas.
