RTMP vs RTMPS Overhead Differences in OBS Studio

This article provides an analysis of the packet overhead differences between standard Real-Time Messaging Protocol (RTMP) and TLS-encrypted RTMP (RTMPS) when streaming with OBS Studio. It examines the protocol stack layers, the cryptographic and framing additions introduced by transport layer security, and the real-world bandwidth and network impact of choosing secure streaming over plain text.

Protocol Stack Comparison

Standard RTMP and RTMPS use identical application-level framing for video and audio data within OBS Studio, but they diverge at the transport encapsulation layer.

  • Standard RTMP: Application Data (FLV/Audio/Video) → RTMP Chunk Stream → TCP → IP → Data Link (Ethernet)
  • RTMPS: Application Data (FLV/Audio/Video) → RTMP Chunk Stream → TLS Record Layer → TCP → IP → Data Link (Ethernet)

OBS Studio multiplexes media into RTMP chunks (typically set to a default chunk size of 4096 bytes after the initial handshake). The key difference in transmission lies in how these chunks are prepared before being written to the network socket.

Byte-Level Header and Framing Overhead

1. Base Transport and RTMP Encapsulation

In a standard RTMP connection (usually over TCP port 1935), the data path includes:

  • IP Header: 20 bytes (IPv4) or 40 bytes (IPv6).
  • TCP Header: 20 to 32 bytes (depending on TCP options like timestamps).
  • RTMP Chunk Header: 1 to 18 bytes per chunk. In continuous streaming inside OBS, Type 3 chunk headers (which omit the message header and only include a 1-byte basic header) are used for subsequent fragments of the same stream, averaging 1 to 4 bytes per chunk.

2. TLS Layer Additions in RTMPS

When RTMPS is selected (typically over TCP port 443), OBS Studio routes the RTMP byte stream through a TLS session (utilizing mbedTLS, Schannel, or Secure Transport depending on the operating system build). Modern RTMPS negotiations utilize TLS 1.2 or TLS 1.3 with authenticated encryption (AEAD), such as AES-GCM or ChaCha20-Poly1305.

The TLS record layer adds overhead directly to the payload:

  • TLS Record Header: 5 bytes per record (Content Type, Protocol Version, and Length).
  • Explicit Nonce / IV: 8 bytes (present in TLS 1.2 AES-GCM; omitted in TLS 1.3).
  • Authentication Tag (MAC): 16 bytes for standard AEAD ciphers (AES-128-GCM, AES-256-GCM, or ChaCha20-Poly1305).
  • Inner Content Type: 1 byte (present in TLS 1.3).

Depending on the negotiated TLS version, the steady-state overhead ranges from 22 bytes (TLS 1.3) to 29 bytes (TLS 1.2) per TLS record.

Interaction with MTU and TCP Segmentation

The Maximum Transmission Unit (MTU) for standard Ethernet is 1500 bytes, yielding a Maximum Segment Size (MSS) of roughly 1460 bytes for IPv4 TCP payloads.

  • Standard RTMP: An OBS RTMP chunk of 4096 bytes is split across multiple TCP packets. A 4096-byte chunk plus RTMP headers fits across three standard TCP packets (e.g., 1460 + 1460 + 1180 bytes), with each packet requiring standard IP and TCP headers.
  • RTMPS: The TLS implementation in OBS generally packages outgoing data into TLS records before passing them to the TCP stack. If a TLS record spans multiple TCP segments, the TLS framing overhead is incurred once per record rather than per TCP packet. However, if records are aligned to network buffers or flushed frequently to reduce latency, small records can cause additional overhead.

Because OBS flushes audio and video data rapidly to maintain low latency, audio packets (which are significantly smaller than video keyframes) suffer a higher proportional overhead under RTMPS due to the static 21–29 byte TLS record wrapper on small payloads.

Initial Connection Overhead

RTMPS requires an expanded connection sequence compared to plain RTMP:

  • RTMP Handshake: Consists of C0/S0, C1/S1, and C2/S2 packets (1537 bytes sent each way) before the RTMP connect command.
  • TLS Handshake: Prior to the RTMP handshake, RTMPS must complete the TLS handshake. This adds 1 to 2 network round trips and exchanges between 3 KB and 6 KB of additional data, primarily due to the server's X.509 certificate chain.

Once the connection is established, this handshake overhead ceases to affect the stream.

Practical Bandwidth Impact

In continuous streaming scenarios inside OBS Studio:

  • At a typical video bitrate of 6000 kbps, standard RTMP protocol overhead (IP, TCP, RTMP headers) accounts for roughly 1.5% to 2.5% of the total bandwidth.
  • RTMPS increases this total overhead to approximately 2.0% to 3.5%, depending on the ratio of audio-to-video frames and the MTU efficiency.

The real-world throughput difference is negligible—representing an additional 30 to 70 kbps on a 6000 kbps broadcast. RTMPS prevents stream tampering, ISP throttling based on deep packet inspection, and eavesdropping, with a minimal trade-off in network packet overhead.
