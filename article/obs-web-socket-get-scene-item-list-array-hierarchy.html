OBS WebSocket GetSceneItemList Array Hierarchy

This article provides an architectural overview of the sceneItems array returned by the GetSceneItemList request in OBS Studio's WebSocket protocol (v5.x). It breaks down the flat structure of the response payload, how Z-order and rendering priority are expressed, and how hierarchical structures like nested scenes and item groups are represented and navigated.

Top-Level Response Structure

When sending a GetSceneItemList request, OBS WebSocket returns a response object containing a responseData payload. Within this payload, the primary data structure is the sceneItems array.

The structure of the JSON payload is formatted as follows:

{
  "op": 7,
  "d": {
    "requestType": "GetSceneItemList",
    "requestStatus": {
      "result": true,
      "code": 100
    },
    "responseData": {
      "sceneItems": [
        {
          "inputKind": null,
          "isGroup": false,
          "sceneItemBlendMode": "OBS_BLEND_NORMAL",
          "sceneItemEnabled": true,
          "sceneItemId": 1,
          "sceneItemIndex": 0,
          "sceneItemLocked": false,
          "sceneItemTransform": { ... },
          "sourceName": "Background Image",
          "sourceType": "OBS_SOURCE_TYPE_INPUT",
          "sourceUuid": "..."
        }
      ]
    }
  }
}

Flat Array Model and Z-Order

Despite scenes in OBS Studio presenting visually as complex layer stacks, GetSceneItemList returns a single-dimensional, flat array. There is no automatic recursive nesting of objects within this specific response.

The stacking order (Z-order) of the elements is dictated by the sceneItemIndex field:

  • Lowest Index (sceneItemIndex: 0): Represents the bottom-most layer on the visual canvas. This item renders first, underneath all other items.
  • Highest Index: Represents the top-most layer on the canvas. It renders last and appears visually in front of other sources.
  • Array Sequence: In standard implementations, the items in the sceneItems array are sorted to align with the visual rendering order, but clients should always rely on sceneItemIndex to programmatically determine canvas priority.

Identification: IDs vs. Names

Each entry in the sceneItems array differentiates between the container on the canvas and the underlying source:

  • sceneItemId: An integer unique only within the scope of the parent scene. If the same source is added to a scene twice, each instance receives a distinct sceneItemId.
  • sourceName and sourceUuid: The global identifier for the underlying asset (e.g., a media file, capture device, or nested scene).
  • sourceType: Distinguishes between standard inputs (OBS_SOURCE_TYPE_INPUT) and scenes (OBS_SOURCE_TYPE_SCENE).

Handling Groups and Nested Hierarchy

The hierarchy for groups and nested scenes is handled non-recursively:

  1. Item Groups (isGroup: true):

    • Groups exist as single entries within the sceneItems array.
    • The group container has its own sceneItemId and sceneItemIndex within the scene.
    • The individual items inside that group are not nested inside the item object. To retrieve the contents of a group, a separate GetGroupSceneItemList request must be made using the group's name.

  2. Nested Scenes (sourceType: "OBS_SOURCE_TYPE_SCENE"):

    • When another scene is used as a source, it appears as a standard item within the array.
    • Its inner components are not expanded inside the current payload.
    • To build a complete tree of a multi-scene composition, client applications must inspect each item's sourceType, identify nested scenes, and issue recursive GetSceneItemList requests using the child scene's sourceName or sourceUuid.
