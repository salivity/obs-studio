How OBS Studio Manages Browser Source Processes

OBS Studio relies on the Chromium Embedded Framework (CEF) to render web-based overlays, alerts, and pages natively within its compositor. Managing these web elements involves a combination of native C++ lifecycle management, shared memory buffer recycling, and CEF render process termination. This article explains how OBS Studio coordinates with CEF to clean up, garbage-collect, and destroy unused browser source render processes to maintain stable performance during streaming and recording sessions.

The Multi-Process CEF Architecture

OBS Studio runs CEF using a multi-process architecture. The main OBS process acts as the browser host, while web pages execute inside isolated helper processes (typically named obs-browser-page.exe on Windows or equivalent helper processes on macOS and Linux). Each browser source can spawn its own renderer process to isolate crashes and distribute compute loads.

Within this framework, process management divides into two primary tiers: internal JavaScript memory management handled by Google's V8 engine inside the renderer, and operating-system-level process destruction governed directly by the OBS Browser plugin via C++.

Visibility States and Process Dormancy

OBS Studio gives users direct control over resource management through the "Shutdown source when not visible" and "Refresh browser when scene becomes active" settings found in each browser source's properties.

  • When "Shutdown source when not visible" is disabled: Switching away from a scene does not destroy the underlying renderer process. OBS merely stops capturing the shared GPU texture and suspends drawing calls. The render process remains alive in system memory, maintaining its DOM state and running background JavaScript unless throttled.
  • When "Shutdown source when not visible" is enabled: Changing scenes prompts OBS to begin immediate teardown. The browser plugin marks the source inactive and begins destroying the CEF browser client.

Destruction of Render Processes

When a browser source is hidden (with the shutdown flag enabled) or permanently deleted from a scene, OBS Studio initiates a structured tear-down process:

  1. Host-Side Closure: The OBS source plugin drops internal references to the browser instance and invokes CEF's CefBrowserHost::CloseBrowser(true). The true parameter forces an immediate closure, bypassing client-side prompts such as beforeunload dialogs.
  2. IPC Termination: The host process severs the Inter-Process Communication (IPC) pipes connecting OBS to the associated renderer subprocess.
  3. Subprocess Teardown: Upon receiving the close signal and detecting the severed IPC channel, the isolated renderer process initiates its own exit sequence. If the subprocess fails to exit cleanly within a brief operating system timeout, the operating system reclaims the process table entry.
  4. Plugin Reference Counting: OBS manages sources through an internal reference-counted model (obs_source_t). Once the source count drops to zero—either via user deletion or scene collection switching—the source's destructor callback executes, deleting the wrapper C++ objects and releasing any associated callbacks.

Shared Memory and GPU Texture Reclamation

Browser sources in OBS do not render directly onto the main graphics canvas; they write into shared memory or direct GPU surfaces:

  • Hardware-Accelerated Path: CEF writes rendered frames into a shared DirectX or OpenGL texture handle. When the source is destroyed or shut down, OBS calls graphics API releases on these textures to prevent VRAM exhaustion.
  • Software Fallback Path: If hardware acceleration is disabled, CEF renders into shared RAM buffers. The OBS browser wrapper frees these shared memory maps immediately after tearing down the browser host.

V8 Engine Garbage Collection

For browser sources that stay active continuously, OBS relies on the V8 JavaScript engine embedded in CEF to manage memory. CEF periodically runs incremental and full garbage collection cycles to sweep unreachable DOM nodes, script variables, and cached textures.

However, long-running web overlays with unoptimized JavaScript (such as memory leaks in custom web animations or recurring setInterval loops) can cause the helper process's memory footprint to grow steadily. In such cases, internal garbage collection cannot release references that the web code inadvertently holds. The only definitive reclamation occurs when OBS destroys the entire process using the "Shutdown source when not visible" workflow or by manually refreshing the source cache.
