Cross-Reference OBS Studio Crashes in Event Viewer

When OBS Studio unexpectedly crashes or causes a full system freeze, the root cause is frequently tied to underlying hardware instability, driver timeouts, or power delivery issues rather than the software itself. This guide outlines how to pinpoint the exact timestamp of an OBS failure using its internal logs, locate the corresponding critical events within the Windows Event Viewer, and identify the specific hardware or driver faults responsible for the disruption.

Step 1: Find the Exact OBS Studio Crash Timestamp

Before investigating Windows logs, you must establish the exact second the failure occurred.

  1. Open File Explorer and enter %APPDATA%\obs-studio\crashes into the address bar, then press Enter. Alternatively, if OBS can still open, navigate to Help > Crash Logs > Show Crash Logs.
  2. Look at the file names in the folder. OBS formats crash logs with the date and time of the crash (e.g., Crash 2023-10-25 18-42-15.txt).
  3. Open the latest crash log. The very top of the file displays the precise date and time of the termination, as well as the faulting thread. Note down this exact timestamp (down to the minute and second).

Step 2: Open Windows Event Viewer

  1. Press Windows Key + R to open the Run dialog box.
  2. Type eventvwr.msc and press Enter to launch the Windows Event Viewer.

Step 3: Filter Logs Around the Crash Time

Windows logs thousands of events daily, making manual searching inefficient. Narrow down the search window to match your OBS crash.

  1. In the left sidebar, expand Windows Logs.
  2. Right-click on System and select Filter Current Log....
  3. Under the Logged drop-down menu, select Custom range....
  4. Choose Events logged, set the range to cover 5 minutes before and 5 minutes after your OBS crash timestamp, and click OK.
  5. Check the boxes for Critical, Warning, and Error.
  6. Click OK to apply the filter.
  7. Repeat this process for the Application log under Windows Logs to capture process-level hardware interactions.

Step 4: Identify Hardware and Driver Error Sources

Look for events that align directly with the recorded OBS timestamp. Focus on the following key event sources and Event IDs:

  • WHEA-Logger (Windows Hardware Error Architecture):
    • Event IDs 18, 19, or 20: These indicate physical CPU or PCIe bus errors, often caused by unstable overclocks, undervolting, or failing processor cores under the encoding load of OBS.
  • Display / nvlddmkm / amdkmdag (GPU Driver Timeouts):
    • Event ID 4101: Indicates that the display driver stopped responding and was successfully recovered (TDR). If OBS utilizes NVENC, AMF, or heavy GPU rendering, an unstable graphics card clock, overheating, or a corrupted graphics driver will trigger this event simultaneously with the OBS crash.
  • Kernel-Power:
    • Event ID 41: Indicates that the system rebooted without cleanly shutting down first. This points to power supply unit (PSU) tripping under transient power spikes caused by simultaneous CPU/GPU load during streaming or recording.
  • Disk or NTFS Errors:
    • Event IDs 7, 11, or 55: Indicates I/O device errors, bad sectors, or controller timeouts. This occurs when OBS cannot write data fast enough to an overloaded or failing storage drive.

Step 5: Correlate and Diagnose

Compare the findings:

  1. Click on the identified event in the middle pane and review the General tab below.
  2. Cross-reference the faulting module from the OBS crash log (such as a graphics dynamic link library like nvencodeapi64.dll or d3d11.dll) with the Event Viewer error.
  3. If an Event Viewer hardware warning appears at the exact second OBS logged its crash, the crash is confirmed to be a symptom of hardware failure, thermal throttling, or driver instability rather than a core OBS application bug.
