Causes of OBS Audio Drops with macOS CoreAudio

When capturing audio in OBS Studio on macOS via an aggregate device, streamers and producers often encounter dropped samples, stuttering, and synchronization drift. This article explains the technical mechanics behind why these drops occur, detailing the interactions between OBS Studio's capture loop, the macOS coreaudiod background daemon, and hardware clock discrepancies.

1. Clock Drift Between Sub-Devices

An aggregate device bundles multiple physical or virtual audio interfaces into a single virtual interface. Each physical device relies on its own hardware oscillator (crystal clock). Because no two physical clocks run at the exact same frequency, their timing inevitably diverges over time—a phenomenon known as clock drift.

When devices drift:

  • One interface delivers slightly more samples per second than another.
  • The macOS CoreAudio daemon (coreaudiod) must drop or duplicate samples to keep the input stream unified.
  • If Drift Correction is disabled for non-clock-master devices in Audio MIDI Setup, the buffers quickly overflow or underflow, causing noticeable audio dropouts in OBS Studio.

2. CoreAudio Resampling and Drift Correction Latency

Even when Drift Correction is enabled, the CoreAudio daemon corrects drift using a real-time software sample-rate converter (SRC). This process dynamically interpolates samples to match the designated clock source.

Under sudden system resource shifts or heavy CPU/GPU rendering loads produced by OBS:

  • The dynamic resampler can experience micro-delays.
  • The daemon fails to supply the required frame count within the real-time deadline.
  • CoreAudio triggers a buffer underrun, leading to silent gaps or dropped samples in OBS.

3. I/O Buffer Size and Request Mismatches

OBS Studio and CoreAudio communicate via the CoreAudio Hardware Abstraction Layer (HAL). Audio clients can request specific I/O buffer sizes (such as 128, 256, or 512 samples).

When an aggregate device is involved:

  • The aggregate device adopts an internal buffer size that may conflict with the requested buffer size of individual member devices or OBS Studio.
  • If member devices cannot fulfill the aggregate device’s requested I/O cycle in time, coreaudiod is forced to issue empty or incomplete buffers to OBS.
  • Frequent buffer resets occur if an application changes the global sample rate or buffer size dynamically, leading to cascading dropouts.

4. Sample Rate Discrepancies Across the Pipeline

OBS Studio typically operates at a fixed internal rate of 44.1 kHz or 48 kHz. For an aggregate device to function reliably:

  • Every member device must support and be locked to the exact same nominal sample rate.
  • The aggregate device itself must match the project sample rate inside OBS Studio Settings (Settings > Audio).

If an aggregate device contains a sub-device locked to 44.1 kHz while the aggregate device and OBS are configured to 48 kHz, macOS forces secondary resampling outside the native driver. This multi-stage conversion increases jitter and drastically raises the probability of buffer starvation.

5. Virtual Driver Timing Flaws

Aggregate devices often include virtual pass-through drivers (such as BlackHole, Loopback, or older solutions like Soundflower) to route desktop audio into OBS. Unlike physical audio interfaces, virtual drivers lack hardware timing mechanisms and instead rely on CPU timers to clock audio.

Because CPU-based clocks do not track at the same cadence as hardware audio chips:

  • The virtual driver easily falls out of sync with hardware microphones or audio interfaces.
  • CoreAudio struggles to arbitrate the master clock when a clockless virtual device is designated as the primary clock source.
  • The resulting timing mismatches produce regular sample dropouts, audible clicks, or robotic pitch artifacts.

6. Thread Priority Inversion and Scheduling Pressure

Audio threads in macOS run under real-time Mach thread constraints, which prioritize audio processing above general application tasks. However, OBS Studio simultaneously executes heavy video encoding, scene compositing, and network I/O.

If the main thread or encoding threads consume excessive CPU or memory bandwidth:

  • The OBS audio capture callback might not retrieve the aggregate device's buffer before the ring buffer wraps around.
  • When OBS fails to read from the HAL ring buffer before the aggregate device writes new data, an audio overrun occurs, discarding old samples entirely.
