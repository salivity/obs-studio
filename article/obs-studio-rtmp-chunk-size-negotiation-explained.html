OBS Studio RTMP Chunk Size Negotiation Explained

This article explores how OBS Studio negotiates Real-Time Messaging Protocol (RTMP) chunk sizes when connecting to ingest edge servers. By default, the legacy RTMP specification limits chunk sizes to 128 bytes, which introduces excessive header overhead for modern high-definition video. To ensure efficient network throughput and reduced CPU consumption, OBS Studio requests a substantially larger chunk size—typically 4096 bytes—immediately following the initial connection handshake.

The Default RTMP Chunk Size Problem

The original RTMP specification mandates a default chunk size of 128 bytes. Every video and audio packet must be fragmented into chunks of this size, each prepended with an RTMP chunk header ranging from 1 to 18 bytes. For modern streaming bitrates (such as 6,000 to 10,000 kbps for 1080p60 content), a 128-byte chunk size generates millions of fragments per stream, significantly increasing packet processing overhead and overall bandwidth waste on both the broadcasting client and the ingest edge server.

OBS Studio Connection and Handshake Flow

When establishing a connection, OBS Studio adheres to the standard RTMP connection sequence:

  1. Handshake: OBS Studio initiates and completes the standard three-way RTMP handshake (C0/C1, S0/S1/S2, and C2) to establish raw socket synchronization.
  2. Connect Command: OBS Studio sends the connect command along with application metadata (such as the target app name and Flash version string).
  3. Chunk Size Declaration: Right after the connection command is established or during the initial session setup, OBS Studio sends a Set Chunk Size protocol control message.

Mechanics of the "Set Chunk Size" Message

In RTMP, chunk size adjustments are unidirectional rather than mutually bargained. A sender simply informs the receiver of the chunk size it will use for all subsequent outgoing messages.

  • Message Type: OBS Studio dispatches a Protocol Control Message with Message Type ID 1 (Set Chunk Size).
  • Payload Value: OBS Studio sets this value to 4096 bytes by default via its underlying librtmp and obs-outputs modules. The value is packed as a 32-bit integer, with the most significant bit reserved (set to 0), defining the new chunk size between 1 and 2,147,483,647 bytes.
  • Immediate Activation: Once OBS Studio dispatches this message, every subsequent packet it transmits uses the newly defined 4096-byte boundary. It does not wait for an explicit application-layer acknowledgment to begin transmitting at this size.

Ingest Server Dynamics

Ingest servers—such as NGINX-RTMP, SRS (Simple Realtime Server), and proprietary edge endpoints used by platforms like Twitch and YouTube—monitor incoming stream data for Type 1 control messages.

Upon parsing OBS Studio's Set Chunk Size packet:

  • Buffer Reallocation: The edge server updates its internal state machine to read up to 4096 bytes of incoming message payload before expecting the next chunk basic header.
  • Return Path Separation: Because RTMP chunk sizes are independent for each direction, the server may continue to send control messages, pings, and acknowledgments back to OBS Studio using either the default 128-byte size or its own negotiated chunk size.

By shifting from 128 bytes to 4096 bytes, OBS Studio minimizes protocol overhead to less than 1% of total bandwidth, streamlining packet parsing and reducing CPU interrupts across ingest networks.
