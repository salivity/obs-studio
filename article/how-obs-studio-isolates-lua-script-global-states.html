How OBS Studio Isolates Lua Script Global States

This article explains how the OBS Studio scripting subsystem isolates global variable states between simultaneously loaded Lua scripts. By allocating a dedicated, independent Lua runtime instance to each script rather than sharing a single global environment, OBS Studio eliminates memory crossover, variable shadowing, and unintended side effects across concurrent scripts.

Dedicated lua_State Instances

The core mechanism of OBS Studio's Lua isolation lies within its native scripting backend (obs-scripting-lua). When a user loads a Lua script into OBS Studio, the application does not execute the code within a pre-existing or shared Lua interpreter. Instead, the backend calls luaL_newstate() to instantiate a completely new, private lua_State structure for that specific script.

Because standard Lua maintains its global environment, string tables, registry, and garbage collection metrics inside this lua_State pointer, separating states at the C level ensures that memory boundaries are strictly enforced. Script A and Script B exist in separate virtual machines running side by side within the OBS process space.

Independent Global Tables (_G)

In Lua, global variables reside in the global environment table _G. Because each loaded script operates within its own lua_State, each script receives a unique _G table.

When a script defines a top-level variable or function without the local keyword, that definition is bound strictly to its own state's global environment:

  • Variable assignments in Script A modify only Script A's internal table.
  • Script B querying the same variable name will either read its own independent definition or evaluate to nil.
  • Overwriting built-in Lua functions or standard library behavior in one script does not alter the execution context of any other script.

Swig and C API Binding Isolation

OBS Studio exposes its native API to Lua via bindings generated by SWIG (Simplified Wrapper and Interface Generator), compiled as the obslua module. During the initialization of each distinct lua_State, OBS Studio registers the obslua module and its native helper functions directly into that specific runtime.

While both scripts invoke the same underlying C functions in the OBS core libraries, their pointers, function wrappers, and Lua-side userdata references are created separately inside each state's private memory pool. The scripts interact with the same underlying OBS objects (such as sources, scenes, and outputs) through shared native pointers, but their script-level representations and wrappers remain fully decoupled.

Hook and Callback Segregation

The OBS Studio event and timer systems—such as timer_add, frame rendering hooks, and source event callbacks—track the target lua_State alongside the registered callback function reference. When a timer ticks or an OBS event fires:

  1. The OBS scripting engine identifies the specific native lua_State tied to that callback.
  2. The engine pushes the callback function onto that specific state's virtual stack.
  3. The callback executes within its originating environment, leaving the memory and stacks of other running scripts untouched.

Inter-Script Communication Boundaries

Because global state isolation is total, two Lua scripts cannot communicate directly via shared memory, global variables, or Lua-level tables. If communication between two scripts is required, it must occur indirectly through the native OBS subsystem using shared resources, such as custom data settings via obs_data_t, properties attached to shared scene items, or external mechanisms such as local sockets and disk I/O.
