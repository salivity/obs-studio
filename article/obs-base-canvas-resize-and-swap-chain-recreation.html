OBS Base Canvas Resize and Swap Chain Recreation

Modifying the base canvas dimensions in OBS Studio alters the core resolution of the rendering pipeline, forcing the underlying graphics subsystem to synchronize display contexts and reallocate hardware framebuffers. When this adjustment occurs during an active stream, the application must maintain uninterrupted frame delivery to the encoder while tearing down and rebuilding the display presentation infrastructure. This article details the specific rendering pipeline mechanics, API calls, and buffer invalidation routines that trigger an internal swap chain recreation when modifying base canvas dimensions.

The Role of the Base Canvas in libobs

The base canvas (base_width and base_height) defines the native rendering target where all active scenes, sources, filters, and overlays are composited. In OBS Studio’s graphics wrapper (libobs/graphics), this composition occurs on an internal render target before any downscaling or encoding takes place.

The preview window and internal presentation surfaces rely on a graphics swap chain (typically IDXGISwapChain in Direct3D 11 on Windows, or an equivalent context surface in OpenGL/Metal on other platforms) to cycle backbuffers to the display. The swap chain’s backbuffer dimensions must strictly match the output target surface to avoid hardware presentation mismatches.

Direct Triggers for Swap Chain Recreation

When the base canvas dimensions are modified, the internal swap chain recreation is triggered by a cascading series of lower-level state changes:

  1. Render Target Invalidation: The primary composition surface is bound directly to the base canvas resolution. Changing this parameter invalidates the existing texture references and depth/stencil buffers associated with the previous resolution.
  2. Buffer Dimension Mismatch (DXGI_ERROR_INVALID_CALL): In Direct3D 11, drawing to or presenting a swap chain whose buffer extents do not match the newly assigned viewport parameters results in runtime graphics errors. To prevent fatal presentation failures, the graphics subsystem flags the swap chain as dirty.
  3. Execution of obs_display_resize: When base canvas properties are committed, the subsystem triggers obs_display_resize or the internal graphics device method device_resize. This routine evaluates the target display rect against the current swap chain buffers.
  4. Invocation of ResizeBuffers: Rather than constructing an entirely new DirectX device context, the graphics layer calls IDXGISwapChain::ResizeBuffers (or completely releases and recreates the swap chain if format or flag modifications accompany the size change). This process forces the release of all outstanding references to the backbuffer surfaces, updates the buffer descriptions to match the new canvas width and height, and reallocates the VRAM surfaces.

Separation of Composition and Encoding Pipelines

OBS Studio utilizes an asynchronous rendering architecture where scene composition is separated from output stream encoding:

  • Canvas Surface: The base canvas operates on the main rendering thread where scene items are transformed.
  • Output Scaler: If the output (scaled) resolution differs from the base canvas, intermediate scaling passes handle the conversion before frames reach the encoder.
  • Encoding Queue: The video encoder consumes frames from an output texture queue.

Because of this decoupled architecture, altering the base canvas while streaming forces the composition swap chain to recreate its buffers without necessarily forcing the encoder swap context to reset, provided the output resolution remains constant. However, the momentary GPU pipeline stall required to flush pending draw commands, release backbuffer references, and re-instantiate swap chain textures can cause a transient compositor frame drop.

Impact on Active Frame Presentation

For the swap chain recreation to succeed while streaming, the OBS graphics subsystem executes a synchronized flush:

  1. The rendering thread finishes drawing the current in-flight frame.
  2. All render target views (RTVs) pointing to the old swap chain buffers are explicitly unbound and released.
  3. The underlying API issues the buffer resize command to allocate new video memory matching the modified base canvas dimensions.
  4. New render targets, viewports, and orthographic projection matrices are generated to align with the new coordinate space.
  5. Compositing resumes, routing the updated dimensions to either the preview swap chain or the output scaling chain.
