OBS Studio TCP Reconnect Back-Off Timers Explained

When a livestream drops unexpectedly due to network instability or a severed TCP connection, OBS Studio relies on an internal reconnection subsystem to restore transmission without user intervention. This article explores how OBS Studio detects TCP socket drops, schedules retry intervals, applies back-off timing logic, and manages the reconnection state machine to balance fast recovery against server overload.

TCP Socket Drop Detection

OBS Studio monitors stream health through its output module (primarily obs-outputs via the RTMP/SRT streaming pipelines). Transmission runs across dedicated worker threads separate from rendering and encoding pipelines to prevent network lag from dropping frames locally.

When a TCP connection terminates unexpectedly—such as receiving a TCP RST packet, failing to receive a TCP ACK, or encountering a broken pipe (EPIPE/WSAECONNRESET)—the active socket write call fails. The output thread catches this failure, flags the stream state as disconnected, and triggers the output error callback.

The Reconnection State Machine

Once the error callback fires, OBS Studio shifts its output state from active transmission to an internal reconnecting state. This transitions execution to an asynchronous reconnect thread:

  1. State Isolation: The encoder continues processing frames or buffering a limited queue, preventing the application from crashing while network operations stall.
  2. Resource Teardown: The existing socket descriptor is explicitly closed, freeing local network handles and tearing down the broken RTMP/TLS session.
  3. Timer Dispatch: The reconnect loop queries user-defined settings in Advanced -> Network to initialize the reconnect counters.

Back-Off Timer Architecture

Unlike protocols that enforce hardcoded truncated binary exponential back-off algorithms, OBS Studio employs a deterministic, user-configurable interval timer managed via high-precision OS timing functions (os_sleepto_ns or platform-specific event loops).

  • Retry Delay: Configured in seconds, this parameter defines the base interval the reconnect thread must wait before initiating a new socket handshake (SYN).
  • Linear vs. Constant Scheduling: By default, OBS Studio uses a static interval strategy rather than dynamic exponential growth. If the user configures a 10-second retry delay, the thread sleeps for precisely 10 seconds between each connection attempt.
  • Network Stack Throttling: While OBS maintains a static delay at the application layer, underlying TCP retransmissions within an active attempt are subject to the operating system's kernel-level exponential back-off timers (RTO calculations) before the connection attempt officially times out and returns execution to the OBS reconnect loop.

Retry Counters and Failure Escalation

To prevent infinite loops during extended outages, the subsystem enforces strict limit checks:

  • Maximum Retries: OBS maintains an internal integer counter tracking failed connection handshakes. Each failed connect() call or handshake timeout increments this counter.
  • Exhaustion Threshold: When the incremented value matches the user-defined Max Retries setting, the reconnect loop breaks.
  • State Finalization: Upon counter exhaustion, OBS Studio transitions the output state from reconnecting to fully stopped, emits an error dialog or log entry, and stops sending frames to the discarded pipeline.

Resetting State After Recovery

When a retry succeeds—meaning the TCP three-way handshake completes, TLS/RTMP handshakes validate, and streaming resumes—the reconnect subsystem executes a state-reset routine:

  • The retry counter resets to zero.
  • Frame buffering mechanisms flush outdated or non-keyframe packets to synchronize audio/video delivery.
  • Normal thread scheduling resumes, allowing real-time bitrate adjustment algorithms to re-evaluate available bandwidth over the fresh TCP connection.
