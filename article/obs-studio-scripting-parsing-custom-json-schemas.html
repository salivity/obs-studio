OBS Studio Scripting: Parsing Custom JSON Schemas

This article explains how OBS Studio handles and parses custom JSON data within its built-in Lua and Python scripting engine. It covers the underlying C libraries responsible for deserialization, the role of internal data structures like obs_data_t, and how schema validation operates between user-defined scripts and the core OBS architecture.

The Underlying Parsing Architecture

OBS Studio relies on libobs, its core C library, to handle application logic, data management, and script bindings. When JSON data passes through the scripting engine, OBS does not use an external runtime interpreter for parsing. Instead, it utilizes Jansson, an embedded C library for encoding, decoding, and manipulating JSON data.

At the API level, OBS wraps Jansson structures inside its own native data container: obs_data_t. This object behaves like a typed key-value dictionary that natively supports strings, integers, floats, booleans, arrays (obs_data_array_t), and nested objects.

Deserialization via obs_data_t

When a script receives or passes JSON strings, parsing occurs through the following sequence:

  1. Ingestion: The script invokes functions such as obs_data_create_from_json() or obs_data_create_from_json_file().
  2. C-Level Parsing: libobs forwards the raw string to Jansson's json_loads() function with validation flags enabled to ensure syntactic correctness.
  3. Data Mapping: If valid, the Jansson AST (Abstract Syntax Tree) is recursively traversed, converting JSON types directly into an obs_data_t reference table.
  4. Binding Exposure: The resulting object pointer is wrapped via SWIG (Simplified Wrapper and Interface Generator) for Python or custom C-Lua wrappers, exposing typed getters (such as obs_data_get_string or obs_data_get_int) to the scripting runtime.

Custom Schema Handling and Validation

OBS Studio's core does not natively implement formal JSON Schema specifications (such as JSON Schema Draft-07 or 2020-12). Instead, it enforces schemas through two distinct mechanisms:

1. Property-Driven Declarative Schemas

For standard user inputs, OBS uses the obs_properties_t structure. In functions like script_properties(), the script defines an implicit schema by binding visual UI widgets (text inputs, sliders, lists) to specific keys. When a user changes a setting:

  • OBS validates that the input matches the defined property type.
  • The values are automatically serialized into an obs_data_t settings container.
  • The script's script_update(settings) callback receives the pre-validated settings object.

2. Arbitrary JSON Payloads

When scripts import arbitrary JSON (for example, from external web APIs, WebSockets, or custom configuration files), schema enforcement shifts entirely to the script environment:

  • Python Scripts: Developers typically bypass libobs parsing initially, relying instead on Python's built-in json module alongside libraries like jsonschema to validate payloads against a formal schema. Once validated, values are passed into OBS APIs or converted to obs_data_t using obs_data_create_from_json().
  • Lua Scripts: Lua lacks a built-in JSON parser or schema validator. Scripts must either rely on third-party pure-Lua modules (such as dkjson or cjson) or pass the raw JSON string directly to obs.obs_data_create_from_json(). In the latter case, structural validation is manual: the script inspects keys and types programmatically using obs_data_has_user_value() and type-checking getters.

Argument Passing in Callbacks and Hotkeys

When custom JSON-derived arguments pass into event handlers, timers, or hotkey callbacks, OBS avoids re-parsing strings. The parsed obs_data_t structure maintains a reference count. When passed through script bindings:

  • obs_data_addref() increments the reference counter to preserve memory across asynchronous execution boundaries.
  • The scripting engine passes the raw memory address wrapped in a language-specific table or class proxy.
  • When the script finishes processing the data, it must explicitly call obs_data_release() (in Lua and C-style APIs) to decrement the counter and prevent memory leaks.
