How OBS Syncs Sources with Mismatched Frame Rates

This article explores how OBS Studio synchronizes video sources running at varying refresh rates within its core rendering pipeline. It details the interaction between OBS Studio's master rendering clock, asynchronous capture threads, GPU texture buffering, and timestamp-based sampling. By decoupling source capture from canvas compositing, OBS Studio seamlessly resolves mismatched framerates by dropping or duplicating frames on demand, ensuring a smooth, unified output stream without pipeline stalls or audio desynchronization.

The Master Render Clock

OBS Studio relies on a central render loop driven by a master clock defined in the user settings (such as 60 FPS or 59.94 FPS). Rather than synchronizing to any incoming video hardware or software feed, the core graphics thread operates on a fixed tick interval—for example, exactly 16.667 milliseconds for a standard 60 FPS canvas.

Every cycle, the render thread executes the compositing pipeline: it clears the canvas, traverses the active scene hierarchy, requests the latest visual data from each source, renders them onto the final surface using the native graphics API (Direct3D 11 on Windows, Metal on macOS, or OpenGL on Linux), and hands the composited frame over to the video encoder.

Decoupled Capture Threads and Shared Surfaces

Video sources in OBS Studio do not render directly onto the canvas. Instead, sources operate on independent, asynchronous threads tailored to their specific capture mechanisms:

  • Hardware capture cards and webcams push frames based on the device’s internal hardware clock (e.g., 30 Hz or 59.94 Hz).
  • Game Capture and Window Capture inject hooks or use OS-level APIs (such as DirectX Graphics Infrastructure or Windows Graphics Capture) that fire whenever the target application presents a frame, which could be 144 Hz, 240 Hz, or variable via G-Sync/FreeSync.
  • Media files and network streams decode frames according to container timebases.

When a source captures a new video frame, it processes the raw data, updates its internal state, and uploads the texture to VRAM (or updates a pointer to a shared DirectX/Metal surface). This capture process happens completely independently of the master render loop.

Timestamp-Based Sampling (Tick and Render)

Synchronization occurs through a pull-based sampling model rather than an event-driven push model. When the master render loop begins its tick, it calculates the current presentation timestamp using a high-precision monotonic clock (os_gettime_ns).

Each source implementation exposes two primary video callbacks to the core engine:

  1. video_tick: Updates the logical state of the source based on elapsed time, recalculating animations, transitions, or media playback positions.
  2. video_render: Binds the active texture and draws the source geometry to the canvas.

When video_render is called, the source simply provides the most recent texture that corresponds to the current tick's timestamp. OBS Studio does not force the source thread and the rendering thread to wait for one another. Instead, thread-safe memory exchange is managed using double- or triple-buffering techniques, allowing the render loop to sample the latest completed frame without blocking the capture thread.

Handling Framerate Discrepancies

Because the canvas composition operates independently of source capture intervals, mismatched refresh rates naturally resolve into frame dropping or frame duplication:

Sources Faster Than the Canvas (e.g., 144 FPS Game onto a 60 FPS Canvas)

When a source generates frames faster than the master clock, multiple frames may arrive between consecutive render ticks. The source continually updates its internal buffer pointer to the newest frame. When the master render thread executes its tick, it draws the latest available frame and ignores the intermediate ones. This effectively drops redundant frames without causing buffer bloat, micro-stutter, or rendering delays.

Sources Slower Than the Canvas (e.g., 30 FPS Camera onto a 60 FPS Canvas)

When a source produces frames slower than the master render clock, the render thread will tick before a new frame has been delivered to that source's texture buffer. In this scenario, the source presents the existing texture from the previous frame. This results in frame duplication, ensuring the canvas maintains its target frame rate while the slower source plays back at its native cadence.

Fractional and Variable Framerates (e.g., 59.94 Hz, VFR, or G-Sync)

Fractional differences often lead to phase drift between the source capture cadence and the render loop cadence. OBS Studio handles this without frame tear or pipeline stalling: it always pulls whichever completed frame is ready at the exact moment of rendering. If drift accumulates to the equivalent of an entire frame interval, OBS will naturally sample a frame twice or skip one frame seamlessly to maintain overall timing integrity.

Audio Synchronization Alignment

While the video pipeline resolves mismatched refresh rates by sampling the most recent texture buffer, audio cannot be dropped or duplicated frame-by-frame without introducing audible pops, clicks, or pitch shifts.

To preserve synchronization between out-of-sync video and continuous audio streams, OBS Studio timestamps every incoming audio packet with the same monotonic system clock used by the video pipeline. Audio frames are routed through an internal buffer where they are mixed and resampled to match the global audio sample rate (typically 48 kHz). OBS then dynamically aligns the audio timestamps with the video frame timestamps during the multiplexing stage before sending the interleaved stream to the encoder.
