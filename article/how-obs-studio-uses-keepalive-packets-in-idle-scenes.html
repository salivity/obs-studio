How OBS Studio Uses Keepalive Packets in Idle Scenes

During visually static or idle scenes, video encoders drastically reduce data output, which can cause streaming servers and network hardware to misinterpret the lack of traffic as a broken connection. OBS Studio prevents stream dropouts during these periods by combining protocol-level keepalive pings, encoder-level bitrate stuffing, and continuous frame generation. This article explains the technical mechanics OBS Studio and its underlying network libraries use to maintain socket persistence and keep the stream active when bandwidth usage drops to near-zero levels.

The Low-Bandwidth Disconnect Problem

Modern video encoders (such as x264, NVENC, and QuickSync) rely heavily on inter-frame compression. In an idle scene—such as a static "Starting Soon" screen or a paused game—consecutive video frames contain almost identical information. Because the encoder only transmits the differences between frames (P-frames and B-frames), the required transmission bitrate can drop precipitously.

If bandwidth drops too low for too long, intermediate network components (such as NAT routers and stateful firewalls) or the ingest server itself may trigger an inactivity timeout, terminating the TCP or UDP connection.

Protocol-Level Keepalive Negotiation

OBS Studio does not handle low-level networking directly; it relies on transport protocols implemented via libraries like FFmpeg, librtmp, and libp2p/SRT. These protocols maintain keepalive mechanisms independently of video payload size.

  • RTMP (Real-Time Messaging Protocol): When streaming via RTMP, OBS utilizes standard RTMP chunking and User Control Messages. If the media pipeline produces negligible data, the protocol employs Ping Request (Type 4, Event 6) and Ping Response (Type 4, Event 7) control packets. The client or server transmits an event containing a timestamp; the receiving end must return the exact timestamp. This bidirectional heartbeat informs the ingest server that the client is still responsive, resetting connection timeout counters even in the complete absence of video payload.
  • SRT (Secure Reliable Transport): For users streaming over SRT, the protocol inherently features a bidirectional control channel. SRT transmits periodic keepalive control packets (UMSG_KEEPALIVE) across the UDP link, typically at negotiated intervals (often once per second). If video data drops off, these tiny control packets ensure the socket stays open and calculate Round Trip Time (RTT).

Socket-Level TCP Keepalive Implementation

Beneath RTMP, the operating system's TCP stack operates with socket-level keepalives. When OBS opens an RTMP socket:

  1. It enables the SO_KEEPALIVE socket option via its underlying network abstraction layer.
  2. The operating system monitors the connection for silence.
  3. If no acknowledgments or data packets cross the wire within the idle timeout threshold, the system sends an empty ACK packet with the sequence number set to one less than the current sequence number.
  4. The server replies with its current ACK, resetting the firewall and NAT connection expiration timers.

Encoder-Level Filler Data (CBR Enforcement)

While network keepalives maintain the connection pipeline, streaming platforms often require a consistent media pipeline to prevent ingest pipeline buffers from emptying. OBS Studio counters this by enforcing Constant Bitrate (CBR) by default.

When CBR is enabled, the encoder cannot simply omit data during an idle scene:

  • If a frame's compressed size is smaller than the target rate dictated by the bitrate and frame rate, the encoder injects Filler NAL units (Network Abstraction Layer units) directly into the video stream (specifically NAL_UNIT_TYPE_FILLER_DATA).
  • This filler data consists of empty payload bytes that pad the video stream to the required bitrate floor.
  • As a result, the network layer continues transmitting packets at a constant pace, preventing the physical link, local network hardware, or platform media demuxers from detecting an idle state.

Continuous Frame Generation

OBS Studio runs a rendering loop synchronized to a strict frame clock (e.g., 60 fps). Even if the on-screen image does not change, OBS does not halt frame generation. It continuously renders the compositor output, passes identical frames to the video encoder, and pushes timestamps to the output muxer. This ensures a persistent stream of timestamps and packet headers flows through the network buffer, making true zero-byte transmission impossible under standard operating conditions.
