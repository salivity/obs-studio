OBS File Handle Permissions on SMB Network Drives

Saving OBS Studio recordings directly to Server Message Block (SMB) network drives introduces distinct file handle behaviors and permission constraints compared to local storage. This article details the primary differences in file handle management, user access tokens, file locking mechanisms, and permission inheritance when OBS writes video data across a network share versus a local disk.

Local vs. SMB File Handle Allocation

When OBS Studio writes to a local drive, it requests a file handle directly from the Windows NT kernel via the Win32 API (CreateFileW). This local handle operates with direct access to the local file system (NTFS, exFAT), allowing immediate, low-latency write buffering and status updates.

When recording to a mapped SMB drive, the file handle request must pass through the Windows Network Redirector (rdbss.sys and mrxsmb.sys). The handle generated is a remote file handle, subject to network latency, transport reliability (TCP/IP), and remote operating system translation. If the SMB connection experiences a micro-disconnection, the remote handle is invalidated (ERROR_NETNAME_DELETED or ERROR_INVALID_HANDLE). Unlike local handles that survive standard process throttling, an invalidated SMB handle causes OBS to fail write calls instantly, often halting the recording or corrupting the output container.

User Token Separation and Elevated Handles

A frequent conflict occurs when running OBS Studio with administrative privileges ("Run as Administrator"). Windows isolates mapped network drives (Z:\) to the specific logon session and security context that created them.

  • Local Storage: An elevated OBS process inherits elevated permissions, granting it broader access to write anywhere on local drives.
  • Mapped SMB Drives: An elevated OBS process cannot see or access mapped network drives created by a non-elevated user token. The file handle request will fail with a "path not found" or "access denied" error unless the registry value EnableLinkedConnections is enabled, or the storage is targeted using explicit UNC paths (\\server\share\recordings) rather than drive letters.

Share Permissions vs. File System ACLs

Local recording handles only evaluate local file system permissions (NTFS Access Control Lists). SMB recording handles require a dual-layer evaluation:

  1. Share-Level Permissions: Determine what rights are granted across the network transport (e.g., Read, Change, Full Control).
  2. NTFS/Underlying ACLs: Determine the physical storage permissions on the host server.

OBS requires continuous stream creation, metadata modification, and data appending. For the SMB file handle to function properly, the effective permission must be the most restrictive intersection of both layers. If an SMB share grants "Change" permissions, but the remote storage account lacks "Modify" on the NTFS level, OBS can create the initial file handle but will fail when attempting to alter file size attributes or finalize container headers.

File Locking, Caching, and Oplocks

OBS requires uninterrupted write handles, especially for single-pass container formats like standard MP4.

  • Local Write Caching: Managed seamlessly by the Windows Cache Manager.
  • SMB Opportunistic Locks (Oplocks): SMB uses opportunistic locking and client-side caching leases to negotiate performance. If the SMB server revokes an oplock—often caused by another process (like a media scanner, backup utility, or another user) accessing the growing file—OBS must immediately flush its buffers and acknowledge the break. If the network or remote host delays this exchange, the write handle blocks, resulting in dropped frames in the recording or an outright I/O freeze.

Mitigating SMB File Handle Failures in OBS

To avoid file handle termination and data loss when recording over SMB:

  • Use Universal Naming Convention (UNC) Paths: Direct OBS output to \\ServerName\ShareName\Path instead of relying on mapped drive letters to bypass token isolation issues.
  • Use Resilient Formats: Record using MKV or Fragmented MP4 (fMP4). If an SMB file handle drops, fragmented formats preserve all data written up to the point of disconnection. Standard MP4 leaves the file unreadable because the moov atom header cannot be finalized over a dead handle.
  • Grant Explicit Modify Rights: Ensure the authenticating network credentials possess both "Change" at the share level and "Modify" at the file system level to ensure attribute-modification handles execute without rejection.
