How OBS Studio Logs Scene Transition Timestamps

This article explains how OBS Studio tracks and records the activation and deactivation timestamps of scene transitions within its logging system for broadcast auditing and compliance purposes. It covers the structure of native session logs, the level of precision recorded during scene transitions, and the methods broadcast engineers use—including native files, the OBS WebSocket API, and custom scripting—to generate auditable records of on-air visual changes.

Native OBS Studio Logging Architecture

OBS Studio generates a new text log file automatically every time the application launches. These files are stored locally in the application's user directory:

  • Windows: %appdata%\obs-studio\logs
  • macOS: ~/Library/Application Support/obs-studio/logs
  • Linux: ~/.config/obs-studio/logs

Each log entry begins with a high-resolution local clock timestamp formatted as HH:MM:SS.mmm (hours, minutes, seconds, and milliseconds). This provides a chronological baseline for all internal engine events, source activations, and hardware performance metrics.

How Scene Switches and Transitions Are Logged

When an operator or automation system switches scenes, the native OBS rendering engine executes a transition (such as Cut, Fade, or Stinger). In standard logs, OBS tracks this activity through specific source state messages:

  1. Activation: When a new scene is called to Program, OBS logs the switch event with an entry such as Switched to scene 'Scene Name'.
  2. Transition Execution: The transition itself is an internal source. When initiated, OBS loads the transition parameters (e.g., duration in milliseconds) and begins rendering the incoming scene while keeping the outgoing scene active in memory.
  3. Deactivation: As the transition finishes, the previous scene's non-shared sources have their render passes deactivated, which is captured in deep logging as source visibility and destruction calls.

While standard logs record the exact millisecond a scene switch is initiated, they primarily treat scenes as container sources rather than outputting explicit TransitionStarted and TransitionEnded text lines by default.

Limitations of Default Logs for Broadcast Auditing

For standard legal compliance, commercial insertion verification, or proof-of-performance auditing, native text logs have specific limitations:

  • Lack of SMPTE Timecode: Default logs record wall-clock time rather than linear SMPTE timecode (LTC) or embedded SDI/NDI frame data.
  • Unstructured Format: Native logs are unstructured text files designed for troubleshooting crashes and performance drops rather than automated database ingestion.
  • Granularity: In high-speed cut transitions or complex stinger animations, standard logs may omit the exact frame where the outgoing scene reaches 0% opacity.

Broadcast-Grade Auditing Solutions

To achieve verifiable, frame-accurate auditing of scene transitions, broadcast environments enhance OBS Studio using built-in programmatic interfaces:

1. OBS WebSocket API

OBS Studio includes native WebSocket support (obs-websocket). Automation software can listen to real-time events that provide definitive transition telemetry:

  • SceneTransitionStarted: Emitted the precise moment a transition begins, containing the transition name, duration, and originating scene.
  • SceneTransitionVideoEnded: Emitted when the video switchover has fully completed.
  • CurrentProgramSceneChanged: Emitted when the new scene is officially designated as live on the program output.

Logging systems subscribe to these events over a local network socket and serialize them directly into time-stamped JSON or SQL databases for audit verification.

2. Python and Lua Audit Scripts

Engineers utilize OBS Studio’s internal scripting engine (accessible via Tools > Scripts) to create custom audit trails. A lightweight Lua or Python script hooks into the obs_frontend_add_event_callback function. Whenever the OBS_FRONTEND_EVENT_SCENE_CHANGED or transition events trigger, the script writes a dedicated CSV file containing:

  • The exact date and UTC timestamp.
  • The outgoing (deactivated) scene name.
  • The incoming (activated) scene name.
  • The transition style and duration.
  • The current streaming or recording uptime.

This creates an isolated, tamper-evident log specifically tailored to the reporting formats required by broadcast compliance bodies and advertising partners.
