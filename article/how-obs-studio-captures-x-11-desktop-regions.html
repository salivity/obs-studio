How OBS Studio Captures X11 Desktop Regions

This article examines how OBS Studio interacts with the X11 composite manager to capture desktop regions on Linux systems. When desktop composition is active, window rendering is redirected to off-screen buffers before being drawn to the screen, fundamentally altering how desktop images are exposed. OBS Studio navigates this environment by interfacing with core X11 extensions—primarily XComposite, MIT-SHM, and the Composite Overlay Window—to acquire, read, and process display pixels reliably without causing visual tearing or interface corruption.

The Role of the X11 Composite Manager

In a traditional, uncomposited X11 environment, all client applications draw directly to the shared front buffer (the root window). Overlapping windows clip each other, and capturing a desktop region requires reading directly from the root window's framebuffer.

When a composite manager (such as Picom, Mutter, or KWin) is active, it claims ownership of screen redirection using the XComposite extension. The X server redirects every top-level window's drawing calls into individual off-screen pixmaps stored in video memory (VRAM). The composite manager then reads these independent pixmaps, applies visual effects (like shadows, transparency, and transformations), and draws the final composed desktop onto either the root window or a specialized hardware-level surface called the Composite Overlay Window (COW).

How OBS Studio Accesses the Composed Scene

When you configure OBS Studio to capture a desktop display or a specific region on an X11 desktop, it primarily relies on the XSHM (MIT Shared Memory Extension) capture plugin (linux-capture). The interaction unfolds through specific mechanisms:

  1. Targeting the Framebuffer: Because the composite manager draws the unified desktop image onto the root window or the Composite Overlay Window, OBS Studio targets this top-level drawable to capture multiple overlapping windows simultaneously.
  2. Buffer Allocation with MIT-SHM: Rather than transferring large chunks of pixel data across the standard X11 network socket protocol—which would cause heavy CPU and I/O bottlenecks—OBS Studio allocates a shared memory segment accessible by both the X server and the OBS process using the XShmCreateImage API.
  3. Reading the Region: To capture a designated bounding box, OBS issues XShmGetImage. The X server copies the requested rectangular pixel coordinates from the composite manager’s composed target buffer directly into the shared memory segment.
  4. Uploading to the GPU Canvas: Once the raw pixels reside in system memory, OBS Studio uploads the frame to its rendering subsystem (typically using OpenGL via GLX or EGL) to be scaled, composited into the OBS canvas, and encoded.

Window-Specific Capture vs. Region Capture

While desktop region capture relies on reading back the composited root surface, capturing an individual, isolated window involves a different interaction with the composite manager.

Through the XComposite extension, OBS Studio can query the X server directly for the named window’s off-screen pixmap (XCompositeNameWindowPixmap). By using the glXBindTexImageEXT extension, OBS can bind that off-screen pixmap directly as an OpenGL texture. This bypasses the composite manager's rendering pass entirely, enabling zero-copy, hardware-accelerated capture of an isolated application window, even if it is occluded or minimized.

For continuous desktop regions spanning multiple windows, however, OBS cannot simply bind a single application pixmap. It must read the composite manager's final output from the root or overlay plane.

Performance and Synchronization Implications

The presence of a composite manager introduces distinct trade-offs during desktop region capture:

  • Tear-Free Capture: Because modern composite managers synchronize their redraws with the vertical refresh rate (V-Sync) using double or triple buffering, capturing the composed desktop prevents the screen tearing that often plagues uncomposited X11 captures.
  • VRAM-to-RAM Bottlenecks: When OBS calls XShmGetImage to capture a desktop region, the graphics hardware must copy the composited image from GPU memory back to system RAM. For high-resolution displays (such as 1440p or 4K) running at 60 FPS, this round-trip transfer creates measurable PCI-e bandwidth usage and CPU overhead.
  • Compositor Pausing (Unredirect): Fullscreen applications often trigger an "unredirect fullscreen" optimization in composite managers to reduce latency during gaming. When this happens, the compositor stops handling the display, returning raw control of the screen to the fullscreen application. OBS must handle this state transition dynamically to prevent the capture from freezing or rendering black frames while reading the root surface.
