How OBS Handles Ethernet to Wi-Fi Disconnection

When an active Ethernet cable is disconnected during a live broadcast, OBS Studio cannot perform a seamless, hitless network handoff to Wi-Fi due to the fundamental constraints of standard streaming protocols. Instead, the sudden disconnection invalidates the active socket, prompting the operating system to reroute traffic through the wireless adapter, which in turn forces OBS Studio to drop the current connection and initiate an automated reconnection sequence over the new network path.

The Underlying Network Constraint

OBS Studio primarily streams using protocols built on top of TCP (such as RTMP) or UDP (such as SRT). Every active network connection is defined by a socket pairing: a source IP address and port, and a destination IP address and port.

When your computer is connected via Ethernet, it has an IP address assigned specifically to that physical Network Interface Card (NIC). The Wi-Fi adapter has its own distinct MAC address and receives a different local IP address. When the Ethernet cable is unplugged:

  1. The Ethernet NIC reports a "carrier lost" or link-down state to the operating system.
  2. The operating system immediately tears down the local IP configuration associated with the Ethernet interface.
  3. The active TCP/UDP socket bound to the Ethernet IP is broken.

Because standard RTMP does not support multi-path transmission or dynamic IP migration, the stream cannot instantly "glide" from one IP to another without breaking the transport layer session.

The Operating System Routing Shift

Once the physical disconnection occurs, the operating system's routing table changes:

  • Route Metric Adjustment: The operating system assigns metrics (priorities) to network adapters. Ethernet usually has a lower metric (higher priority) than Wi-Fi. With Ethernet unavailable, the operating system promotes the Wi-Fi adapter's default gateway as the primary route for all outbound internet traffic.
  • Socket Invalidation: Any attempt by OBS to continue sending packets via the old socket results in a network error (such as WSAECONNABORTED, WSAENETUNREACHED, or ECONNRESET), terminating the transmission pipeline.

How OBS Responds

How OBS Studio behaves during this transition depends largely on your network configuration settings within the software.

1. Network Binding Settings

Located in Settings > Advanced > Network > Bind to IP:

  • Default (Recommended for Failover): OBS binds its sockets to 0.0.0.0 (INADDR_ANY), allowing the operating system to determine which interface routes the traffic. When the cable is pulled and OBS drops the stream, the subsequent reconnection attempt will naturally route through the newly active Wi-Fi adapter.
  • Specific IP/Interface Selection: If you manually set OBS to bind exclusively to the Ethernet adapter’s IP address, OBS will refuse to use Wi-Fi. The stream will terminate and fail to reconnect until the Ethernet cable is reconnected.

2. The Auto-Reconnect Engine

When the connection drops, OBS relies on its internal reconnection logic:

  • OBS enters a "Reconnecting" state (configured under Settings > Advanced > Network > Automatically Reconnect).
  • It waits for the specified retry delay (default is typically 2 to 10 seconds).
  • Once the timer elapses, OBS initializes a completely new socket connection. Assuming "Bind to IP" is set to Default, the operating system routes this new request through the Wi-Fi adapter.
  • OBS performs a fresh handshake with the ingest server (e.g., Twitch, YouTube, or Kick), authenticates the stream key, and resumes broadcasting.

Viewer Impact and Mitigation

From the viewer's perspective, this handoff is not invisible. The broadcast will freeze or show a buffering wheel for several seconds while the socket fails, the OS updates its routing table, and OBS completes the re-handshake and sends a fresh keyframe (I-frame).

To achieve a truly seamless transition without stream interruption, standard OBS cannot rely on basic OS switching alone. It requires packet-level bonding solutions—such as hardware bonding encoders, specialized dual-WAN routers, or software aggregation tools—which present a single, virtual network adapter to OBS while managing data distribution across Ethernet and Wi-Fi simultaneously in the background.
