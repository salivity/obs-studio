How OBS Studio Logs VRAM Texture Allocation Errors

When OBS Studio attempts to allocate oversized render textures on systems with insufficient video memory (VRAM), it records detailed failure events to its application log files via its core graphics abstraction layer (libobs/graphics). This article explains the exact log signatures, API-level error codes, and cascading failure events generated by OBS Studio during low-VRAM conditions, detailing how the software handles and reports out-of-memory states across Direct3D 11 and OpenGL backends.

The Graphics Abstraction Layer and Logging Mechanism

OBS Studio handles rendering operations through an internal graphics abstraction layer that interfaces with underlying graphics APIs (primarily Direct3D 11 on Windows and OpenGL on Linux). When a scene, source, or canvas requires a render target that exceeds available VRAM or driver-imposed dimension limits, the initialization function (gs_texture_create or gs_texture_create_render_target) fails.

OBS captures these failures using its internal logging macro (blog(LOG_ERROR, ...)), tagging the failure directly to the active graphics subsystem.

Direct3D 11 Failure Signatures

On Windows, where OBS Studio defaults to Direct3D 11, texture creation calls interface with ID3D11Device::CreateTexture2D. When this call fails due to low VRAM or excessive texture dimensions, OBS outputs explicit error codes in the application log:

[D3D11] device_texture_create (D3D11): Failed to create 2D texture (<HRESULT>)

The <HRESULT> returned by DirectX identifies the root cause:

  • 0x8007000E (E_OUTOFMEMORY): Indicates the system or GPU could not reserve the contiguous block of memory required for the specified width, height, and color format.
  • 0x887A0003 (DXGI_ERROR_UNSUPPORTED): Occurs if the requested texture dimensions exceed the hardware feature level's maximum texture size limit (e.g., exceeding 16,384 pixels on modern hardware).

Following this initial failure, OBS Studio typically logs an allocation failure within its rendering pipeline:

gs_texture_create failed
Failed to create render target for source

Cascading Device Removal Warnings

Low-VRAM conditions often cause Windows Display Driver Model (WDDM) timeouts (TDR) if the driver stalls while attempting to swap or allocate memory. When this occurs, the DirectX device collapses, leading to secondary entries in the OBS log:

device_present (D3D11): Present failed (0x887A0005)
Device removed, reason: 0x887A0006
  • 0x887A0005 (DXGI_ERROR_DEVICE_REMOVED): The GPU has been physically removed, turned off, or a driver reset occurred.
  • 0x887A0006 (DXGI_ERROR_DEVICE_RESET): The driver failed to process commands in the allotted time and was reinitialized by the OS.

When these messages appear immediately after a texture creation failure, it confirms that the oversized texture request overwhelmed the GPU scheduler and triggered driver recovery.

OpenGL Failure Logs

On platforms utilizing OpenGL, OBS interfaces with glTexImage2D or glTexStorage2D. When an oversized texture fails to allocate, OpenGL logs reflect API-level validation:

device_texture_create (GL): Failed to create 2D texture: GL_OUT_OF_MEMORY

Unlike Direct3D, OpenGL may also raise a generic invalid operation or value warning if dimensions exceed GL_MAX_TEXTURE_SIZE:

device_texture_create (GL): Texture dimensions exceed maximum supported size

Locating and Diagnosing the Errors

OBS writes these entries chronologically into the current session log, stored locally:

  • Windows: %APPDATA%\obs-studio\logs
  • Linux: ~/.config/obs-studio/logs
  • macOS: ~/Library/Application Support/obs-studio/logs

To identify oversized render texture issues, search the log file for device_texture_create, E_OUTOFMEMORY, or DXGI_ERROR_DEVICE_REMOVED. Correlating these entries with the base canvas resolution, scaled output resolution, or specific custom filter sizes listed near the top of the log reveals which asset or canvas dimension caused the allocation failure.
