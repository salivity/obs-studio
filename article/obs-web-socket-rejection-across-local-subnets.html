OBS WebSocket Rejection Across Local Subnets

Connecting to OBS Studio's built-in WebSocket server from an external subnet often results in immediate connection rejections, timeouts, or refused handshakes. This article explores the root causes of cross-subnet connection failures with OBS WebSocket—including OS-level firewall restrictions, interface binding limitations, inter-VLAN routing controls, and network address translation issues—and explains how to resolve them to ensure reliable remote control.

Default Host Firewall Scope Restrictions

The most common cause of cross-subnet connection failure is the host operating system's firewall. When you allow OBS Studio through the Windows Defender Firewall or a Linux firewall (such as ufw or iptables), the rule often defaults to permitting incoming traffic solely from the local subnet.

When a packet arrives from an IP address outside the host's immediate IP range (for example, from a 192.168.20.x management VLAN to a 192.168.10.x production workstation), the host firewall treats the request as a potential threat and silently drops or explicitly rejects the TCP connection on port 4455.

  • The Fix: Modify the inbound firewall rule for OBS Studio or port 4455. In Windows Defender Firewall with Advanced Security, locate the rule, open Properties > Scope, and ensure the Remote IP address setting is set to Any IP address or explicitly includes the remote subnet range.

Incorrect IP Interface Binding

OBS WebSocket must listen on an interface accessible to the rest of the network. If the server is bound specifically to 127.0.0.1 (loopback), it will reject any connection attempt originating from outside the host machine itself, including traffic from other subnets.

While modern OBS Studio WebSocket (v5.x+) binds to 0.0.0.0 (all IPv4 interfaces) by default, customized configurations, third-party plugins, or multi-homed network adapters can bind the service to a single network interface that cannot route between your specific subnets.

  • The Fix: Ensure OBS is bound to listen on all interfaces (0.0.0.0 for IPv4 or :: for IPv6). Check whether multiple network cards (such as a dedicated Dante or NDI interface) are confusing the default routing table of the host machine.

Inter-VLAN Routing and Network Access Control Lists (ACLs)

In segmented networks featuring multiple VLANs or subnets, routers and layer-3 switches enforce access control lists (ACLs) and stateful firewall rules between segments.

If the router separating the client subnet from the OBS subnet does not explicitly permit TCP traffic on the OBS WebSocket port (default: 4455), the router will either drop the packets or send back a TCP RST (reset) packet.

  • The Fix: Verify your router or firewall rules between the subnets. Create a permissive rule that allows traffic from the client subnet/IP to the OBS host IP on TCP port 4455. Confirm that reverse traffic (established/related connections) is allowed back through the firewall.

Asymmetric Routing and NAT Issues

If your network employs multiple gateways or complex routing paths, traffic sent to the OBS host might arrive successfully, but the OBS machine might route the return packets through a different default gateway. Asymmetric routing often causes stateful firewalls to drop return packets because the connection state was never recorded on the alternate return path.

Similarly, if Destination NAT (DNAT) or Source NAT (SNAT) is incorrectly applied across local boundaries, the source or destination IP headers may not match what the TCP stack expects during the initial three-way handshake, resulting in a dropped connection.

  • The Fix: Trace the route from both ends using tools like traceroute or tracert to ensure that packets travel along a symmetrical path. Avoid applying NAT between trusted internal subnets.

Hostname and mDNS Resolution Failures

Many remote control applications (such as custom Stream Deck integrations, companion apps, or web interfaces) attempt to connect to OBS using local hostnames (e.g., obs-pc.local). Multicast DNS (mDNS) packets do not cross subnet boundaries by default without an mDNS reflector or repeater (such as Avahi).

If the client application cannot resolve the .local address across the subnet, the connection fails before a WebSocket handshake can even begin.

  • The Fix: Connect using the static IPv4 address of the OBS Studio workstation rather than a local hostname, or configure an mDNS gateway/proxy on your network router to propagate discovery packets between subnets.
