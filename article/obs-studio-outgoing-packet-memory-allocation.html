OBS Studio Outgoing Packet Memory Allocation

This article provides an overview of the internal memory allocation and staging mechanisms used by OBS Studio to process outgoing network packets before serialization. OBS Studio relies on a combination of custom heap wrappers, an interleaved FIFO packet staging queue, and reference-managed structures (encoder_packet) to handle video and audio data safely across thread boundaries. Understanding this pipeline reveals how OBS balances real-time broadcast latency against memory consumption and network congestion.

The Memory Abstraction Layer: bmem

At the foundational level, OBS Studio wraps platform-specific memory allocators using its internal memory management utility located in libobs/util/bmem.c. The primitives—bmalloc, brealloc, bfree, and bmemdup—manage raw allocations for packet buffers. While these typically map directly to standard system allocators (malloc/free) or platform-specific implementations, they provide unified alignment and crash-on-failure safety semantics across all supported operating systems.

Encapsulation via struct encoder_packet

When an encoder (such as x264, NVENC, or Apple VT) finishes compressing a video frame or audio chunk, it outputs raw encoded bitstream data. This payload is wrapped inside a struct encoder_packet.

The packet structure stores critical stream metadata, including:

  • A direct pointer to the heap-allocated payload buffer (uint8_t *data).
  • The allocation size (size_t size).
  • Timing information, such as Presentation Timestamp (PTS) and Decode Timestamp (DTS).
  • Packet classification, including packet type (audio or video) and frame priority (keyframe, P-frame, or B-frame).

The packet data buffer is allocated dynamically via bmalloc to hold the exact size of the compressed NAL units or audio frames.

Packet Staging and the Interleaved Output Queue

Before packets can be serialized to a specific protocol—such as RTMP, SRT, or WebRTC—they must be synchronized and scheduled. This occurs within the output module pipeline (for example, plugins/obs-outputs/rtmp-stream.c).

OBS Studio implements a dedicated network dispatch thread (send_thread) fed by an interleaved FIFO queue. Memory allocation within this staging queue operates as follows:

  1. Queue Enqueueing: The video and audio encoding threads push completed encoder_packet instances into a shared queue protected by a mutex.
  2. Buffer Duplication: If a packet needs to be staged or delayed across execution contexts, OBS duplicates packet ownership using obs_encoder_packet_ref or by creating a deep copy of the raw payload using bmemdup.
  3. Queue Sizing: The queue does not preallocate fixed slabs; instead, it dynamically tracks the aggregate byte size and duration of buffered packets on the heap.

Congestion Control and Buffer Eviction

To prevent unbounded memory growth during network degradation, the staging queue enforces thresholds based on time and memory usage:

  • Drop Thresholds: If the network socket blocks and the staging queue exceeds user-defined or internal limits, OBS Studio triggers frame-dropping logic.
  • Selective Eviction: The queue inspects the buffered encoder_packet structures and purges disposable packets (such as B-frames or non-reference P-frames) first.
  • Immediate Deallocation: Discarded packets are freed immediately by calling obs_encoder_packet_release, returning the associated payload memory to the system allocator via bfree.

Serialization and Deallocation

Once the dispatch thread dequeues an encoder_packet, the payload is handed over to the network serializer (such as librtmp or an SRT transmission socket). The data buffer is serialized directly into network transport buffers. Immediately following successful transmission or socket handoff, the staging pipeline invokes obs_encoder_packet_release, reclaiming the allocated heap memory and completing the lifecycle of the packet.
