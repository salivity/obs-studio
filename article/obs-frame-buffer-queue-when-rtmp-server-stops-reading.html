OBS Frame Buffer Queue When RTMP Server Stops Reading

When an RTMP ingest server stops reading incoming TCP packets, a cascade of network backpressure occurs that directly impacts OBS Studio. Because TCP guarantees reliable, in-order delivery, unread data causes system network buffers to fill, which subsequently forces OBS Studio's internal output buffer queue to saturate. This article breaks down the step-by-step technical process of what happens inside OBS Studio, from TCP window exhaustion and internal queue accumulation to network frame drops and eventual stream disconnection.

1. TCP Flow Control and Backpressure

The process begins at the transport layer:

  • TCP Receive Buffer Saturation: As the RTMP server application stops reading from its local socket, its operating system's TCP receive buffer fills to capacity.
  • Zero Window State: In response, the server's TCP stack sends TCP ACK packets with a Receive Window (Win) size of zero to the streaming machine, signaling that it can no longer accept new data.
  • Client Send Buffer Saturation: The operating system running OBS Studio respects the Zero Window update and ceases network transmission, causing the local OS-level TCP send socket buffer (SO_SNDBUF) to rapidly fill with outgoing RTMP data.
  • Socket Non-Writable: Once the local socket buffer is completely full, non-blocking write operations on the RTMP socket fail, returning EWOULDBLOCK or EAGAIN.

2. OBS Internal Queue Accumulation

OBS Studio decouples video and audio encoding from network transmission. The encoder continues to produce encoded video and audio frames at the configured framerate and bitrate, pushing them to the RTMP output module (rtmp-stream).

Under normal operation, a dedicated network output thread continuously pulls frames from this internal queue and writes them to the socket. When the socket becomes non-writable due to TCP backpressure:

  • The send thread cannot dispatch packets to the operating system.
  • The internal packet queue begins buffering all newly encoded audio and video packets in memory.
  • If enabled, dynamic bitrate algorithms will attempt to drop the encoder bitrate to zero, but without the ability to flush bytes to the wire, data continues to pile up.

3. Buffer Saturation and "Dropped Frames (Network)"

OBS Studio imposes limits on its internal packet buffer to prevent unbounded RAM consumption:

  • Buffer Thresholds: OBS monitors the age and quantity of un-transmitted packets waiting in the queue.
  • Packet Discarding: Once the internal queue reaches its memory limit or transmission latency threshold, OBS Studio begins discarding frames directly from the queue. Video packets (especially B-frames and P-frames) are discarded first to maintain audio synchronization.
  • UI Status Indication: In the OBS Studio interface, discarded packets are registered as "Dropped Frames (Network)". The bitrate indicator in the bottom status bar drops to 0 kb/s, and the status square changes from green to red.

4. Connection Timeout and Disconnection

If the RTMP server continues to reject or ignore incoming TCP traffic, the stream will terminate:

  • TCP Keep-Alive / Retransmission Failure: The client OS sends TCP Keep-Alive or Zero Window Probe packets. If these go unacknowledged, or if the connection remains completely stalled, standard TCP retransmission timeouts occur.
  • RTMP Write Timeout: OBS Studio's output implementation tracks write attempts. When writes block beyond a defined socket timeout period (typically between 10 to 30 seconds), OBS flags the connection as dead.
  • Socket Destruction: OBS closes the socket, flushes the remaining unsent buffer queue to free system memory, and triggers a disconnect event. If the "Automatic Reconnect" setting is enabled in OBS, it will begin attempting a fresh handshake sequence on a new TCP connection.
