OBS Studio Socket Calls for Graceful Stream Stop

When a user stops a live broadcast in OBS Studio, the application performs an orderly teardown across both the RTMP application protocol layer and the underlying operating system transport layer rather than abruptly dropping the connection. This process ensures that queued media frames are delivered, the media server is formally notified that the stream has finished, and the underlying TCP connection cleanly closes without lingering states or corrupted archives. Below is the exact sequence of socket API calls executed by OBS Studio during a graceful stream termination.

1. Final Payload Flush: send()

Before the socket itself is closed, the OBS streaming thread flushes any remaining buffered audio and video packets. Once the media buffers clear, the RTMP protocol client inside OBS (obs-outputs) constructs and transmits final RTMP control messages to inform the ingestion server (such as YouTube, Twitch, or NGINX-RTMP) that broadcasting has ended:

  • FCUnpublish / deleteStream: Instructs the RTMP server to unbind the active stream ID.
  • closeStream: Informs the server that the stream instance is ending.

These command frames are transmitted using:

  • send() (POSIX) or WSASend() / send() (Windows Winsock)

The return value is checked to guarantee that all bytes representing the protocol teardown are accepted into the kernel’s TCP send buffer.

2. Transport Half-Close: shutdown()

Once the final protocol packets are queued for delivery, OBS Studio signals to the remote peer that it has finished sending data. It does this by closing the write half of the bidirectional TCP socket:

  • POSIX: shutdown(socket_fd, SHUT_WR)
  • Windows (Winsock): shutdown(socket_fd, SD_SEND)

Executing shutdown() with the write-direction flag triggers the operating system's TCP stack to construct and send a TCP FIN packet to the ingestion server. This notifies the remote server that transmission from the client has stopped while still keeping the receive channel open to capture any final acknowledgments (ACK) or server-side responses.

3. Draining Inbound Data: recv()

To prevent an abrupt RST (TCP Reset) packet, which can occur if unread data remains in the receive buffer when a socket is destroyed, OBS enters a brief draining loop to read any final responses from the server:

  • POSIX / Windows: recv(socket_fd, buffer, length, 0)

The recv() function is called repeatedly inside a polling or timed read loop:

  • If recv() returns 0, it indicates that the remote server has received the client's FIN, sent its own FIN, and completed the standard four-way TCP handshake.
  • If recv() returns -1 (or SOCKET_ERROR on Windows) with an error code like EWOULDBLOCK or WSAEWOULDBLOCK, the socket waits via select() or poll() up to a predetermined timeout.

4. Releasing the Socket Handle: close() or closesocket()

Once the remote FIN is confirmed or the drain timeout expires, OBS initiates the final disposal of the socket descriptor to free kernel resources:

  • POSIX (Linux, macOS): close(socket_fd)
  • Windows (Winsock): closesocket(socket_fd)

Calling this final function destroys the local socket handle, decrements system reference counters, and moves the local TCP state into TIME_WAIT (or terminates it if already acknowledged), completing the graceful termination process.
