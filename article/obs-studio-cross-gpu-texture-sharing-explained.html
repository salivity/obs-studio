OBS Studio Cross-GPU Texture Sharing Explained

This article provides an overview of how OBS Studio handles texture sharing across distinct GPU adapter contexts in multi-GPU configurations. Running games, capture hooks, and rendering pipelines on separate physical graphics adapters introduces latency and synchronization barriers. OBS Studio overcomes these barriers on modern Windows systems by leveraging DirectX Graphics Infrastructure (DXGI) shared surfaces, OS-level DMA transfers, and keyed mutex synchronization, while retaining CPU-mediated staging fallbacks when hardware-level zero-copy transfers are unavailable.

The Capture Hook and Adapter Isolation

In a multi-GPU environment—such as a laptop with an integrated GPU (iGPU) and a discrete GPU (dGPU), or a desktop with multiple dedicated graphics cards—a game often executes on Adapter A while OBS Studio composes and renders on Adapter B.

OBS Studio captures application frames using an injected dynamic link library (graphics-hook). When the hook intercepts a frame inside the target application's render loop (typically Direct3D 11, Direct3D 12, or Vulkan), it does not immediately pull pixels back to system RAM. Instead, it writes the rendered image directly into an offscreen render target allocated on that specific application's GPU context.

DXGI Shared Handles and Keyed Mutexes

To expose this texture to OBS Studio's internal graphics subsystem (libobs), the hook registers the allocation as a shared DXGI resource. Under Direct3D 11, this is achieved by creating the texture with flags such as D3D11_RESOURCE_MISC_SHARED or modern NT handles using D3D11_RESOURCE_MISC_SHARED_NTHANDLE.

Because concurrent access by two separate GPU contexts can cause screen tearing or pipeline stalls, OBS Studio synchronizes frame access via the IDXGIKeyedMutex interface:

  1. The capture hook acquires the mutex with a specific key, writes the frame to the shared texture, and releases the mutex with an incremented key.
  2. The OBS rendering thread on the host adapter opens the shared texture via ID3D11Device1::OpenSharedResource1 (or OpenSharedResource for legacy handles) and acquires the mutex on the matching key.
  3. Once read, OBS releases the mutex, allowing the game's render loop to reuse the buffer without blocking the game's presentation thread.

Cross-Adapter Data Movement via WDDM

When both the capture process and OBS reside on the same physical GPU, the DXGI handle allows zero-copy access; the texture pointer simply points to the same VRAM address. However, when OBS runs on a different GPU, the texture physically resides on the VRAM of the capturing adapter.

Modern versions of Windows (WDDM 2.0 and later) natively support cross-adapter shared surfaces. When OBS opens a shared handle originating from a foreign GPU adapter:

  • The Direct3D runtime and the Windows OS graphics kernel establish a cross-adapter resource link.
  • The GPU Direct Memory Access (DMA) copy engine transfers the texture directly over the PCIe bus from Adapter A’s VRAM into Adapter B’s VRAM.
  • This peer-to-peer or PCIe-based transfer bypasses standard application-space memory copies, minimizing CPU utilization and preserving high frame rates.

System RAM Staging Fallback

Direct cross-adapter sharing requires driver-level support and compatible resource formats. When capturing legacy APIs, running on older operating systems, or handling configurations where cross-adapter handle sharing fails, OBS Studio automatically falls back to system memory staging.

In this fallback path:

  1. The hook copies the captured GPU surface to a CPU-accessible staging texture on Adapter A using ID3D11DeviceContext::CopyResource.
  2. The hook maps the texture memory and copies the raw pixel data to shared system memory (RAM).
  3. The OBS process reads the buffer from system RAM and uploads it into a new texture allocated inside Adapter B's VRAM.

While this software-mediated path ensures broad compatibility across diverse hardware combinations, it introduces substantial PCIe bus traffic and higher CPU overhead compared to hardware-backed DXGI cross-adapter texture sharing.
