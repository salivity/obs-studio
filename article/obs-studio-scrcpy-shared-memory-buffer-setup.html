OBS Studio Scrcpy Shared Memory Buffer Setup

Capturing Android video feeds in OBS Studio through scrcpy using shared memory provides a low-latency, zero-copy or near-zero-copy pipeline for high-framerate streaming. This article explains the technical mechanics of how shared memory buffers are configured between the two systems, covering the inter-process communication (IPC) layout, memory mapping mechanisms, buffer synchronization, and how OBS Studio ingests these frames into its graphics rendering pipeline.

The Pipeline Architecture

When scrcpy captures an Android device's screen, the feed is encoded via the device's hardware encoder (MediaCodec) and piped over an Android Debug Bridge (ADB) connection using a raw TCP socket. On the host machine, scrcpy decodes the incoming H.264/H.265 stream using FFmpeg (libavcodec).

To pass the uncompressed raw frames into OBS Studio without network overhead or file I/O bottlenecks, the host system allocates a shared memory segment. Depending on the operating system and capture implementation, this is achieved via:

  • POSIX Shared Memory (shm_open / mmap): Standard for Linux environments or when directing output to a V4L2 loopback device configured in memory.
  • Windows Named File Mapping (CreateFileMapping / MapViewOfFile): Standard for native Windows IPC plugins.
  • DirectX/DXGI Shared Handles: Used when scrcpy renders via Direct3D/OpenGL and shares GPU texture surfaces directly with OBS.

Buffer Allocation and Memory Sizing

Before frame transmission begins, the producer process establishes a shared memory region sized to hold frame data plus synchronization metadata.

  1. Header Block: Contains metadata updated per frame, including frame sequence numbers, timestamp, image width, image height, pixel format (typically NV12, YUV420p, or BGRA), and row stride (pitch).
  2. Payload Region: Sized according to the uncompressed frame footprint: \[\text{Buffer Size} = \text{Stride} \times \text{Height} \times \text{Format Multiplier}\] To ensure memory alignment for SIMD operations and GPU DMA transfers, row strides are aligned to 16-byte, 32-byte, or 64-byte boundaries.

Double and Triple Buffering for Frame Synchronization

To prevent race conditions where OBS reads a buffer while scrcpy is writing to it (causing visual tearing), the shared memory region is structured as a ring buffer utilizing double or triple buffering.

  • Write Indexing: The producer (scrcpy or its output hook) locks an available buffer slot using an atomic index swap or system semaphore.
  • Lock-Free Rings: High-performance shared memory bridges often employ lock-free circular queues with atomic sequence counters (std::atomic<uint64_t>). The producer writes the decoded frame, updates the sequence number, and releases the buffer.
  • Reader Consumption: OBS checks for sequence increments. If a newer frame is ready, OBS locks that slot for reading while the producer moves to the next available buffer in the ring. If OBS lags, older unread frames are dropped to maintain real-time synchronization.

OBS Ingestion via libobs

On the consumer side, OBS Studio accesses the shared memory region through a source plugin (such as a shared memory capture plugin or virtual capture interface):

  1. Mapping: The OBS plugin attaches to the existing named shared memory handle using the same identifier established by the producer.
  2. Polling or Event Wait: The plugin listens on an OS synchronization event (such as a Windows Event or Linux pthread_cond/eventfd) triggered by scrcpy upon frame completion.
  3. Graphics Subsystem Transfer: Once a frame is ready, the plugin passes the raw memory pointer into the libobs graphics pipeline. Using functions like gs_texture_create and gs_texture_set_image, OBS copies the memory block into a GPU-accessible texture. If DXGI shared surfaces are used, OBS completely bypasses system RAM, directly binding the shared texture handle to its DirectX 11 rendering context.

Latency and Performance Tuning

Optimal buffer performance relies on maintaining matching color formats between the scrcpy decoder and OBS input. If the scrcpy FFmpeg decoder outputs NV12, configuring the shared memory buffer to accept NV12 directly eliminates CPU-based color conversion on the host. OBS offloads the YUV-to-RGB conversion to a pixel shader during its final composition pass, ensuring minimal CPU usage and sub-frame delivery latency.
