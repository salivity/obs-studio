Cache Coherency in OBS CPU Encoding While Gaming

Running high-resolution software encoding alongside modern video games in OBS Studio places severe contention on the CPU memory hierarchy. When a system executes compute-heavy game loops alongside encoders like x264 or SVT-AV1, the operating system multiplexes both workloads across shared execution resources. This creates significant cache thrashing in the shared Last-Level Cache (L3), triggers heavy cache line invalidation via hardware coherency protocols, and saturates the CPU's internal interconnects. The end result is measurable performance degradation, characterized by frame time spikes and severe drops in 1% low framerates for the game.

The Divergent Access Patterns of Games and Video Encoders

Game engines depend heavily on low-latency memory access. Game threads continuously read and update small, dynamic structures: physics objects, game logic states, transform matrices, and render command queues. These working sets benefit immensely from staying resident in high-speed L2 and L3 caches.

Software video encoders operate on an entirely different memory paradigm characterized by streaming throughput. High-resolution encoding (such as 1080p60 or 4K) requires processing multi-megabyte uncompressed frame buffers (NV12 or YUV420p). An encoder continually streams raw pixel arrays, performs discrete cosine transforms, analyzes macroblocks, and performs motion estimation against multiple reference frames. These operations rapidly sweep through tens of megabytes of data per frame, vastly exceeding the capacity of local L1 and L2 caches and repeatedly evicting data from the shared L3 cache.

Last-Level Cache (L3) Contention and Eviction

In modern x86 processors, L3 cache is typically shared among all cores on a single compute die. Because software encoding threads continually fetch fresh frame data and reference frames from system memory, they evict the cache lines containing the game's working set.

When the game thread attempts to execute its frame update, it encounters frequent L3 cache misses. Each miss forces the memory controller to make a high-latency round trip to system DRAM. Instead of retrieving data in single-digit or low double-digit nanoseconds from L3, the core stalls for 60 to 80 nanoseconds waiting for main memory. This latency variance directly produces micro-stutters and uneven frame pacing in the rendered game.

Cache Coherency Protocols and Line Invalidation

Modern multi-core processors maintain memory consistency across individual L1 and L2 caches using coherency protocols such as MESI (Modified, Exclusive, Shared, Invalid) or MOESI. In an OBS streaming scenario, cache coherency mechanisms are stressed by both shared data pipelines and memory bus snooping:

  1. Shared Memory Buffers: OBS intercepts frame data from the game through DirectX or Vulkan shared textures and memory hooks. When OBS capture threads read this data, cache lines holding framebuffers are marked as "Shared" across multiple cores. When the game engine or GPU driver writes to subsequent frames, it must issue an invalidation request to every core holding those lines, forcing pipeline flushes and coherency overhead.
  2. Cache Line Bouncing: If the capture thread and game engine touch adjacent variables located on the same 64-byte cache line (false sharing), the line is repeatedly moved between core-local caches. Each write transitions the line to the "Modified" state, forcing other cores to invalidate their copy and re-request it, inducing extreme latency spikes on both threads.

Interconnect Saturation on Multi-Core and Chiplet Architectures

The impact of coherency overhead is amplified on multi-CCX or multi-CCD architectures, such as AMD Ryzen processors, and Intel hybrid architectures featuring separate P-core and E-core clusters.

On AMD chiplet-based processors, if the game executes on CCD0 while OBS software encoding runs on CCD1, coherency traffic must traverse the Infinity Fabric. Whenever an encoding thread requests access to frame data held in CCD0's cache, or when cross-CCD snooping occurs to maintain global memory consistency, probe and invalidation traffic floods the data fabric. This saturates inter-die bandwidth, raising the effective access latency for all cores on the package.

Similarly, on hybrid Intel platforms, running memory-dense software encoding threads on E-cores while gaming on P-cores saturates the shared ring bus. The continuous flow of coherency validation messages and memory read/write requests degrades the throughput of the ring bus, directly slowing down the communication between the P-cores and the L3 cache slices.

Mitigating Coherency Bottlenecks

To minimize the impact of cache coherency and eviction issues during software encoding:

  • CPU Core Affinity (Pinning): Manually assigning the game to specific physical cores (or an entire CCD on dual-CCD processors) and binding OBS and its encoder threads to the remaining cores eliminates cross-cluster L3 cache eviction.
  • Hardware-Accelerated Encoding: Offloading the encoding pipeline to dedicated ASIC blocks (such as NVIDIA NVENC, Intel QuickSync, or AMD AMF) bypasses the CPU cache hierarchy entirely, isolating the system RAM and GPU VRAM pipelines from the CPU's coherent memory subsystem.
