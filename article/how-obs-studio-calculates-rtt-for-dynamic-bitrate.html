How OBS Studio Calculates RTT for Dynamic Bitrate

OBS Studio manages network instability by monitoring round-trip time (RTT) and socket buffer behavior directly through operating system network APIs rather than relying on application-level pings. By inspecting TCP transport statistics and measuring the drain rate of outbound socket buffers, OBS detects network congestion in real time. This mechanism allows the dynamic bitrate algorithm to throttle encoding output before the operating system's send queue overflows and forces frame drops.

The Role of Kernel-Level TCP Telemetry

OBS Studio delegates raw RTT calculation to the operating system's TCP stack. The TCP protocol continuously tracks round-trip time during transmission to regulate its congestion window (\(cwnd\)) through standard acknowledgment (ACK) packets. Instead of generating artificial network overhead with custom ping requests, OBS reads the kernel's existing calculations:

  • Windows: OBS leverages the IP Helper API (GetPerTcpConnectionEStats) to access TcpConnectionEstatsPath. This interface exposes real-time TCP telemetry, including measured smoothed RTT (SumRtt divided by sample counts) and minimum RTT.
  • Linux and macOS: OBS inspects socket-level options using getsockopt with the TCP_INFO flag. The resulting structure returns the kernel’s smoothed RTT (tcpi_rtt) and RTT variance (tcpi_rttvar) in microseconds.

By reading these values directly, OBS gains low-overhead, millisecond-accurate visibility into packet travel and acknowledgment times.

Socket Buffer Backlog and Queue Delay

RTT alone does not provide a complete picture of impending congestion. An increase in RTT often occurs downstream before packet loss actually manifests. To detect this early, OBS tracks the outbound socket buffer depth.

When a client pushes video frames to an RTMP or SRT socket faster than the network can transmit them, the unsent bytes accumulate in the send queue. On Windows, OBS tracks the socket backlog using WSAIoctl with flags like SIO_IDEAL_SEND_BACKLOG_QUERY or by measuring unacknowledged bytes in flight. When the outbound buffer begins to fill, the effective latency—the time it takes for a newly generated frame to be committed to the wire and acknowledged—increases significantly. OBS treats this buffer-bloat delay as an artificial inflation of RTT.

The Dynamic Bitrate (DBR) Control Loop

The dynamic bitrate algorithm operates on a periodic tick (typically every 100 to 500 milliseconds) to evaluate connection health using a feedback loop:

  1. Sampling: OBS samples the current smoothed RTT and the size of the unacknowledged data in the outbound buffer.
  2. Congestion Threshold Evaluation: The current RTT is compared against the baseline RTT (the minimum RTT established during stable transmission). If the measured RTT exceeds the baseline by a configured margin, or if the socket buffer fills beyond a critical threshold, the network is marked as congested.
  3. Step-Down Adjustment: When congestion is flagged, OBS immediately commands the active video encoder to reduce its target bitrate. Lowering the bitrate reduces the volume of data pushed into the socket buffer on subsequent frames, allowing the existing queue to clear.
  4. Recovery and Step-Up: When the kernel reports that the buffer has emptied and RTT has returned to baseline levels for a sustained period, the control loop incrementally increases the encoder's bitrate back toward the user-defined maximum.

Preventing Buffer Overruns

Without this telemetry, an application continues pushing data at a static rate until the OS socket buffer reaches its absolute maximum capacity. Once full, calls to send() either block the streaming thread or return WSAEWOULDBLOCK/EAGAIN, forcing the application to discard entire video packets.

By calculating the rate of change in RTT alongside the growth of the outbound socket buffer, OBS Studio acts proactively. It throttles the source data rate at the encoder level, preventing the socket from overflowing and ensuring smooth video delivery without dropped frames.
