OBS WebSocket Rate-Limiting Against DoS Loops

OBS Studio defends its integrated WebSocket server against denial-of-service (DoS) loops and malicious connection floods through a combination of strict handshake timeouts, strict state-machine enforcement, thread isolation, and transport-level backpressure. Rather than relying solely on arbitrary per-IP request counters, the obs-websocket architecture regulates traffic by limiting resource allocation until mutual authentication is achieved, immediately terminating non-compliant or repetitive bad-faith sockets, and isolating network processing from the critical video rendering pipeline.

Connection State Machine and Handshake Timeouts

The obs-websocket protocol (v5) establishes a strict multi-stage lifecycle for all incoming connections. Upon opening a raw TCP connection, a client is placed in a non-authenticated initial state.

OBS Studio prevents clients from hanging connections or rapidly spinning reconnect loops by enforcing a strict identification timeout. If a client connects and fails to send a valid Identify payload within the designated window (typically a few seconds), the server forcefully terminates the connection with an appropriate WebSocket close code (such as 1008 for policy violation or protocol-specific 400X codes). By evicting idle or looping sockets immediately, the server prevents connection table exhaustion.

Protocol Validation and Immediate Eviction

To stop flood loops where a client repeatedly transmits invalid payloads or spam requests, OBS Studio applies immediate disconnection rules rather than silently queueing or ignoring bad data:

  • Strict Sequential Ordering: If a client transmits standard requests or events before completing the Identify exchange, the connection is instantly aborted.
  • Authentication Lockout: When authentication is enabled, requests with incorrect authentication tokens or malformed challenge responses trigger immediate socket closure.
  • Malformed Payload Drops: Any message that fails JSON deserialization or protocol schema validation results in a hard disconnect, stopping recursive loop exploits at the boundary layer.

By dropping the underlying transport connection upon the first violation instead of keeping the connection open, OBS minimizes the CPU overhead required to repeatedly inspect bad traffic.

Network Buffer Backpressure

The underlying network backend (built upon asynchronous I/O frameworks such as WebSocket++) utilizes TCP socket buffering to handle incoming message volume. If a connected client attempts to flood the server with high-frequency valid requests, the processing queue naturally fills up.

Once the ingress buffer reaches its capacity, the transport layer stops reading from the operating system's TCP receive window. This pushes backpressure directly back to the sender at the transport protocol level, effectively stalling the client's transmission rate without consuming additional dynamic memory in OBS Studio.

Thread Decoupling and Main Loop Protection

A primary risk of a WebSocket DoS attack is starving the host application's video encoding and user interface threads. OBS Studio mitigates this by running the WebSocket server on dedicated worker threads decoupled from the core graphics rendering loop.

Incoming requests are parsed, validated, and placed onto internal event dispatch queues. If an incoming message stream threatens system performance, the worker thread isolates the compute load, preventing the stream output, frame rendering, and user interface from dropping frames or crashing due to network saturation.
