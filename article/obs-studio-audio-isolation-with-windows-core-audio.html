OBS Studio Audio Isolation with Windows Core Audio

OBS Studio captures and isolates audio from specific Windows applications without recording global desktop audio by integrating directly with the Windows Core Audio APIs. By leveraging the IAudioSessionManager2 interface alongside IAudioSessionNotification callbacks, OBS discovers, filters, and monitors audio sessions mapped to specific Process Identifiers (PIDs). This article explains the technical pipeline OBS Studio uses to locate target processes, track dynamic audio streams, and capture isolated application audio buffers in real time.

Core Audio and Session Architecture

Windows handles desktop audio through the Windows Audio Session API (WASAPI). Audio generated by an application is treated as an individual audio session within a WASAPI session submix rather than a unified global stream.

Every active application audio stream exposes an IAudioSessionControl interface, which can be queried for an extended IAudioSessionControl2 interface. This extended interface exposes key metadata about the process generating the sound, most notably the target application's PID via the GetProcessId method.

Session Discovery and PID Filtering

To isolate a chosen application, OBS Studio queries the default audio output endpoint using the multimedia device interface (IMMDeviceEnumerator and IMMDevice). It activates an IAudioSessionManager2 instance on that endpoint to inspect all currently open audio sessions.

  1. Session Enumeration: OBS calls IAudioSessionManager2::GetSessionEnumerator to retrieve an IAudioSessionEnumerator.
  2. Session Inspection: It loops through every active session retrieved by GetSession, querying each for IAudioSessionControl2.
  3. PID Matching: OBS extracts the PID of each session via IAudioSessionControl2::GetProcessId. If the PID matches the user-selected application (or belongs to a child/parent process linked to that executable), that session handle is targeted for capture.

Real-Time Session Monitoring with IAudioSessionNotification

Applications regularly open and close audio handles—for example, when a media player moves to a new track, when a game loads a cutscene, or when a web browser suspends inactive tabs. Static PID polling is inefficient and can lead to dropped capture handles.

To address this, OBS Studio implements and registers the IAudioSessionNotification interface:

  • Registration: OBS calls IAudioSessionManager2::RegisterSessionNotification, passing its custom notification client.
  • Event Dispatching: Whenever any application creates a new audio session on the selected device, Windows fires the IAudioSessionNotification::OnSessionCreated callback.
  • Dynamic Hooking: The OnSessionCreated event passes a pointer to the new IAudioSessionControl. OBS immediately queries this pointer for IAudioSessionControl2, checks if the new session's PID matches the tracked target, and attaches its capture pipeline if there is a match.

Capture Implementation and Process Loopback

Once the matching session handles are verified, OBS captures the isolated audio stream. On modern versions of Windows 10 (build 2004 and newer) and Windows 11, OBS utilizes process-specific loopback capture via the AUDIOCLIENT_PROCESS_LOOPBACK_PARAMS structure passed into IAudioClient::InitializeClientService.

By supplying the target PID to the process loopback activation parameters:

  • Windows automatically isolates that process's audio tree at the driver and mixer level.
  • Background system sounds, voice chat from separate applications, and other desktop audio are excluded natively by the operating system audio engine.
  • Audio packets are read asynchronously using an IAudioCaptureClient buffer loop, then normalized and fed into the OBS Studio mixing bus.

Session Destruction and Lifecycle Handling

In addition to creation tracking, OBS implements IAudioSessionEvents on individual sessions to handle state changes:

  • Session Disconnection: Monitored through IAudioSessionEvents::OnSessionDisconnected, which alerts OBS if the application closed its audio device or terminated.
  • Volume and Mute Changes: Monitored via IAudioSessionEvents::OnSimpleVolumeChanged, allowing OBS to accurately mirror native application volume behavior.

When the target application terminates, OBS unregisters its notification listeners using IAudioSessionManager2::UnregisterSessionNotification and cleans up allocated COM pointers to prevent handle leaks. If the user restarts the target executable, the dynamic registration triggers again as soon as the application initializes its new WASAPI render client.
