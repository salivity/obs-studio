Low Latency OBS Streaming Through a Reverse Proxy

This article examines how OBS Studio achieves and maintains low latency when routing live video frames through an intermediary local reverse proxy. By coordinating optimized real-time transport protocols, zero-latency encoding profiles, operating-system-level socket configurations, and unbuffered proxy pipelines, the software bypasses typical network bottlenecks. Understanding this pipeline reveals how high-bitrate video reaches destination endpoints without perceptible delay.

Minimal Pipeline Buffering and Encoder Tuning

Latency control begins at the encoding layer within OBS Studio. Standard live-streaming presets introduce small frame buffers to improve compression efficiency, particularly through the use of bidirectional predictive frames (B-frames). To maintain low latency, OBS allows users to deploy low-overhead presets, such as x264’s tune=zerolatency or hardware-accelerated modes (such as NVIDIA NVENC Low Latency). These modes force immediate frame-in, frame-out behavior by eliminating B-frames entirely and restricting reference frame lookaheads. By ensuring that frames are encoded instantaneously, OBS prevents frame accumulation before the data reaches the output buffer.

Low-Overhead Network Protocols

The choice of protocol between OBS and the reverse proxy plays a critical role in latency management:

  • SRT (Secure Reliable Transport): Uses UDP as its base, implementing configurable retransmission buffers. Over a local loopback interface, the latency parameter can be dropped to near zero (e.g., 20–50 ms) without risk of packet loss.
  • WebRTC / WHIP: Provides sub-second real-time streaming natively using UDP, SRTP, and SCTP, prioritizing real-time delivery over complete packet reliability.
  • RTMP / Enhanced RTMP: While bound to TCP, RTMP remains standard. Because the connection to a local reverse proxy runs over local hardware (such as 127.0.0.1), the network round-trip time (RTT) is practically instantaneous, largely mitigating TCP's head-of-line blocking issues.

Socket-Level Optimizations

When transmitting data over local TCP connections, OBS and the underlying network stack rely on specific socket configurations to prevent transmission delays:

  • Disabling Nagle's Algorithm (TCP_NODELAY): By default, TCP stacks buffer small packets to combine them into larger segments. Enabling TCP_NODELAY forces the OS network stack to dispatch video chunks immediately, regardless of packet payload size.
  • Kernel Buffer Sizing: OBS maintains small, dedicated egress buffers. If network congestion does not exist (as is typical for local loopback connections), data transfers directly from user space to the proxy's receiving socket with near-zero queueing.

Reverse Proxy Configuration Requirements

The local reverse proxy (such as NGINX, HAProxy, or Envoy) must actively support real-time data pass-through. A standard reverse proxy often buffers inbound requests to optimize disk or network I/O. For low-latency streaming:

  • Proxy Buffering Disabled: In NGINX, for instance, directives like proxy_buffering off; and proxy_request_buffering off; prevent the proxy from caching frames before forwarding them downstream.
  • TCP Streaming (Layer 4 Forwarding): Instead of parsing HTTP or application layers, proxies can route traffic at the transport layer using TCP/UDP stream modules. This minimizes CPU parsing overhead and enables pure packet-level forwarding.
  • Unix Domain Sockets: If supported by both OBS plugins and the proxy, transmitting data via Unix domain sockets rather than the TCP loopback stack bypasses network stack overhead altogether, utilizing direct shared-kernel memory copies.

Through the combination of immediate encoding, non-blocking transport sockets, and streaming-oriented proxy configurations, OBS Studio transmits video through local reverse proxies with delay measured in single-digit milliseconds.
