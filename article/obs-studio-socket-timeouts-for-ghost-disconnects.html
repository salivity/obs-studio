OBS Studio Socket Timeouts for Ghost Disconnects

This article examines how OBS Studio handles socket timeout configurations and underlying network parameters to identify ghost disconnections—situations where a network path silently fails while the software still considers the connection active. You will learn the mechanics behind TCP half-open states in streaming, how OBS Studio and its core libraries enforce socket-level send/receive timeouts and keepalives, and the configuration strategies used to trigger clean reconnections before ingestion servers drop the streaming session.

The Mechanics of Ghost Disconnections

A ghost disconnection (or TCP half-open connection) occurs when the local machine continues attempting to send data over a route that has silently dropped packets, lost its gateway, or experienced an unacknowledged failure. In standard TCP communication, if an intermediate router drops a connection without sending a FIN or RST packet, the operating system can take anywhere from several minutes to hours to declare the socket dead via default retransmission limits.

For real-time streaming to services like Twitch, YouTube, or ingest relays, a half-open state causes local buffer saturation, frame drops, and severe latency. Meanwhile, the server-side ingest server eventually times out the idle session and terminates it. To prevent this, OBS Studio must actively detect the failure locally via strict socket timeout parameters and trigger its internal reconnect logic before the server closes the session.

Protocol-Level Socket Timeout Implementation

OBS Studio does not rely purely on default OS-level TCP socket behavior. Depending on the streaming protocol used (RTMP, RTMPS, or SRT), OBS and its underlying modules (obs-outputs, libobs, and integrated libraries like FFmpeg and libsrt) configure explicit socket properties.

1. RTMP and FFmpeg Network Options

For standard RTMP/RTMPS streams driven by FFmpeg or native output implementations, socket behavior is bounded by specific network timeout flags passed down to the TCP socket:

  • rw_timeout / timeout: Configured in microseconds, this parameter sets the maximum blocking time for read and write operations. If a socket write fails to complete within this window due to a stalled TCP window or unacknowledged packets, the call returns an error (ETIMEDOUT or EWOULDBLOCK).
  • SO_SNDTIMEO and SO_RCVTIMEO: At the OS socket layer, these flags ensure that if output buffers fill up and cannot be flushed to the network card within a predetermined time threshold, the blocking send system call aborts rather than hanging indefinitely.

When OBS detects a failed write cycle through these timed-out calls, it flags the output status as disconnected immediately, rather than waiting for OS-level TCP retransmission timeouts (which default to 15 retries under Linux or 5 under Windows).

2. SRT (Secure Reliable Transport) Socket Timers

When using the SRT protocol in OBS, timeout handling shifts from OS TCP management to user-space UDP timers:

  • sndtimeo: Sets the maximum blocking time for sending data. If the network interface cannot send packet bursts, the socket terminates the operation.
  • peeridle: Dictates how long the SRT connection will wait for a keepalive or data packet from the receiver before declaring the session dead (typically set to 5000 ms by default).

Because SRT implements its own handshake, flow control, and keepalive logic over UDP, it detects link degradation and ghost breaks significantly faster than standard TCP stacks.

OS TCP Keepalive Probing

To detect silent dead links where no active write error has yet propagated up the stack, OBS benefits from TCP Keepalive settings (SO_KEEPALIVE).

When configured at the socket level:

  1. Probe Interval (TCP_KEEPINTVL): The frequency at which keepalive probes are transmitted when previous probes go unacknowledged.
  2. Idle Time (TCP_KEEPIDLE): The duration of silence before the socket transmits the first keepalive probe.
  3. Probe Count (TCP_KEEPCNT): The number of unanswered probes required before marking the socket as broken.

By forcing aggressive keepalive intervals within its network code, OBS ensures that dead links are validated in seconds rather than the operating system’s default multi-minute windows.

Advanced Network Configuration within OBS Studio

OBS exposes internal network controls in its user interface that directly manipulate how data is queued and pushed through the underlying sockets:

  • Enable network optimizations: Binds the internal streaming pipeline to event-driven socket handling rather than fixed-interval buffer dumps. This allows the application to detect socket backpressure and unacknowledged buffers instantly.
  • Dynamically change bitrate to manage congestion: Instead of allowing internal socket buffers to overflow—which triggers abrupt timeout errors—OBS throttles video bitrate in real time based on how fast the remote socket consumes the data.
  • Bind to IP: Explicitly forces socket allocation to a specific Network Interface Card (NIC). This ensures that if a route fails, the socket does not silently get rerouted through a dormant fallback interface that leaves the connection in a half-dead state.

Reconnection Logic Execution

Once the socket timeout threshold is breached and the socket returns an unrecoverable error, OBS Studio's internal state machine initiates its reconnect loop:

  1. Active Socket Teardown: The stalled file descriptor is closed immediately, releasing local port bindings and flushing stale memory queues.
  2. Grace Period Management: OBS starts its configured Retry Delay countdown (found under Settings > Advanced > Automatic Reconnect).
  3. Session Resumption: A fresh handshake is dispatched to the ingestion server. If executed before the server's own upstream inactivity timer drops the session completely, the stream resumes without generating an entirely new broadcast ID or breaking the viewer stream.
