OBS Studio Audio Video Thread Deadlock Symptoms

An internal thread deadlock between the audio processing loop and the video renderer in OBS Studio creates a critical synchronization failure that disrupts media encoding, UI interaction, and output pipelines. This article details the distinct operational symptoms associated with this issue, including output freezes, buffer starvation, persistent "Stopping" states during session shutdown, and specific thread execution patterns observed in diagnostic logs and process monitors.

1. Instantaneous Video Preview and Output Freeze

Because the video rendering thread becomes blocked waiting on an audio mutex or synchronization event, frame delivery abruptly halts. The canvas preview within the OBS interface freezes on the last successfully processed frame. Similarly, the outgoing stream or local recording stops updating visually, sending duplicate frames or freezing entirely depending on the container format and encoder behavior.

2. Audio Starvation, Stuttering, or Abrupt Silence

When the audio processing loop cannot proceed due to the reciprocal lock held by the video renderer, the audio buffers run dry. This causes immediate audio artifacts such as high-frequency stuttering, looped buffer buzzing, or sudden, complete silence in the output. The audio meters in the OBS mixer either freeze in their last active state or drop to negative infinity decibels without updating.

3. Permanent "Stopping Stream" or "Stopping Recording" Hang

One of the most identifiable markers of this deadlock occurs when the user attempts to terminate an active session. The UI button changes to "Stopping Streaming..." or "Stopping Recording..." and remains stuck indefinitely. Because OBS requires all media threads to cleanly flush buffers and join before closing the output context, the circular dependency prevents the shutdown sequence from completing, requiring a forced process termination via Task Manager or kill -9.

4. Flatlined Thread CPU Usage Without Process Termination

Unlike a crash that generates a crash report window, a thread deadlock leaves the obs64.exe process fully alive in the operating system. In system diagnostics, CPU utilization for the media processing threads drops to zero or near-zero percent because the threads are in a wait state (Wait:UserRequest or waiting on a critical section) rather than executing active code. Memory usage remains static, and no active CPU spikes occur.

5. Suspended Log Output and Timestamp Divergence

In standard operation, OBS continuously outputs performance metrics and frame-drop statistics to its runtime log. Once the audio and video threads deadlock, new log entries relating to frame rendering, audio tick cycles, and encoding statistics cease entirely. If debug logging is enabled, the log will show an abrupt divergence in audio and video timestamps right before all logging activity stops.

6. Mutex Wait States in Thread Backtraces

When analyzing a memory dump using a debugger such as WinDbg or GDB, the symptoms resolve into a classic circular wait:

  • The video thread (often inside obs_graphics_thread or render pass routines) waits on an audio-related lock or clock synchronization primitive.
  • The audio thread (inside audio_thread or related buffer mixing routines) waits on a video frame lock or shared scene-item mutex.
  • Neither thread can release its resource, keeping both execution loops permanently suspended.
