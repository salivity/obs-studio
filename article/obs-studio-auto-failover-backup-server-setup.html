OBS Studio Auto-Failover Backup Server Setup

Configuring an emergency backup streaming server ensures zero downtime by routing both your primary and secondary OBS rigs through an intermediary ingestion proxy before hitting the final distribution platform. If the primary feed drops due to hardware failure, network outage, or software crashes, the proxy server instantly switches to the secondary feed or an emergency standby slate without dropping the connection to the audience. This guide details how to build and configure a self-hosted, automated RTMP/SRT failover pipeline to handle OBS signal loss seamlessly.

1. Architecture Overview

Directly streaming to platforms like YouTube or Twitch from two independent rigs rarely works smoothly without platform-level dual-ingest features. To achieve universal auto-failover across any platform:

  1. Primary OBS Rig: Sends stream to rtmp://[Your-Server-IP]/live/primary.
  2. Secondary OBS Rig (or Standby Looper): Sends identical stream to rtmp://[Your-Server-IP]/live/backup.
  3. Intermediary Ingest Server (NGINX/FFmpeg): Listens to both streams. It defaults to relaying the primary stream to the destination CDN. Upon signal loss on the primary stream, it switches output to the backup stream automatically.
  4. Target Platform: Receives a single continuous stream from the intermediary server.

2. Deploying the Ingest Proxy Server

The most reliable, lightweight approach is an Ubuntu-based Linux VPS (DigitalOcean, Linode, AWS EC2, or a local server) running NGINX with the RTMP module.

Step 1: Install Dependencies

Run the following commands on your Linux server:

sudo apt update
sudo apt install -y build-essential libpcre3 libpcre3-dev libssl-dev zlib1g-dev ffmpeg nginx libnginx-mod-rtmp

Step 2: Configure NGINX RTMP with Fallback Redundancy

Edit the NGINX configuration file:

sudo nano /etc/nginx/nginx.conf

Append the following configuration block to the end of the file:

rtmp {
    server {
        listen 1935;
        chunk_size 4096;

        # Primary ingest point
        application primary {
            live on;
            record off;

            # Direct fallback if primary stream is unavailable
            fallback backup;

            # Push directly to final target (e.g., YouTube/Twitch)
            push rtmp://a.rtmp.youtube.com/live2/YOUR-STREAM-KEY;
        }

        # Backup ingest point
        application backup {
            live on;
            record off;
        }
    }
}

Step 3: Restart NGINX

Verify syntax and restart the service:

sudo nginx -t
sudo systemctl restart nginx

3. Alternative: FFmpeg Seamless Switching Server

If you need automated failover with continuous sync or the ability to show an emergency slate (looping video) when both OBS rigs go down, configure an FFmpeg listener process.

Create a bash script (failover_relay.sh) running on the server:

#!/bin/bash
PRIMARY_INPUT="rtmp://127.0.0.1:1935/live/primary"
BACKUP_INPUT="rtmp://127.0.0.1:1935/live/backup"
DESTINATION="rtmp://live.twitch.tv/app/YOUR_STREAM_KEY"

ffmpeg -re -stream_loop -1 -i emergency_slate.mp4 \
  -f live_flv -i "$PRIMARY_INPUT" \
  -f live_flv -i "$BACKUP_INPUT" \
  -filter_complex "[1:v][2:v][0:v]fallback=primary=0:secondary=1:tertiary=2[outv];[1:a][2:a][0:a]amix=inputs=3[outa]" \
  -map "[outv]" -map "[outa]" \
  -c:v libx264 -preset veryfast -b:v 6000k \
  -c:a aac -b:a 160k \
  -f flv "$DESTINATION"

4. Configuring OBS Studio (Primary and Secondary Rigs)

Both instances of OBS Studio must output streams with identical video and audio parameters to avoid encoder renegotiation delays at the server level.

Encode Uniformity Settings

Match these settings on both machines:

  • Settings > Output > Output Mode: Advanced
  • Keyframe Interval: 2 seconds (strictly fixed; do not use auto/0).
  • Rate Control: CBR
  • Framerate & Resolution: Identical (e.g., 1080p60 on both).
  • Audio Sample Rate: 48 kHz (Settings > Audio).

Stream Target Configuration

  • Primary Machine:
    • Service: Custom...
    • Server: rtmp://[YOUR-SERVER-IP]:1935/primary
    • Stream Key: Leave blank or set a secure token.
  • Secondary Machine:
    • Service: Custom...
    • Server: rtmp://[YOUR-SERVER-IP]:1935/backup
    • Stream Key: Leave blank or set a secure token.

5. Cloud Alternative: AWS Elemental MediaLive Automatic Input Failover

If managing a Linux VPS is not preferred, use cloud provider auto-failover:

  1. In AWS Console, navigate to MediaLive and create two Inputs of type RTMP (push).
  2. Name them OBS_Primary and OBS_Backup.
  3. Create an Input Failover Pair in MediaLive:
    • Select OBS_Primary as Primary.
    • Select OBS_Backup as Secondary.
    • Set Failover Conditions to trigger on loss of video/audio or input loss (set detection threshold between 2000ms and 5000ms).
  4. Set the Channel Output to push to your destination CDN via RTMP.

6. Validation and Failover Testing

  1. Start streaming from both the Primary and Secondary OBS rigs.
  2. Verify that the destination platform receives the primary feed.
  3. Simulate an unexpected drop:
    • Hard Fail: Disconnect the Ethernet cable or kill the OBS process (killall -9 obs or Task Manager force close) on the primary rig.
  4. Monitor the final destination stream. The ingest server will detect the missing RTMP packets and swap ingestion to the secondary OBS feed within 1 to 3 seconds.
  5. Restore the primary rig connection to verify whether the system holds on the backup feed or cleanly preempts back to the primary source, depending on your fallback rule configuration.
