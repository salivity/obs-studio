OBS Studio CORS in Local Browser Overlays

This article examines how OBS Studio handles Cross-Origin Resource Sharing (CORS) restrictions when rendering local HTML browser overlays. OBS Studio uses the Chromium Embedded Framework (CEF) to process web sources, meaning it inherently enforces standard modern browser security models. Understanding how OBS treats the file:/// origin, why API requests fail, and the available mechanisms to circumvent these restrictions ensures custom alerts, widgets, and dynamic overlays function correctly.

The Underlying Architecture: Chromium Embedded Framework (CEF)

OBS Studio does not use a custom HTML rendering engine; instead, it embeds CEF. Because CEF mirrors Google Chrome's security model, it enforces standard Same-Origin Policy (SOP) and CORS rules out of the box.

When you load a remote URL (such as https://example.com/overlay.html), CEF handles CORS normally: if that page makes a fetch() or XMLHttpRequest to a third-party API, the target server must include appropriate Access-Control-Allow-Origin headers matching the calling domain.

The Problem with Local Files (file:///)

When developing custom overlays locally and loading them into OBS via the "Local file" checkbox in the Browser Source properties, the page is served using the file:/// protocol.

Modern Chromium versions treat local files with extreme security:

  • The Origin header for a file:/// request is sent as null or omitted entirely.
  • Most public and private REST APIs automatically reject requests where Origin: null unless the API is configured with a wildcard (Access-Control-Allow-Origin: *).
  • Chromium restricts local scripts from accessing network resources if the protocol does not match, leading to console errors such as: Access to fetch at '...' from origin 'null' has been blocked by CORS policy.

How OBS Handles CORS Natively

OBS Studio itself does not automatically patch or disable CORS for individual Browser Sources. The software maintains Chromium's sandboxing and security features by default to prevent malicious web pages from exploiting the user's local network or file system.

Consequently, if a local overlay script attempts to pull data directly from an API that does not support null origins or wildcard CORS, the request will fail silently in the stream unless inspected through CEF remote debugging.

Solutions for Bypassing CORS in OBS Overlays

Streamers and developers dynamic data into local overlays must handle CORS through one of several standard methods:

1. Running a Local Web Server

Instead of checking the "Local file" box in the Browser Source, serve the overlay from a local web server (such as Node.js, Python's http.server, or an extension like VS Code Live Server).

  • Point the OBS Browser Source to http://localhost:PORT/overlay.html.
  • This changes the origin from null to http://localhost:PORT.
  • You can then configure a local proxy server to query the third-party API, attach appropriate CORS headers, and return the data to the overlay.

2. Launching OBS with Web Security Disabled

For local, trusted development environments, OBS Studio can be forced to ignore CORS restrictions entirely via CEF startup flags.

  • Add --disable-web-security to the OBS Studio shortcut target: 
    "C:\Program Files\obs-studio\bin\64bit\obs64.exe" --disable-web-security
  • This flag completely disables the Same-Origin Policy within CEF, allowing file:/// overlays to freely fetch data from any external API regardless of CORS headers.
  • Note: This reduces browser isolation security across all Browser Sources inside that OBS session.

3. Using JSONP or Server-Side Relays

If the target API supports JSONP (JSON with Padding), requests can be made via dynamic <script> tags rather than fetch(), bypassing CORS entirely. Alternatively, routing requests through a remote cloud function (such as AWS Lambda or Cloudflare Workers) that appends Access-Control-Allow-Origin: * to the API response ensures the overlay can consume the data without changing OBS launch parameters.
