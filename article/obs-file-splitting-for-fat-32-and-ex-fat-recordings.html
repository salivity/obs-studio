OBS File Splitting for FAT32 and exFAT Recordings

This article examines how OBS Studio handles file size thresholds during continuous 24-hour recording sessions on FAT32 and exFAT file systems. It covers the technical constraints imposed by legacy and modern drive formats, the mechanics of OBS Studio’s automatic file-splitting engine, the consequences of failing to implement thresholds on restrictive file systems, and the optimal configuration practices required to ensure uninterrupted, stable data capture over extended periods.

The Technical Limits of FAT32 vs. exFAT

The primary operational difference between FAT32 and exFAT lies in their maximum file size thresholds.

  • FAT32: Has a strict 32-bit architecture limit allowing a maximum single-file size of 4 GiB minus 1 byte (4,294,967,295 bytes). If any application attempts to write data beyond this boundary, the operating system issues an I/O write error.
  • exFAT: Designed as the modern successor to FAT32 for flash storage, exFAT supports a theoretical file size limit of 16 EiB (exabytes). A continuous 24-hour recording—even at extremely high bitrates—will never encounter a hard filesystem cap on an exFAT volume.

How OBS Behaves Without Configured Thresholds

OBS Studio relies on system-level write calls to deposit encoded frames into the destination container. It does not automatically detect whether the target volume is formatted as FAT32 or exFAT.

If a user initiates a continuous recording to a FAT32 partition without configuring split parameters, OBS will write normally until the file size reaches 4 GiB. At this point, the underlying filesystem refuses additional write operations. OBS flags an encoding/output error, stops recording, and often terminates the session unexpectedly. Depending on the chosen container (such as standard MP4), this abrupt halt can leave the file unfinalized and corrupted.

On an exFAT volume without configured split parameters, OBS writes continuously until either the drive runs out of physical space or the user manually terminates the recording. The 24-hour session remains contained within a single file.

Configuring Automatic File Splitting in OBS Studio

To navigate the 4 GiB ceiling of FAT32 or to make multi-hour recordings manageable on exFAT, OBS Studio provides native file-splitting mechanisms under Settings > Output > Recording (with Output Mode set to Advanced).

Under the Automatic File Splitting section, users can toggle splits based on two primary metrics:

  1. Split by Size: OBS monitors the current output file's byte count. For FAT32 partitions, this threshold should be configured conservatively below the 4 GiB limit—typically set between 3500 MB and 3900 MB (or roughly 3.5 GiB to 3.8 GiB). This provides a safety margin preventing container metadata overhead or buffer flushes from triggering the 4 GiB filesystem block.
  2. Split by Time: OBS splits the file at set temporal intervals (e.g., every 60 minutes or 120 minutes). For a continuous 24-hour stream on FAT32, users must calculate their bitrate to ensure that the time window never accumulates more than 4 GiB of data. On exFAT, time-based splits are typically deployed to create predictable segment lengths rather than to bypass hardware limitations.

Seamless Transitions and Container Behavior

When a split threshold is reached, OBS executes a seamless boundary transition. The internal multiplexer closes the current segment and immediately directs subsequent video and audio packets into a newly generated file (typically tagged with an incrementing numerical suffix or timestamp).

Because the encoder runs continuously in the background, this transition produces zero dropped frames between the end of the previous file and the start of the next file. When imported into post-production non-linear editing software, adjacent clips align back-to-back without gaps or sync drift.

Recommended Container Selection for 24-Hour Recordings

Regardless of whether FAT32 thresholds or exFAT capacities are used, long continuous sessions are vulnerable to power interruptions or crashes.

  • Standard MP4/MOV: Requires a continuous "moov" atom at the end of the file. If an unmonitored FAT32 write error occurs, the entire segment becomes unreadable.
  • Fragmented MP4 (fMP4) or MKV: Writes data in self-contained fragments throughout the session. If an error occurs—whether due to a full drive or hitting a FAT32 ceiling—the recorded footage up to that exact millisecond remains playable and salvageable. MKV or fMP4 should always be selected as the output format when maintaining multi-hour recording setups.
