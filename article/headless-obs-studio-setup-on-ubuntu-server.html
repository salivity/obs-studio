Headless OBS Studio Setup on Ubuntu Server

Deploying OBS Studio on a headless Ubuntu server enables scalable, automated cloud video production without requiring a physical monitor or manual GUI interaction. Because OBS Studio is natively designed as a desktop application dependent on a display server and rendering context, achieving headless operation requires simulating a display environment using Xvfb, configuring software or GPU-accelerated rendering, managing configuration files programmatically, and driving production remotely via the OBS WebSocket API.

Virtual Display Emulation with Xvfb

OBS Studio requires an active X11 display server to initialize its graphical interface and canvas compositing pipelines. On a headless Ubuntu server, this requirement is met using the X Virtual Framebuffer (xvfb), which performs all graphical operations in memory without physical display hardware.

To prepare the environment, install the necessary dependencies:

sudo apt update
sudo apt install -y obs-studio xvfb

You can execute OBS Studio within an ephemeral virtual display using the xvfb-run wrapper:

xvfb-run --auto-servernum --server-args="-screen 0 1920x1080x24" obs

Alternatively, you can run an isolated Xvfb display daemon as a persistent service:

Xvfb :99 -screen 0 1920x1080x24 &
export DISPLAY=:99
obs &

Hardware and Software Rendering Configuration

OBS Studio utilizes OpenGL for rendering scenes and transitions. In a headless environment, rendering must be routed through either hardware or software acceleration:

  • Software Rendering (CPU): If the server lacks a dedicated GPU, Ubuntu uses Mesa's LLVMpipe driver to handle OpenGL calls on the CPU. While functional for low-framerate or basic compositing tasks, it significantly increases CPU load.
  • Hardware Acceleration (GPU): In cloud instances equipped with NVIDIA GPUs, install the proprietary NVIDIA drivers and the NVIDIA headless display configuration utilities. Ensure the display server has access to the GPU via EGL or a virtual display context, which enables NVENC hardware encoding and hardware-accelerated OpenGL compositing.

Pre-Configuring Profiles and Scene Collections

Because the graphical interface cannot be manipulated manually, configuration files must be provisioned ahead of runtime.

OBS stores its configurations in ~/.config/obs-studio/. To automate deployments:

  1. Generate the desired profile (containing video output resolution, bitrate, and encoder settings) and scene collection (containing layouts, RTMP inputs, and overlays) on a local machine.
  2. Export these JSON and INI configuration files into your deployment pipeline.
  3. Place the files into ~/.config/obs-studio/basic/profiles/ and ~/.config/obs-studio/basic/scenes/ on the server before launch.

You can direct OBS to load specific configurations upon launch using command-line arguments:

xvfb-run obs --profile "CloudProduction" --collection "DefaultScene" --startstreaming

Automation via OBS WebSocket API

Modern versions of OBS Studio (v28 and later) include the native OBS WebSocket server, which serves as the primary control plane for cloud workflows.

To enable the WebSocket server headlessly, edit ~/.config/obs-studio/global.ini to configure the network port, authentication password, and auto-start directives:

[OBSWebSocket]
ServerEnabled=true
ServerPort=4455
ServerPassword=YourSecurePassword
AlertsEnabled=false

Once running, external orchestration tools, automated workers, or cloud microservices can connect over WebSocket using standard client libraries (available in Python, JavaScript, Go, and C#). Through this interface, automated workflows can:

  • Switch scenes dynamically based on external triggers or webhooks.
  • Update browser source URLs, media files, and lower-third graphics.
  • Monitor dropped frames, CPU utilization, and streaming output health.
  • Trigger start and stop actions for recording and RTMP/SRT streaming endpoints.

Containerization and Process Supervision

For resilient production pipelines, the virtual display, OBS process, and configuration mounts are typically encapsulated within a Docker container or managed via a systemd service unit. A systemd configuration ensures that the Xvfb instance and OBS process automatically restart upon failure, providing continuous availability for cloud-native streaming infrastructure.
