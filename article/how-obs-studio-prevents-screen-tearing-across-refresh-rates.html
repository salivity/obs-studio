How OBS Studio Prevents Screen Tearing Across Refresh Rates

This article explains the technical pipeline OBS Studio uses to eliminate screen tearing when capturing and rendering frames at a framerate that differs from your monitor's native vertical refresh rate (V-Sync). It covers the decoupled rendering architecture, off-screen GPU framebuffers, DirectX Graphics Infrastructure (DXGI) capture methods, and how the composited canvas is safely handed off to the video encoder without scanline artifacts.

The Decoupled Render Loop

Traditional screen tearing occurs on physical displays when a GPU pushes a new frame to the monitor's front buffer while the display is mid-scanout, resulting in parts of two different frames showing at once. OBS Studio bypasses this hardware limitation because its internal canvas does not directly drive physical display hardware.

Instead, OBS Studio operates a completely independent graphics thread with a decoupled timing loop:

  • High-Resolution Clock: OBS uses precision platform timers to trigger render ticks at exact mathematical intervals (for example, every 16.66 milliseconds for a 60 FPS canvas), entirely independent of whether the host display runs at 60 Hz, 144 Hz, 240 Hz, or a variable refresh rate (G-Sync/FreeSync).
  • Off-Screen Memory Buffering: The canvas renders strictly to internal VRAM textures rather than the monitor's active scanout buffers. Because memory writes occur within bounded off-screen framebuffers, monitor scanlines do not dictate frame generation.

Source Ingestion via Shared GPU Textures

When capturing sources such as games or secondary applications, OBS Studio accesses finished frames rather than partial rasterizations:

  1. DirectX/Vulkan Hooking: When using Game Capture, OBS injects a hook into the target process that listens for presentation calls (such as IDXGISwapChain::Present).
  2. Copying Completed Surfaces: The hook grabs a handle to the back buffer only after the application finishes drawing the frame. If the game runs at 120 FPS and OBS runs at 60 FPS, OBS simply polls the latest fully completed texture when its own internal tick arrives, dropping or skipping the intermediate frames entirely.
  3. Shared Surfaces: Through cross-adapter or cross-process texture sharing (IDXGIResource::GetSharedHandle), the frame moves within GPU VRAM directly into OBS Studio’s rendering engine without intermediate memory tearing.

Double and Triple Buffering on the Canvas

OBS Studio applies multi-buffering to its scene rendering pipeline. When a new tick begins:

  • Compositing: The graphics subsystem draws each active source (game feeds, webcams, browser overlays) onto an internal back-buffer texture.
  • Atomic Swaps: Once compositing is 100% complete, OBS performs an atomic buffer swap. The newly composited frame is marked as ready for encoding, while the previous frame is retired. If a source updates while OBS is mid-composite, OBS ignores that partial update until the subsequent canvas tick, ensuring incomplete frames are never merged into the final canvas.

The Hand-Off to Hardware Encoders

Once the internal canvas frame is complete, it must be sent to the video encoder (NVENC, QuickSync, AMF, or CPU/x264). Because the canvas texture is fully realized in VRAM:

  • The encoder accesses the complete, sealed texture surface directly through an asynchronous memory copy or hardware-level pointer handoff.
  • The encoder processes the surface as a static image slice. Scanline desynchronization cannot occur inside the encoder because it reads from a fixed memory address containing a single, cohesive frame.

Rendering the Preview on Mismatched Displays

If the native monitor has an active V-Sync rate distinct from the canvas (e.g., viewing a 60 FPS OBS preview on a 144 Hz screen), OBS relies on the operating system’s compositor (such as the Desktop Window Manager, or DWM, on Windows):

  • The DWM acts as an intermediary, treating the OBS Studio preview window as an application surface.
  • The DWM composites the application window into the desktop's native presentation rate using its own multi-buffering, preventing tearing on the local monitor during live operation, even if frame-pacing judder occurs due to non-integer frame rate divisions.
