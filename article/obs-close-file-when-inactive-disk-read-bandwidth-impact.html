OBS Close File When Inactive: Disk Read Bandwidth Impact

This article examines how the "Close file when inactive" setting in OBS Studio influences disk read bandwidth across multi-scene production environments. You will learn the mechanics behind this Media Source toggle, how it alters drive input/output patterns, the performance trade-offs between continuous read bandwidth and sudden access spikes, and how to configure it properly based on your storage hardware.

Understanding the Setting

In OBS Studio, any Media Source includes an option labeled "Close file when inactive." By default, OBS keeps media assets open and cached in system memory or standby, even when the scene containing that source is not active on Program or Preview.

Checking "Close file when inactive" forces OBS to terminate the active file handle, release memory allocations, and cease playback entirely as soon as the source leaves the active rendering pipeline. When the scene becomes active again, OBS must reopen and re-read the file from your storage drive.

The Impact on Disk Read Bandwidth

In multi-scene setups containing video loops, stingers, background plates, or animated overlays, this single toggle fundamentally shifts how your storage drive handles read bandwidth.

1. Baseline Bandwidth Reduction

When the option is unchecked, multiple scenes containing running media files can pull constant read streams from your storage simultaneously—even while hidden. If you have five scenes that each feature a 4K 60 FPS video loop, your storage may need to service concurrent reads across all five files at all times.

Checking "Close file when inactive" eliminates this idle overhead. Inactive scenes consume exactly zero disk read bandwidth. Baseline disk activity drops to only the assets currently visible in the active scene or transition.

2. Burst Spikes During Scene Transitions

While enabling the setting prevents sustained disk reading, it introduces sharp, immediate read spikes. The moment you transition to a new scene:

  • OBS must locate the file on disk.
  • The drive must read the initial container data and video headers.
  • Decoders must populate buffer caches before rendering frames.

Instead of a smooth, predictable stream, the storage drive experiences a burst of high-bandwidth read requests compressed into a few milliseconds.

Storage Hardware Considerations

The practical impact of these bandwidth dynamics depends heavily on your drive architecture:

  • NVMe SSDs: High-speed NVMe drives easily absorb the initial read spikes created when reopening closed files. Because read latency is near zero and sequential throughput is massive, you can check this setting on almost every source to keep baseline disk bandwidth low without causing dropped frames during transitions.
  • SATA SSDs: Capable of handling moderate burst activity, but simultaneous scene changes with multiple heavy media assets can briefly saturate SATA bandwidth limits (around 500–550 MB/s), potentially introducing minor frame pacing stutters.
  • Mechanical Hard Drives (HDDs): HDDs handle continuous, predictable reads much better than sudden, random seek bursts. Checking "Close file when inactive" on an HDD setup often results in visible transition lag, audio desync, or black frames while the drive head physically repositions to reopen and read the asset.

Best Practices for Multi-Scene Setups

To balance disk read bandwidth and transition smoothness, apply the setting selectively rather than globally:

  • Leave unchecked for critical scene transitions (such as stinger transitions) and immediate overlay loops where even a 50ms buffer delay would cause a noticeable hitch.
  • Enable (check) for large background videos, pre-recorded segments, or long-form replay files residing in scenes visited infrequently throughout a broadcast.
  • Enable (check) if total concurrent scene playback threatens to saturate your storage bus or deplete system RAM.
