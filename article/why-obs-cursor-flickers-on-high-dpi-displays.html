Why OBS Cursor Flickers on High-DPI Displays

Cursor flickering during OBS Studio Display Capture on high-DPI Windows setups is primarily caused by synchronization conflicts between Windows Desktop Window Manager (DWM), display scaling layers, and OBS’s frame-grabbing APIs. When Windows applies non-integer DPI scaling (such as 125% or 150%), the operating system draws the mouse cursor on an independent hardware overlay plane, while OBS attempts to capture the desktop surface and composite the cursor simultaneously. This timing and coordinate mismatch between the desktop render thread and the cursor’s hardware sprite results in noticeable blinking or disappearing cursors.

DPI Scaling and Fractional Coordinate Mismatches

Windows scales user interfaces on 2K, 4K, and high-density monitors to maintain readability. When display scaling is set above 100%, Windows uses virtualized coordinates for desktop elements while rendering the cursor at physical pixel coordinates. OBS Studio's Display Capture source must reconcile these differences in real time. If the coordinate rounding introduces floating-point errors during frame compositing, the cursor can flicker between visible and invisible states across consecutive frames.

DXGI Desktop Duplication API Constraints

By default, OBS Studio utilizes Microsoft's DirectX Graphics Infrastructure (DXGI) Desktop Duplication API for classic Display Capture on Windows. Under DXGI, mouse cursor updates are treated as separate metadata containing the cursor image and position coordinates. The capture API relies on whether the cursor position has moved to trigger an update. When high-DPI scaling or variable refresh rates are involved, the API can intermittently fail to synchronize cursor buffer swaps with the desktop video frame buffer, causing the cursor layer to drop for individual frames.

Multi-Plane Overlays (MPO) and Hardware Acceleration

Modern GPU drivers use Multi-Plane Overlays (MPO) to render different parts of the screen—such as video playback and the mouse pointer—on separate hardware planes to save power and reduce latency. When OBS reads the desktop frame buffer, it may bypass or desynchronize from the specific hardware plane currently rendering the cursor. Furthermore, Windows Hardware-Accelerated GPU Scheduling (HAGS) alters how tasks are queued, sometimes prioritizing desktop responsiveness over the secondary capture pipeline, which exacerbates cursor frame drops.

Conflicting Capture Methods: DXGI vs. Windows Graphics Capture

The method selected within the Display Capture properties plays a significant role in this behavior. Older capture methods rely on DXGI Desktop Duplication, which composites the cursor manually inside OBS. In contrast, the modern "Windows 10 (1903 and up)" capture method uses the Windows Graphics Capture (WGC) API. The WGC API captures the rendered desktop natively through the DWM compositor, including the cursor directly in the visual stream. If a system defaults to DXGI on a high-DPI monitor, the manual sprite compositing is far more prone to flickering than the integrated WGC approach.

Multi-Monitor Refresh Rate and GPU Mismatches

When high-DPI displays are paired with secondary monitors running at different resolutions or refresh rates, DWM dynamically balances multiple display timers. If an application or the desktop cursor moves across rendering boundaries, the timing variance between OBS's target frame rate (e.g., 60 FPS) and the display's variable or high refresh rate (e.g., 144 Hz) causes phase alignment errors, resulting in the cursor repeatedly dropping in and out of the captured stream.
