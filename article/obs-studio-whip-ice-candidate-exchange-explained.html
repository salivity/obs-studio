OBS Studio WHIP ICE Candidate Exchange Explained

This article explains how the WebRTC HTTP Ingestion Protocol (WHIP) output implementation in OBS Studio manages Interactive Connectivity Establishment (ICE) candidate exchanges. It covers the signaling workflow driven by OBS Studio's underlying WebRTC stack, how local candidates are gathered and dispatched via HTTP POST requests, and how the standard accommodates trickle ICE scenarios to establish low-latency streaming sessions.

The Underlying Engine: libdatachannel

OBS Studio implements its WebRTC and WHIP capabilities using libdatachannel, an open-source, lightweight C/C++ WebRTC library. Rather than using the large, native Google WebRTC codebase, libdatachannel provides direct control over the media pipeline, connection state, and signaling lifecycle. This implementation defines how candidate gathering, network traversal, and signaling handshakes occur.

Initial Offer and Pre-Gathering (Vanilla ICE)

In traditional WebRTC signaling (such as WebSockets), implementations often rely heavily on "Trickle ICE," where candidates are discovered and sent one by one as they become available. WHIP, standardized under the IETF, uses standard HTTP semantics to simplify ingest infrastructure.

When you start streaming via WHIP in OBS Studio, the output handles ICE candidates primarily through non-trickle (Vanilla) ICE gathering:

  1. Local Gathering: Upon initiation, the WebRTC peer connection initializes and queries local network interfaces and any configured STUN/TURN servers.
  2. Buffering Candidates: OBS Studio waits for the local ICE gathering state to complete (or reach a usable threshold where host and reflexive candidates are identified).
  3. Bundling into the Offer: The gathered ICE candidates are appended directly into the local Session Description Protocol (SDP) offer string.
  4. HTTP POST Dispatch: OBS Studio sends this fully populated SDP offer as the payload of an HTTP POST request to the configured WHIP ingest URL with the Content-Type: application/sdp.

Media Server Response

Once the ingest server receives the HTTP POST request containing the SDP offer and all embedded ICE candidates, it processes the request:

  1. The server performs its own ICE candidate gathering.
  2. It generates an SDP answer containing its media capabilities and server-side ICE candidates.
  3. The server responds to OBS with an HTTP 201 Created status code containing the SDP answer in the response body.
  4. OBS Studio injects this SDP answer back into its peer connection instance.

At this point, both sides possess the complete candidate lists required to begin ICE connectivity checks (STUN binding requests/responses) directly over UDP. Once a valid candidate pair succeeds, the DTLS handshake completes, and media transmission begins.

Trickle ICE via HTTP PATCH

While gathering candidates prior to sending the HTTP POST avoids complex state management, the WHIP specification also defines support for Trickle ICE to minimize connection startup latency.

When Trickle ICE is active:

  • OBS sends an initial SDP offer with minimal or no candidates to the WHIP resource endpoint via HTTP POST.
  • The server responds with 201 Created and provides a specific URL in the HTTP Location header representing the session resource.
  • As new candidates are discovered by OBS Studio, it sends an HTTP PATCH request targeting that session URL.
  • The PATCH payload uses the application/trickle-ice-sdpfrag content type, transmitting individual candidate fragments as they are discovered.

Failure Handling and Restarts

If network conditions change or the initial candidate pair fails to establish connectivity, the WHIP protocol defines ICE restarts through subsequent HTTP requests. OBS Studio tears down or renegotiates the session by issuing updated offers to the resource URL, regenerating candidate lists to restore the media path without requiring a manual reconfiguration of the broadcast settings.
