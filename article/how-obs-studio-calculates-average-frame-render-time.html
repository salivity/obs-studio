How OBS Studio Calculates Average Frame Render Time

This article explains how OBS Studio calculates the "Average time to render frame" metric shown in its native Stats dock. OBS Studio determines this value by recording high-resolution timestamps during the video compositing cycle on the graphics thread, isolating GPU rendering duration from encoding and capture delays, and dividing the total rendering time by the number of frames processed within a rolling sampling window. The following breakdown details the timing mechanisms, the components included in the measurement, the mathematical averaging process, and the practical significance of this metric.

High-Resolution Timing on the Graphics Thread

OBS Studio relies on platform-specific, high-precision system clocks (such as QueryPerformanceCounter on Windows or clock_gettime(CLOCK_MONOTONIC) on Linux) accessed internally via its utility function os_gettime_ns().

The measurement process occurs exclusively on the internal graphics rendering thread (obs_graphics_thread). For every target video frame:

  1. Start Timestamp: Immediately before OBS begins traversing the active scene graph, it takes a nanosecond-precision start timestamp.
  2. Scene Composition: The graphics subsystem processes all active video sources, calculates transformations, applies shaders, evaluates filters, and composites the final image onto the rendering surface.
  3. End Timestamp: Once GPU commands for drawing the entire frame have been dispatched and the frame composition finishes, a second timestamp is captured.
  4. Delta Calculation: The elapsed time for that single frame is calculated as delta = end_time - start_time.

What the Render Time Measures

The frame render metric strictly measures the scene composition phase. It does not measure the entire lifetime of a video frame.

  • Included: GPU texture updates, source transitions, color format conversions, canvas scaling, shader execution, filter rendering (such as color grading, chroma keying, and masks), and scene composition.
  • Excluded: Audio processing, video encoding (handled asynchronously by software encoders like x264 or hardware encoders like NVENC/AMF), network packet transmission, capture card hardware latency, and vertical synchronization (vsync) delays.

The Averaging Algorithm

Rather than displaying the instantaneous render time—which fluctuates significantly frame-by-frame and would make the user interface unreadable—OBS computes an accumulated average across its UI refresh interval:

  1. Accumulation: OBS maintains cumulative variables for total nanoseconds spent rendering and the total count of successfully rendered frames.
  2. Periodic Sampling: The native Stats dock updates on a fixed interval (typically once per second). When updating, OBS takes the accumulated render time (in nanoseconds) and divides it by the total frames rendered during that interval.
  3. Unit Conversion: The resulting value is converted from nanoseconds to milliseconds (ms = nanoseconds / 1,000,000.0) and displayed to two decimal places in the Stats dialog.
  4. Reset: Once polled, the counters reset or shift their sampling window to prepare for the next statistical cycle.

Performance Significance and the Frame Budget

The average render time reveals how close OBS is to overloading the GPU. To maintain a consistent framerate without dropping rendering frames, the average time must remain strictly below the frame budget defined by the canvas framerate:

  • 60 FPS: 16.67 ms frame budget
  • 30 FPS: 33.33 ms frame budget
  • 120 FPS: 8.33 ms frame budget

If the rendering time approaches or exceeds the frame budget, the graphics thread cannot finish composition before the next scheduled frame tick, resulting in the "Frames missed due to rendering lag" counter incrementing.
