Why OBS Hangs on Shutdown Waiting for Network Sockets

When OBS Studio hangs indefinitely during shutdown while waiting for background network sockets to close, it is typically caused by blocking network operations, misbehaving third-party plugins, or frozen streaming connections failing to complete their termination handshakes. In this state, the core OBS process attempts to gracefully terminate all active threads, but a thread stuck waiting for an unfulfilled TCP teardown or an unresponsive remote server prevents the application from exiting cleanly.

Blocking Sockets and Protocol Handshakes

The most common cause relates to how protocols like RTMP, RTMPS, and SRT handle session termination. When you stop a stream or close the software, OBS issues a teardown signal to the remote ingest server (such as Twitch, YouTube, or a custom RTMP destination). If the network connection is unstable, packets are dropped, or the remote server stops responding, the active socket can remain stuck in a blocking state waiting for an acknowledgment (such as a TCP FIN or RST packet, or an SSL_shutdown() confirmation). Because the underlying network call is synchronous and lacks a short, enforced timeout, the thread sleeps indefinitely.

Thread Deadlocks During Cleanup

OBS Studio utilizes a multithreaded architecture where the main interface thread coordinates shutdown by joining background worker threads. When shutting down:

  1. The main thread signals audio, video, and output threads to terminate.
  2. The main thread calls a blocking join (such as pthread_join or Windows WaitForSingleObject) to ensure all data has safely flushed before freeing memory.
  3. If the output thread is blocked indefinitely inside a socket cleanup function, it never signals completion.
  4. This results in a deadlock where the main thread refuses to exit until the socket thread completes, and the socket thread cannot complete until the network stack returns an error.

Third-Party Plugins and WebSockets

Third-party extensions, particularly those relying on persistent network connections (such as NDI plugins, custom stream deck integrations, telemetry tools, or older versions of obs-websocket), often manage their own asynchronous networking threads. If these plugins do not implement proper cancellation tokens or fail to hook into the OBS shutdown event cleanly, their background worker threads can keep active TCP sockets open, trapping the application in an endless wait loop.

CEF and Browser Source Sockets

OBS embeds the Chromium Embedded Framework (CEF) to render browser sources like chat overlays, alerts, and web pages. Browser sources frequently open persistent WebSockets or WebRTC connections. If an embedded webpage fails to tear down its open socket or if the CEF sub-process fails to respond to the host termination signal, OBS will hang while waiting for the inter-process communication (IPC) and associated network handles to release.

Security Software and Network Intermediaries

Antivirus suites, third-party firewalls, and VPN adapters frequently inspect outgoing and incoming network packets at the kernel level. In some instances, these security tools intercept or drop socket termination packets, preventing the operating system's network stack from delivering the final closure state to OBS. Without receiving a connection reset or timeout signal from the OS, the socket remains permanently open in the background.
