How OBS Studio Logs RTMPS SSL Parameters

This article explains how OBS Studio captures and records SSL/TLS negotiation parameters when establishing an encrypted Real-Time Messaging Protocol (RTMPS) stream. When connecting to an RTMPS endpoint, OBS Studio delegates cryptographic handshakes to underlying security libraries such as mbedTLS or OpenSSL, funneling critical negotiation parameters—including TLS protocol versions, cipher suites, and certificate validation statuses—directly into the application's runtime log system.

The Underlying TLS Architecture

OBS Studio handles live RTMP/RTMPS broadcasting primarily through its obs-outputs module. When connecting to an rtmps:// URL on port 443, the application establishes a TCP socket and initiates a Transport Layer Security (TLS) handshake before transmitting RTMP packets.

Depending on the operating system and compile-time configurations, OBS Studio typically utilizes mbedTLS or OpenSSL as its cryptographic backend. The communication between the TLS library and OBS Studio's internal logging framework (blog()) is managed via diagnostic callbacks. When the handshake process begins, the cryptographic library communicates state changes and negotiation metadata back to the application.

Logged Negotiation Parameters

During standard operation, OBS Studio records the macroscopic state of the connection to keep log sizes manageable. When the TLS layer executes, the following parameters are processed and selectively written to the log:

  • Protocol Version: The negotiated TLS version (e.g., TLSv1.2 or TLSv1.3). If a server fails to negotiate a mutually supported version, a protocol mismatch error is explicitly logged.
  • Cipher Suite: The specific key exchange, bulk cipher, and message authentication algorithms selected for the session (e.g., TLS_AES_256_GCM_SHA384 or ECDHE-RSA-AES128-GCM-SHA256).
  • Certificate Verification Status: Information regarding server identity verification. This includes whether the peer certificate is valid, expired, self-signed, or untrusted according to the system's root certificate store.
  • Handshake Completion or Failure Codes: Success messages confirming the socket upgrade to TLS, or standard alert codes (such as UNKNOWN_CA, HANDSHAKE_FAILURE, or DECRYPT_ERROR) if the negotiation fails.

Standard Logging vs. Verbose Logging

By default, OBS Studio operates at an informational log level (LOG_INFO). In this mode, successful handshakes often appear as succinct status entries confirming that a secure connection has been established to the target host and port. Granular details, such as intermediate certificate chain resolution and specific cipher negotiation steps, are retained at lower log levels to prevent log bloat.

To log comprehensive TLS parameters:

  1. Launch OBS Studio via command line using the --verbose flag (e.g., obs64.exe --verbose on Windows).
  2. The --verbose flag elevates internal log levels to LOG_DEBUG, instructing the underlying TLS callbacks to dump exact handshake states, record-layer details, and supported client-versus-server cipher comparisons.

Locating and Inspecting the Logs

Log entries generated during the RTMPS connection attempt are written to standard plain-text files.

  • In OBS Studio, open Help > Log Files > View Current Log (or View Previous Log).
  • Alternatively, navigate directly to the application data directory:
    • Windows: %APPDATA%\obs-studio\logs
    • macOS: ~/Library/Application Support/obs-studio/logs
    • Linux: ~/.config/obs-studio/logs

Within the log file, search for [rtmp stream: 'adv_stream'] or [rtmp stream: 'simple_stream'] followed by Connecting to RTMP URL. Handshake negotiations, TLS alerts, or library-specific diagnostic lines will appear immediately after the TCP connection confirmation.
