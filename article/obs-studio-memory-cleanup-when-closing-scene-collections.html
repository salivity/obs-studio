OBS Studio Memory Cleanup When Closing Scene Collections

When you close or switch away from a heavily filtered scene collection without quitting OBS Studio, the application executes a structured teardown process to release both system RAM and GPU VRAM. By utilizing an internal reference-counting model across its core framework (libobs), OBS systematically unloads active render pipelines, destroys filter chains, and signals the operating system and graphics drivers to release hardware resources. While the teardown triggers immediate deallocation instructions within the software, the actual observed memory footprint depends on how external drivers, third-party plugins, and the OS memory manager handle deferred reclamation.

Reference Counting and Source Destruction

OBS Studio treats every scene, source, and filter as an obs_source_t object. Filters operate as child sources attached to parent sources within a linked list. When a scene collection is closed:

  1. Hierarchy Teardown: OBS traverses the scene graph, detaching filters from their respective sources and sources from their scenes.
  2. Reference Decrementing: The software invokes obs_source_release on every object in the collection. This decrements the object's reference counter.
  3. Destruction Callback: Once an object's reference count drops to zero, libobs calls the internal destroy function specific to that source or filter type. This stops processing threads, halts asynchronous video rendering ticks, and frees the source's memory allocation.

GPU Memory (VRAM) Reclamation

Heavily filtered collections consume significant video memory due to intermediate render targets, dynamic textures, and custom shaders (e.g., blur passes, color grading LUTs, scaling masks). During collection closure:

  • Render Target Deletion: OBS calls graphics subsystem wrappers (such as gs_texture_destroy and gs_stagesurf_destroy) to release Direct3D 11, OpenGL, or Metal textures assigned to offscreen render passes.
  • Shader Pipeline Flushes: Active filter shaders are unbound from the rendering context. Shaders shared across the core engine may remain cached, but instance-specific parameters, constant buffers, and framebuffers are purged.
  • Driver Caching: Although OBS marks these graphics contexts for deletion, graphics drivers (NVIDIA, AMD, or Intel) may not immediately return the VRAM to the global pool. The driver frequently retains allocated memory blocks to minimize reallocation latency for incoming tasks.

System RAM and CPU Cleanup

Filters that process audio, perform software-based compositing, or utilize CPU-driven machine learning (such as background removal) allocate substantial system memory. When the collection closes:

  • Buffer Deallocation: Frame buffers, audio ring buffers, and worker queues are deallocated using internal memory utilities (bfree).
  • Plugin Teardown: Native plugins release their dynamically allocated data structs and terminate associated background worker threads.
  • C-Runtime Behavior: Even after OBS frees heap memory, the C-runtime memory allocator (or OS virtual memory manager) might hold onto the committed pages rather than returning them to physical RAM instantly. This explains why Task Manager or Activity Monitor may show a delayed or partial reduction in RAM usage until the memory is actively requested by another process.

Third-Party Plugin Leaks

The reliability of memory reclamation heavily relies on filter implementation. Core OBS Studio filters (such as Chroma Key, Color Correction, and Scaling) cleanly destroy all allocations. However, third-party plugins—particularly those utilizing external AI frameworks or unmanaged code—may fail to properly implement the destroy callback. In such cases, dangling pointers or orphaned threads can cause persistent memory leaks that remain resident in system memory until the OBS application is completely restarted.
