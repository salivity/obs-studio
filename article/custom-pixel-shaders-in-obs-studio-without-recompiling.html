Custom Pixel Shaders in OBS Studio Without Recompiling

Custom pixel shaders can be injected directly into the OBS Studio rendering graph without modifying or recompiling the core application codebase. This is achieved either through existing shader filter plugins that expose runtime HLSL/GLSL compilation to end users, or by developing a custom dynamic plugin leveraging the libobs API. By utilizing dynamic link libraries and the built-in graphics subsystem, developers and creators can insert custom rendering passes into individual sources, scenes, or global video output pipelines seamlessly.

The OBS Studio Graphics Architecture

OBS Studio relies on libobs, an underlying C library responsible for the core engine, media pipelines, and graphics abstraction layer. The graphics subsystem (gs) abstracts DirectX 11 on Windows and OpenGL/Metal on POSIX systems.

Rendering in OBS is executed as a scene graph. Each visual element—whether an image, capture card, or scene—is treated as an obs_source. Sources can be extended using filters. During the video render loop, OBS traverses this graph and calls the render function for each source and its associated filters, allowing custom draw calls and shader effects to manipulate pixel buffers at runtime.

Method 1: Using Runtime Shader Filter Plugins

For immediate injection without coding a custom C plugin, users can utilize modular dynamic plugins such as obs-shaderfilter.

  • Mechanism: These plugins register a generalized filter with OBS that loads plain text .shader or .hlsl files at runtime.
  • Execution: The plugin exposes a user interface in OBS where shader parameters (uniforms, float variables, colors) can be modified on the fly.
  • Compilation: When a file is loaded or modified, the plugin passes the raw text to the graphics subsystem, compiling the pixel shader dynamically without interrupting the live stream or requiring a software restart.

Method 2: Native Dynamic Plugin Development (libobs)

For advanced use cases requiring custom textures, complex multi-pass rendering, or programmatic control, developers can build a standalone dynamic library (.dll, .so, or .dylib) using the OBS Studio plugin API.

  1. Implement an OBS Source Filter: Create a standard plugin and define an obs_source_info structure with the source type set to OBS_SOURCE_TYPE_FILTER and output capabilities set to OBS_SOURCE_VIDEO.

  2. Load Custom Effect Files: OBS uses an effect framework modeled after Direct3D Effects (.effect files), which bundle vertex shaders, pixel shaders, sampling states, and techniques. Use the internal graphics API to compile the shader from memory or disk:

    gs_effect_t *custom_effect = gs_effect_create_from_file("path/to/custom_shader.effect", NULL);

  3. Render Hooking: In the filter’s video_render callback, execute the rendering pass. The typical implementation targets the parent source texture, passes it into your custom pixel shader as a sampler parameter, and draws a screen-aligned quad:

    gs_eparam_t *image_param = gs_effect_get_param_by_name(custom_effect, "image");
gs_effect_set_texture(image_param, obs_source_get_texture(obs_filter_get_target(filter)));

while (gs_effect_loop(custom_effect, "DrawTechnique")) {
    obs_source_process_filter_draw(filter, custom_effect, width, height, GS_RGBA);
}

  4. Dynamic Deployment: Compile the code into a shared binary and place it in the OBS plugin directory. OBS automatically loads it during startup via obs_load_all_modules().

Through either user-facing shader loaders or the modular libobs API, custom pixel shaders execute directly on the GPU within the main OBS composition graph while leaving the base application fully untouched.
