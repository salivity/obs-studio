FTL vs RTMP Handshake Differences in OBS Studio

This article compares the network handshake protocols of standard RTMP and the Faster Than Light (FTL) protocol within OBS Studio forks. While standard RTMP establishes an all-TCP, multi-phase byte exchange followed by Action Message Format (AMF) control packets, FTL utilizes a dual-channel architecture consisting of a lightweight TCP control handshake with cryptographic verification that provisions a UDP-based Real-Time Transport Protocol (RTP) pipeline. Understanding these fundamental handshake variations explains why FTL achieves sub-second latency while RTMP remains tied to higher-overhead transmission pipelines.

Transport Layer Architecture

The fundamental difference between RTMP and FTL begins at the transport layer of the OSI model:

  • RTMP: Operates entirely over a single TCP connection (typically port 1935). The handshake, stream control, and media transmission share this reliable, ordered byte stream.
  • FTL: Employs a hybrid transport architecture. It initiates a TCP connection (typically port 8084 or 7984) strictly as a control and signaling channel, while actual audio and video data travel independently over UDP using RTP.

Because RTMP encapsulates everything in TCP, its handshake binds the client and server to TCP's window sizing, congestion avoidance, and acknowledgment loops from the outset. FTL's handshake uses TCP only long enough to authenticate and negotiate parameters before switching media ingestion to UDP, eliminating head-of-line blocking.

The Standard RTMP Handshake Sequence

The RTMP handshake consists of a predefined, non-negotiated exchange of raw byte packets labeled C0/S0, C1/S1, and C2/S2:

  1. Packet C0 and S0: The client sends a single byte (C0) specifying the requested RTMP version (typically 0x03). The server replies with S0, confirming the version.
  2. Packet C1 and S1: The client transmits C1 (1,536 bytes), containing an epoch timestamp, a zeroed field, and 1,528 bytes of random data. The server acknowledges and sends S1, which contains its own timestamp and 1,528 random bytes.
  3. Packet C2 and S2: The client mirrors the random data from S1 back to the server in C2. The server mirrors the data from C1 back to the client in S2.

Once this byte-level exchange completes, the connection is considered established. However, the client must then send an application-level connect command formatted in Action Message Format (AMF0/AMF3), wait for a _result response, issue a createStream command, and finally send a publish command before any media transmission can occur. This requires multiple Round Trip Times (RTT) over TCP.

The FTL Protocol Handshake Sequence

FTL bypasses the fixed-byte structure of RTMP in favor of a text- and JSON-based command-response sequence over its TCP control connection:

  1. TCP Connection & Version Check: The OBS client connects to the ingest server and sends an initial string handshake containing the protocol version (e.g., FTL/0.2).
  2. HMAC-SHA256 Challenge-Response: Unlike RTMP, which passes stream keys as plain text query parameters or inside AMF objects, FTL integrates secure authentication directly into the handshake. The server transmits a cryptographic salt/challenge to the client. The client hashes its stream key with this salt using HMAC-SHA256 and sends the response back to the server.
  3. Port and Payload Negotiation: Once authenticated, the server returns configuration data, including an assigned UDP destination port and designated Dynamic Payload Types (such as H.264 for video and Opus for audio).
  4. RTP/SRTP Initialization: The OBS fork completes the TCP negotiation and immediately binds an outbound UDP socket. Media frames are wrapped in RTP headers containing synchronized timestamps and Sequence Numbers, then fired directly to the server-assigned UDP port without requiring acknowledgment handshakes for each packet.

Authentication Timing and Stream Initialization

The placement of the authentication step highlights a key architectural divergence:

  • In RTMP, authentication is decoupled from the network transport handshake. The three-way packet handshake (C0–C2) must finish successfully before the client can transmit authentication credentials inside the AMF-encoded connect or publish payload. If the key is invalid, the TCP connection closes only after multiple round trips have already elapsed.
  • In FTL, authentication is native to the control handshake. The control channel serves as an explicit gatekeeper: unless the cryptographic challenge is resolved, the server never opens or allocates a UDP port for media ingestion.

Network Overhead and Startup Latency

RTMP’s multi-phase setup introduces substantial startup latency. Between the underlying TCP three-way handshake (SYN, SYN-ACK, ACK), the raw RTMP handshake (C0/C1/C2), and the subsequent AMF commands (connect, createStream, publish), RTMP typically requires at least 4 to 6 round trips before transmitting the first audio/video chunk.

By comparison, FTL consolidates signaling into a brief request-response exchange over TCP and immediately transitions media to UDP. By decoupling media transmission from TCP state management, FTL avoids the initial buffering requirements and connection latency inherent in standard RTMP implementations in OBS Studio.
