AOM-AV1 Multi-Socket CPU Tile Distribution in OBS

This article examines how the AOM-AV1 (libaom) software encoder in OBS Studio splits video frames into tiles and manages workloads across high-core-count, multi-socket CPU systems. It details the underlying tile-threading model, the impact of row-based multithreading, how Non-Uniform Memory Access (NUMA) architectures influence performance, and how operating system schedulers handle the cross-socket encoding pipeline.

AV1 Tile Architecture and Thread Partitioning

The AV1 video standard divides each frame into a rectangular grid of independently decodable and encodable regions known as tiles. In the reference AOM-AV1 implementation used by OBS Studio, tile boundaries eliminate intra-prediction dependencies across tile edges during the initial transform and quantization phases.

Tile allocation is controlled logarithmically via encoder parameters:

  • tile-columns: Divides the frame horizontally into \(2^N\) columns.
  • tile-rows: Divides the frame vertically into \(2^N\) rows.

For example, a configuration with --tile-columns=2 and --tile-rows=1 divides the frame into 8 discrete tiles (4 columns by 2 rows). Each tile can be assigned to a separate worker thread within the encoder's thread pool.

Thread Allocation and Row-Based Multithreading

When OBS Studio initializes the AOM-AV1 encoder, it exposes the standard threads parameter alongside tile options. By default, pure tile-based multithreading limits the maximum parallel worker count to the number of defined tiles. If a system features 64 or 128 logical cores across two sockets, defining only 4 or 8 tiles leaves the vast majority of execution units idle.

To mitigate this, AOM-AV1 integrates row-based multithreading (row-mt=1). Row multithreading allows multiple threads to work on different block rows within the same tile concurrently, provided the top-right block dependencies have completed processing. Consequently, the encoder can effectively scale across dozens of logical threads even when the frame is partitioned into a modest number of physical tiles.

Multi-Socket and NUMA Distribution Dynamics

High-core-count, multi-socket systems use Non-Uniform Memory Access (NUMA). In these environments, memory local to Socket 0 exhibits significantly lower latency and higher bandwidth to Socket 0 cores than to Socket 1 cores.

AOM-AV1 within OBS Studio does not natively pin worker threads to specific NUMA domains or allocate tile memory strictly within local NUMA nodes:

  1. OS Thread Scheduling: The distribution of worker threads across multiple sockets is deferred to the operating system's thread scheduler (such as the Windows thread scheduler or the Linux Completely Fair Scheduler).
  2. Memory Shared State: While tiles are mathematically independent during block-level encoding, all worker threads must read from common reference frame buffers stored in system RAM. On a multi-socket machine, threads running on Socket 1 accessing reference buffers initially allocated in Socket 0’s memory bank must transfer data over the inter-socket interconnect (AMD Infinity Fabric or Intel Ultra Path Interconnect).
  3. In-Loop Filtering Synchronization: Once all tiles in a frame finish encoding, AV1 applies in-loop filtering—consisting of the deblocking filter, Constrained Directional Enhancement Filter (CDEF), and Loop Restoration. These stages often require cross-tile coordination, creating synchronization barriers where threads on all sockets must wait for the slowest tile to complete before updating reference frames for subsequent pictures.

Windows Processor Group Constraints

On Windows systems, the OS organizes machines with more than 64 logical processors into multiple Processor Groups. Standard Win32 applications that are not explicitly group-aware will assign threads to a single processor group by default.

Unless OBS Studio and its underlying libaom build are compiled with support for assigning threads across multiple processor groups, AOM-AV1 encoding threads may remain restricted to a single socket or single group of 64 logical cores. On Linux, the scheduler inherently spans threads across all available NUMA nodes without processor group boundaries, though cross-node memory latencies still apply.

Optimizing Distribution via OBS Custom Parameters

Because OBS Studio exposes custom parameter inputs for the AOM-AV1 encoder, users on high-core-count systems can optimize tile distribution manually. In the encoder settings, custom parameters can be supplied via the aom-params field:

  • Increase Tile Counts: Setting tile-columns=2 or tile-columns=3 (giving 4 to 8 columns) and tile-rows=1 (giving 2 rows) ensures that there are enough distinct tasks to distribute across broad core clusters.
  • Enable Row Multithreading: Ensuring row-mt=1 is active enables fine-grained parallel processing within each tile.
  • Thread Sizing: Setting threads to match the target logical core allocation prevents the thread pool from defaulting to conservative, low-core profiles.

For optimal NUMA efficiency on multi-socket servers, system administrators often use external tools (such as numactl on Linux or process affinity utilities on Windows) to restrict the entire OBS Studio process to a single physical socket, avoiding cross-interconnect synchronization penalties entirely.
