How OBS Studio Calculates Timestamps for VFR Sources

OBS Studio manages variable frame rate (VFR) sources by decoupling input ingestion from its internal rendering pipeline, converting irregular incoming frames into a predictable, constant frame rate (CFR) output. When sources deliver frames at fluctuating intervals, OBS buffers these inputs, synchronizes them against a high-resolution monotonic master clock, and samples the most appropriate frame during each scheduled compositing tick. The final presentation timestamp (PTS) assigned to the composited frame is generated directly by OBS Studio's internal render loop, ensuring the downstream video encoder receives strictly monotonic, evenly spaced timestamps regardless of input variance.

The Monotonic Master Clock and Render Cadence

OBS Studio relies on a central monotonic time provider (os_gettime_ns) to coordinate audio and video subsystems. While sources may emit frames with varying delays or native presentation timestamps, the OBS video rendering thread runs on a rigid, predetermined interval defined by the user’s canvas settings (for example, 16.666 milliseconds for 60 FPS).

This fixed interval establishes the cadence for the compositing engine. The render thread periodically awakens at defined tick boundaries. The presentation timestamp of the final composited frame is tied to this render clock rather than the raw timestamps delivered by individual capture devices or media decoders.

Ingestion and Timestamp Normalization

When a VFR source—such as a smartphone camera, window capture, or media file—delivers a video frame to OBS, it arrives inside an obs_source_frame struct containing its source-generated timestamp. OBS immediately converts or maps this incoming timestamp to the unified engine timeline:

  1. Clock Drift and Alignment: OBS assesses the source's arrival time relative to the master clock. If a source provides hardware-level timestamps, OBS normalizes them to prevent drift relative to system audio.
  2. Buffering: Ingested frames enter a circular queue or state cache for that specific source. Because the source is variable, intervals between arrivals may be shorter or longer than the compositor's tick rate.

Frame Selection During Compositing

When the video render loop triggers at target time \(T\), OBS walks the active scene graph to draw each source. For every VFR source, OBS evaluates the buffered frames to choose which visual data to composite:

  • Frame Evaluation: OBS checks the timestamps of queued frames against the current rendering timestamp \(T\).
  • The Nearest Valid Frame: The compositor selects the most recent frame whose adjusted timestamp is less than or equal to \(T\) (\(PTS_{source} \le T\)).
  • Frame Dropping: Any older frames lingering in the source queue that were superseded before the current render tick are discarded without being drawn. This prevents latency accumulation when a source temporarily spikes above the target frame rate.
  • Frame Duplication: If the VFR source has not delivered a new frame since the last tick (a frame drop or low-framerate dip), OBS retains and redraws the last rendered frame.

Output PTS Generation for Encoders

Once all active sources are sampled and blended onto the rendering canvas, the frame is complete. OBS does not pass individual source PTS metadata to the output pipeline. Instead, the composited frame is stamped with a newly generated output presentation timestamp.

The output PTS represents the exact tick index multiplied by the canvas timebase:

\[\text{PTS} = \text{Frame Count} \times \text{Frame Duration}\]

This calculation guarantees that downstream hardware or software encoders receive an uninterrupted CFR stream. Even if a VFR source stutters, drops to 5 FPS, or surges to 120 FPS, OBS Studio’s frame presentation timestamps remain strictly uniform and synchronized with system audio.
