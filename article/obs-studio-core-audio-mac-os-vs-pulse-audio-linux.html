OBS Studio: CoreAudio macOS vs PulseAudio Linux

This article examines the architectural differences in how OBS Studio interfaces with CoreAudio on macOS compared to PulseAudio on Linux. It outlines how OBS interacts with these systems, focusing on client-server design versus direct hardware abstraction, threading models, buffer handling, latency management, and the operating-system-level constraints that dictate how digital audio reaches the OBS mixing engine.

System Topology and Transport Layers

The fundamental divergence between CoreAudio and PulseAudio in OBS Studio lies in the distance between OBS and the hardware.

On macOS, OBS Studio utilizes CoreAudio’s Hardware Abstraction Layer (HAL) and AudioUnit APIs. CoreAudio operates as an in-process, direct-link subsystem. Audio input from microphones or system audio taps runs through the system's AudioComponent pipeline, where the driver directly executes synchronous audio processing callbacks. There is no intermediary sound server; OBS registers input procedures directly within the process space that interfaces with the kernel-level audio drivers.

On Linux, OBS Studio interfaces with PulseAudio as a client to a user-space sound server daemon. The OBS PulseAudio plugin (linux-pulseaudio) links against libpulse. Audio does not travel straight from the kernel (ALSA) into OBS. Instead, the kernel sends data to the PulseAudio daemon, which processes, mixes, and transfers the stream across a local Unix domain socket using asynchronous Inter-Process Communication (IPC) and shared memory (shm) blocks into the OBS process.

Threading and Execution Models

CoreAudio relies on dedicated, high-priority real-time I/O threads managed by the macOS kernel. When an input device has samples available, CoreAudio invokes an AudioDeviceIOProc callback on this high-priority thread. OBS Studio must process or copy these raw PCM buffers immediately to prevent an audio drop (overrun/underrun). OBS handles this by doing minimal work in the callback: it reads the AudioBufferList and immediately pushes the data into its internal circular ring buffers (circlebuf).

PulseAudio relies on an event-driven mainloop architecture. OBS typically implements the pa_threaded_mainloop to interact with the PulseAudio API. The thread runs a poll-based event loop where state changes, buffer requests, and data receipts are processed asynchronously. Instead of being dictated by hardware clocks, data delivery depends on the scheduling of both the PulseAudio daemon and the client thread. When the stream is readable, a callback (pa_stream_read) is triggered to retrieve pointers to the shared memory region containing the audio samples.

Latency Management and Clocking

CoreAudio uses strict hardware clock-driven synchronization. Latency is configured by setting buffer frame sizes directly on the hardware device via properties like kAudioDevicePropertyBufferFrameSize. Because the CoreAudio thread is driven by the physical hardware interrupt, clock drift between physical capture devices and OBS is minimal and deterministic, provided the sample rates match.

PulseAudio employs timer-based scheduling (tsched), popularized in modern desktop Linux. Instead of relying purely on regular hardware interrupts, PulseAudio programs system timers to wake up the system dynamically when buffers need servicing. OBS requests latency characteristics through target buffer metrics (pa_buffer_attr), such as maxlength, tlength, and fragsize. The actual latency varies dynamically based on system load and scheduler latency, requiring OBS to actively monitor stream timing to correct for clock drift relative to its internal video presentation timestamps.

System Audio Capture and Sandboxing

Capturing desktop/application audio highlights a major architectural split between the two platforms:

  • macOS (CoreAudio): CoreAudio does not natively provide a default loopback or "monitor" device for output audio due to macOS security and privacy models. Modern OBS versions on macOS capture desktop audio either through high-level ScreenCaptureKit APIs (which wrap CoreAudio application audio routing) or require a virtual CoreAudio HAL plugin (such as an aggregate device or virtual sound driver). Modern macOS also strictly requires user entitlement checks and TCC (Transparency, Consent, and Control) approvals to execute CoreAudio capture threads.
  • Linux (PulseAudio): PulseAudio natively abstracts every sink (output) with a corresponding "monitor source." OBS Studio queries the server via introspection routines (pa_context_get_source_info_list) and captures full desktop audio simply by connecting a recording stream (pa_stream_connect_record) directly to the target sink's monitor. No external drivers, aggregate devices, or specialized permissions are required to route desktop outputs into OBS.

Resampling and Format Negotiation

OBS Studio's internal audio pipeline operates using 32-bit floating-point planar PCM data at a user-defined sample rate (typically 44.1 kHz or 48 kHz).

Under CoreAudio, OBS requests native input formats via the AudioStreamBasicDescription (ASBD) structure. CoreAudio can perform in-process, high-quality sample rate conversion and channel mapping automatically via an AudioConverter unit before the data reaches the OBS internal buffer, minimizing CPU overhead while maintaining sample accuracy.

Under PulseAudio, the audio stream format is negotiated using pa_sample_spec. If the source hardware format does not match what OBS requests, the PulseAudio server daemon performs the resampling, channel mixing, and format conversion prior to transmitting the stream over IPC to OBS. While this centralizes processing, it can introduce additional CPU overhead at the daemon level unless explicitly bypassed via pass-through configurations or matching sample rates.
