How OBS Studio Handles Multiple WebSocket Requests

This article provides an overview of how OBS Studio manages simultaneous WebSocket connections and API requests coming from multiple third-party control surfaces, such as Elgato Stream Decks, Touch Portal, and Loupedeck consoles. It explores the underlying network architecture, thread synchronization mechanisms, event broadcasting, and conflict resolution strategies that ensure stability and data integrity across all connected devices.

Underlying WebSocket Architecture

Since OBS Studio version 28, the obs-websocket plugin has been integrated natively into the core application. The server runs on a dedicated network thread using an asynchronous I/O model (powered by modern C++ networking libraries like asio). Each connected control surface maintains its own persistent TCP socket and independent authentication session. Because network I/O is decoupled from the rendering pipeline, high-frequency network activity from multiple controllers does not inherently degrade video capture or encoding frame rates.

Request Ingestion and Queueing

When multiple control surfaces send commands simultaneously—such as two devices attempting to switch scenes, toggle filters, or adjust audio levels at the exact same millisecond—the WebSocket server ingests these requests asynchronously:

  1. Independent Sockets: Each controller's payload is received and framed independently on the network thread.
  2. Message Parsing: JSON-RPC-style payloads are validated and parsed into internal command structures.
  3. Dispatch to Core: Once validated, commands are scheduled for execution against the core OBS API.

Thread Synchronization and OBS Core Safety

While network ingestion is asynchronous and concurrent, OBS Studio's internal state management relies on strict thread safety. Many operations—such as scene switching, audio source modifications, and output controls—must interact directly with the OBS main thread or invoke internal synchronization primitives (mutexes):

  • Serialized State Modification: Operations affecting the scene graph or rendering pipeline are marshaled onto the main OBS thread or guarded by locks. This serializes state changes, ensuring that conflicting requests are executed sequentially rather than concurrently.
  • Deterministic Execution: The command that secures the lock or arrives at the processing queue first is executed first. The subsequent command executes immediately afterward against the newly updated state.

Conflict Resolution Example

If Controller A sends a request to switch to "Scene 1" at the exact same moment Controller B requests a switch to "Scene 2", the execution operates on a strict first-come, first-served basis:

  • The first command to be dequeued triggers the transition to Scene 1.
  • The second command is evaluated immediately following the first. Depending on whether a transition is already locked in progress, the second request will either trigger a secondary transition to Scene 2 or return an operational error (such as an active transition collision) back to Controller B.

Real-Time Event Broadcasting

To keep all control surfaces synchronized, obs-websocket uses an event-driven pub/sub architecture. Whenever a command alters the state of OBS Studio, the system fires an internal event. The WebSocket server captures this event and broadcasts it over every open connection that subscribed to that event category.

For instance, if a user mutes a microphone using a physical button on a Stream Deck:

  1. The Stream Deck sends the SetInputMute request.
  2. OBS updates the audio state.
  3. The server broadcasts an InputMuteStateChanged event to all connected devices.
  4. Touch Portal, MIDI controllers, and any secondary software interfaces immediately update their visual state to reflect the mute, preventing desynchronization across surfaces.
