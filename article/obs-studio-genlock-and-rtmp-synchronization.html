OBS Studio Genlock and RTMP Synchronization

This article examines how OBS Studio achieves synchronized multi-camera playback from disparate remote RTMP feeds with varying network latencies. While traditional broadcasting relies on hardware-based genlock pulses, OBS Studio uses an internal software presentation clock, jitter buffering, and frame-rate adaptation to normalize multiple asynchronous inputs onto a unified rendering canvas.

The Myth of Hardware Genlock in Software Streaming

Traditional broadcast genlock relies on a master reference generator transmitting an analog black burst or digital tri-level sync signal over SDI cables to align camera frame intervals down to the microsecond. Remote RTMP (Real-Time Messaging Protocol) feeds operating over public TCP/IP networks cannot receive an external hardware genlock signal. Instead, OBS Studio replaces hardware synchronization with a software-defined presentation pipeline that forces unpredictable network streams to conform to a fixed internal frame rate.

The OBS Master Clock Architecture

OBS Studio decouples input frame capture from output canvas rendering. The core rendering pipeline operates on a fixed time interval governed by a high-resolution monotonic system clock (os_gettime_ns()).

When OBS is configured to output at 60 frames per second, the rendering engine ticks precisely every 16.67 milliseconds. The canvas does not wait for incoming network frames to arrive. Instead, every tick of the master clock pulls the most current valid frame available in each source's decoded frame buffer, effectively standardizing disparate video sources into a single coherent output raster.

RTMP Packet Ingestion and Jitter Buffering

Remote RTMP feeds arrive via TCP, which introduces packet retransmission delays, jitter, and variable latency. OBS handles this inconsistency through its input sources (such as the Media Source or VLC Source backed by FFmpeg/libavformat):

  1. Demuxing and Timestamps: RTMP packets carry Presentation Time Stamps (PTS) and Decoding Time Stamps (DTS). The demuxer separates the compressed audio and video streams and reads these native timestamps.
  2. Jitter Buffering: To absorb network fluctuation, OBS maintains a network receive buffer. This buffer stores a configurable duration of media (typically between 100ms and 2000ms), giving delayed TCP packets time to arrive and assemble into complete frames before they are scheduled for decoding.
  3. Hardware/Software Decoding: Once reordered, frames are decoded and sent to an internal queue as raw surface textures (e.g., NV12, YUV420p) waiting for ingestion by the graphics renderer.

Frame Sampling, Duplication, and Dropping

Because remote callers transmit from separate devices with independent system clocks, clock drift is inevitable. Even if two callers output at 30 fps, one may produce 29.98 fps while the other produces 30.01 fps.

To maintain continuous visual sync on the canvas, OBS employs a frame-sampling strategy:

  • Frame Duplication (Underflow): If a high-latency caller suffers a network hiccup and no new frame is decoded when the render loop ticks, OBS samples and displays the previous frame texture again. This prevents the output canvas from tearing, freezing other elements, or stalling the program feed.
  • Frame Dropping (Overflow): If a remote feed delivers frames faster than the OBS render clock consumes them—or delivers a burst of delayed frames following a network spike—OBS discards stale frames whose timestamps fall behind the current playback position, preventing infinite latency growth.

Audio-Driven Synchronization and Resampling

Video frames cannot be synchronized in a vacuum; human perception is far more sensitive to audio desynchronization. OBS Studio treats the primary audio subsystem as the master sync anchor.

The software tracks the offset between incoming RTMP audio presentation timestamps and the video presentation timestamps. If clock drift causes a remote caller's audio and video to drift apart, OBS applies dynamic audio resampling to slightly stretch or compress the audio buffer, keeping lip-sync locked without introducing audible pitch changes or visual stutter.

Latency Normalization Across Multiple Callers

To give multiple disparate remote callers the appearance of being in the same physical studio, production operators must manually align relative arrival delays. OBS Studio facilitates this via the "Sync Offset" property in the Advanced Audio Properties and source-level render caching. By adding artificial delay buffers to the lowest-latency callers, operators align their presentation times with the highest-latency caller, ensuring that multi-person conversations happen synchronously within the master canvas tick.
