OBS Studio Scripting: Lua vs Python Memory Overhead

This article examines the distinct differences in memory overhead between Lua and Python scripts when executed within OBS Studio. While both scripting languages provide access to the OBS API to automate scenes, control sources, and handle events, Lua provides a drastically smaller memory footprint and lighter runtime footprint than Python, which requires initializing a full external CPython environment.

Interpreter Architecture and Base Footprint

The primary driver of memory divergence is how OBS Studio interfaces with each runtime:

  • Lua (LuaJIT): OBS Studio integrates Lua directly using a built-in interpreter (typically LuaJIT). The base memory overhead of spinning up the Lua state inside OBS is practically negligible, usually consuming less than 1 to 2 MB of RAM. Because it is compiled directly into the application ecosystem, it requires no external runtime dependencies to be mapped into the process space.
  • Python: OBS Studio does not bundle Python natively; it dynamically links against an external Python installation (specifically the CPython shared library, such as python3x.dll on Windows). Loading this runtime forces OBS to map the CPython interpreter, initialization routines, and core modules into the host process's memory space. This immediately introduces a baseline overhead of approximately 20 MB to 50 MB, even before running any custom script logic.

Memory Overhead per Data Structure

Beyond the initial runtime startup, the way each language represents internal data types significantly affects memory consumption:

  • Python Object Headers: Python treats everything as a heap-allocated object (PyObject). Every integer, float, string, or boolean carries overhead for reference counting, type identification, and memory alignment flags. A basic integer in Python typically consumes 28 bytes on a 64-bit system.
  • Lua Value Representation: Standard Lua and LuaJIT use compact tagged unions (TValue) for primitive types. Small numbers and booleans are stored directly by value without requiring individual heap allocation headers. As a result, arrays, tables, and numeric operations in Lua allocate a fraction of the memory required for equivalent Python lists and dictionaries.

Garbage Collection and Memory Management

  • Lua's Garbage Collector: Lua uses an incremental mark-and-sweep collector tailored for embedded environments. It maintains low metadata overhead, keeping memory fragmented less frequently and avoiding the need for heavy cyclic tracking data structures.
  • Python's Dual Garbage Collector: Python uses a combination of reference counting and a generational cyclic garbage collector. Tracking references across complex objects requires maintaining doubly linked lists for container objects, which adds an additional layer of memory overhead to every non-primitive structure.

Practical Impact on OBS Studio

In production environments, especially during live streaming or recording under high CPU and GPU loads, memory efficiency directly influences system responsiveness.

Running multiple Lua scripts introduces virtually no noticeable change to the OBS Studio memory footprint, making it the superior choice for simple automation, timers, hotkeys, and source manipulation. Python should generally be reserved only for tasks that strictly require Python-specific third-party modules, as its baseline and operational memory costs can quickly scale up the overall private working set of the OBS process.
