Enhanced RTMP Timecode Formatting in OBS Studio

OBS Studio implements timecode and timestamp formatting for multi-track video within the Enhanced RTMP (E-RTMP) specification by synchronizing tracks against a single monotonic clock and expressing presentation offsets across RTMP chunk headers, extended video packet headers, and optional in-band SEI messaging. By standardizing the Decode Time Stamp (DTS) at the chunk header level and pairing it with a 24-bit Composition Time Offset (CTS) inside the extended payload, OBS Studio ensures that multiple concurrent video renditions remain precisely aligned for player-side client switching.

The Monotonic Reference Clock

When OBS Studio streams multi-track video—such as Twitch Enhanced Broadcasting with multiple resolution tiers—it derives all track timings from a shared internal clock. Rather than generating independent timelines for each encoder instance, OBS creates a shared reference base at the start of the stream. Video frames captured from the canvas are assigned presentation timestamps (PTS) before being routed to each parallel encoder. This ensures that a specific video frame in a 1080p60 track shares the exact PTS reference with the corresponding frame in the 720p60 or 480p30 tracks.

RTMP Chunk Header Timestamps (DTS)

At the container level, OBS Studio uses standard RTMP chunk message headers to convey the Decode Time Stamp (DTS) for each track:

  • Basic Header & Message Header: A standard Type 0 or Type 1 RTMP message header includes a 24-bit integer timestamp field measured in milliseconds.
  • Extended Timestamp Field: If the stream runtime exceeds 16,777,215 milliseconds (~4.66 hours), the 24-bit field is populated with 0xFFFFFF, and an additional 32-bit extended timestamp field follows the header to prevent rollover.
  • Track Differentiation: Multi-track streams assign unique Chunk Stream IDs (CSID) and Message Stream IDs to separate video feeds, allowing downstream ingest servers to track DTS progressions independently without cross-stream timeline collision.

Enhanced RTMP Extended Video Header Structure

Enhanced RTMP replaces traditional Flash Video (FLV) tags with an extended video packet structure to accommodate modern codecs (such as HEVC and AV1) and multi-track signaling. OBS Studio formats the initial bytes of each video packet payload as follows:

  1. Header Control Byte (1 byte):
    • Bits 0–3 define the PacketType (e.g., 0 for Sequence Start, 1 for Coded Frames, 3 for Coded Frames X).
    • Bits 4–7 define the FrameType (Keyframe 1, Inter-frame 2).
  2. FourCC Identifier (4 bytes): Directly follows the control byte to identify the video codec (e.g., hvc1 for HEVC, av01 for AV1, or avc1 for H.264).
  3. Composition Time Offset / CTS (3 bytes): For codecs utilizing B-frames (bi-directional predictive frames), the extended header inserts a 24-bit signed or unsigned integer representing the Composition Time Offset (\(CTS = PTS - DTS\)) in milliseconds. When a decoder processes the packet, it calculates the true rendering time by adding this 24-bit CTS to the DTS provided in the RTMP chunk header. If the codec profile does not use B-frames (e.g., low-latency baseline configurations or AV1 streams without reordering), this offset is set to 0.

In-Band NALU Timecodes (SEI)

In addition to container-level millisecond timestamps, OBS Studio can pass embedded timecodes directly within the video elementary bitstream. For H.264 and HEVC encodes, Supplemental Enhancement Information (SEI) Network Abstraction Layer (NAL) units are prepended to keyframes:

  • Picture Timing SEI: Encodes precise clock ticks, field/frame flags, and picture structure timing derived from the encoder's internal counter.
  • User Data Unregistered SEI: Used in specialized broadcast workflows to carry SMPTE timecodes (hours, minutes, seconds, frames) or ISO-8601 UTC timestamps, ensuring down-funnel synchronization for DVR alignment and multi-camera playback.
