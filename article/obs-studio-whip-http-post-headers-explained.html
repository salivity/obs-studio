OBS Studio WHIP HTTP POST Headers Explained

OBS Studio uses the WebRTC HTTP Ingestion Protocol (WHIP) to publish real-time, ultra-low-latency video feeds to remote media servers using standard HTTP-based signaling. When initiating a stream, OBS sends an HTTP POST request carrying an SDP (Session Description Protocol) offer to negotiate WebRTC media capabilities. This article details the exact structure, syntax, and formatting of the HTTP POST headers generated by OBS Studio during this handshake process.

The Request Method and Target

When a user clicks "Start Streaming" in OBS with the service configured to WHIP, the internal WebRTC output module initiates a single standard HTTP/1.1 or HTTP/2 POST request to the configured WHIP URL endpoint.

POST /whip/endpoint HTTP/1.1

Core Signaling Headers

To adhere to the IETF WHIP specification, OBS Studio formats the following key signaling headers:

  • Content-Type: application/sdp
    This header is strictly required. It informs the ingest server that the HTTP request body contains a plaintext SDP offer describing the stream's tracks (e.g., H.264/AV1 video, Opus audio), ICE credentials, and DTLS fingerprints.
  • Accept: application/sdp
    OBS includes this header to indicate that it expects the WHIP server to return an HTTP 201 Created response containing the server's matching SDP answer in the body.

Authentication Headers

If an authentication token is provided in the OBS Stream settings under the "Bearer Token" field, OBS constructs an HTTP Authorization header:

  • Authorization: Bearer <token>
    The <token> is formatted as a standard OAuth 2.0-style Bearer string without extra quotes or escaping. If no token is entered in OBS, this header is omitted entirely.

Standard Protocol and Network Headers

OBS relies on underlying network libraries (such as libcurl) to manage the HTTP layer, resulting in standard connection metadata headers:

  • Host: <hostname>:<port>
    Derived directly from the WHIP server URL provided in the settings.
  • User-Agent: <client-string>
    Identifies the client software. Depending on the OBS build and OS, this typically identifies OBS Studio and the underlying network component (for example, OBS/<version> or libcurl/<version>).
  • Content-Length: <bytes>
    Specifies the exact size of the generated SDP offer payload in bytes.
  • Expect: 100-continue (Optional/Conditional)
    Depending on the network stack configuration and payload size, libcurl may append this header to verify that the server will accept the incoming SDP offer before transmitting the full body.

Complete Request Example

Below is an example of the fully assembled HTTP POST request generated by OBS Studio when publishing to a secure WHIP endpoint:

POST /api/v1/whip/live HTTP/1.1
Host: ingest.example.com
User-Agent: OBS/30.0.0 (libcurl/8.4.0)
Accept: application/sdp
Content-Type: application/sdp
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
Content-Length: 2154

v=0
o=- 4611732625244588936 2 IN IP4 127.0.0.1
s=-
t=0 0
a=group:BUNDLE 0 1
...
[Remainder of SDP Offer]

Once the remote server verifies these headers and accepts the SDP offer, it returns an HTTP 201 Created status code along with a Location header, which OBS stores for sending future teardown (DELETE) requests when the user stops the stream.
