OBS WebSocket Audio Monitor State for Controllers

This article explores how OBS Studio exposes its audio monitoring states via the native obs-websocket API to provide real-time status feedback for hardware controllers like Stream Decks, MIDI surfaces, and custom microcontrollers. By leveraging dedicated request commands, typed event subscriptions, and structured enumeration payloads, developers can accurately display and toggle whether an audio source is muted to headphones, monitored locally, or broadcast directly to the stream.

The WebSocket Protocol Foundation

Starting with OBS Studio 28, the obs-websocket v5 protocol is integrated directly into the core application. Hardware controllers interact with this interface over a persistent TCP WebSocket connection, exchanging structured JSON objects.

To track audio monitoring, the controller interacts with three key elements of the protocol:

  1. Direct requests to read current state.
  2. Direct requests to modify state.
  3. Event subscriptions to listen for real-time changes originating within the OBS interface or third-party plugins.

Querying Audio Monitor States

To establish the initial state of hardware LEDs, displays, or motorized faders upon connection, a controller issues the GetInputAudioMonitorType request.

The request payload requires an identifier for the target input:

{
  "op": 6,
  "d": {
    "requestType": "GetInputAudioMonitorType",
    "requestId": "unique-request-id-1",
    "requestData": {
      "inputName": "Desktop Audio"
    }
  }
}

OBS Studio responds with a RequestResponse containing the monitorType property:

{
  "op": 7,
  "d": {
    "requestType": "GetInputAudioMonitorType",
    "requestId": "unique-request-id-1",
    "requestStatus": {
      "result": true,
      "code": 100
    },
    "responseData": {
      "monitorType": "OBS_MONITORING_TYPE_MONITOR_AND_OUTPUT"
    }
  }
}

The monitorType property exposes one of three string enumerations:

  • OBS_MONITORING_TYPE_NONE: Monitor Off (audio goes only to the stream/recording output).
  • OBS_MONITORING_TYPE_MONITOR_ONLY: Monitor Only, mute output (audio goes only to the local monitoring device).
  • OBS_MONITORING_TYPE_MONITOR_AND_OUTPUT: Monitor and Output (audio is sent to both the local monitor device and the stream/recording).

Real-Time Event Feedback

Polling requests are inefficient for hardware interfaces requiring instant visual updates. Instead, controllers subscribe to the Inputs event category during the initial authentication handshake (Identify operation, setting the eventSubscriptions bitmask flag to include 1 << 3).

When an audio source's monitoring status changes—whether altered via the OBS Advanced Audio Properties menu, a hotkey, or another script—OBS Studio emits the InputAudioMonitorTypeChanged event:

{
  "op": 5,
  "d": {
    "eventType": "InputAudioMonitorTypeChanged",
    "eventData": {
      "inputName": "Desktop Audio",
      "inputUuid": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
      "monitorType": "OBS_MONITORING_TYPE_NONE"
    }
  }
}

Hardware devices parse eventData.monitorType and update their physical state (such as switching an LED from amber to off) based on the matching inputName or inputUuid.

Modifying State from the Hardware

When a user presses a button on the hardware controller to cycle or set the monitoring mode, the controller sends a SetInputAudioMonitorType request:

{
  "op": 6,
  "d": {
    "requestType": "SetInputAudioMonitorType",
    "requestId": "unique-request-id-2",
    "requestData": {
      "inputName": "Desktop Audio",
      "monitorType": "OBS_MONITORING_TYPE_MONITOR_ONLY"
    }
  }
}

Upon executing the command, OBS Studio updates the internal audio mixer, returns a success code to the request, and broadcasts the corresponding InputAudioMonitorTypeChanged event, ensuring all connected hardware peripherals maintain state synchronization.
