OBS Studio Audio Buffer Underrun Detection

This article provides an overview of how OBS Studio detects and reports audio buffer underruns during live production and diagnostic analysis. It covers the internal mechanics of the OBS audio pipeline, the criteria used by the core mixer to identify sample starvation, and the exact manner in which verbose console mode formats and outputs these hardware and timing anomalies.

Audio Pipeline and Timing Mechanics

OBS Studio handles audio through a dedicated subsystem implemented in libobs/audio-io. Incoming audio feeds from capture devices, desktop loopbacks, and media files are converted to a standard internal floating-point format and placed into circular buffers.

The audio subsystem operates on strict discrete timing intervals, typically processing 1024 samples per frame at a standard sample rate of 44.1 kHz or 48 kHz. A dedicated audio mixing thread ticks at predetermined intervals, pulling the required number of samples from each source's buffer to mix down into the final program tracks.

How Underruns Occur and Are Detected

An audio buffer underrun occurs when the mixing thread or the underlying platform audio output device requests a block of audio frames, but the buffer does not contain enough data to fulfill the request. This leads to dropped samples, audible clicks, crackles, or desynchronization.

OBS Studio detects these conditions at two distinct layers:

  1. System and Hardware Callbacks: At the device driver layer (such as Windows WASAPI, macOS CoreAudio, or Linux ALSA/PulseAudio), the OS audio engine reports device-level buffer glitches. For example, in WASAPI event-driven capture mode, if the capture buffer fills before OBS reads it, or if the render buffer empties before OBS supplies new packets, the API returns diagnostic flags indicating glitching or starvation.
  2. Internal Buffer Starvation (libobs): Inside the core audio mixer, OBS calculates timestamps for every expected batch of audio samples using high-resolution system timers (os_gettime_ns). If the mixing thread wakes up and finds that a source queue contains fewer samples than required for the current timestamp window, it registers an underrun condition.

Diagnostic Reporting in Verbose Console Mode

When OBS Studio is launched with the --verbose command-line argument, the standard logging engine increases its verbosity level, printing granular timing notifications directly to the console output and the session log file.

Under verbose mode, underrun detection is surfaced through several specific log events:

  • Dynamic Buffering Increases: When internal starvation occurs consistently, OBS attempts to mitigate future dropouts by dynamically increasing total audio buffering latency. In verbose mode, the log outputs messages such as:
    adding [X] ms of audio buffering, total: [Y] ms
    This indicates that an underrun condition forced the audio clock to back up to prevent permanent desynchronization.
  • WASAPI and OS-Level Glitch Logging: Platform-specific modules write low-level error codes to the console. On Windows, verbose logs reveal calls to IAudioCaptureClient::GetBuffer that return AUDCLNT_E_BUFFER_ERROR or indicate missed packet events.
  • Timestamp Skew Alerts: When input frames arrive later than their scheduled presentation timestamp, the console logs timestamp-drift warnings, detailing the expected versus actual nanosecond arrival times and marking dropped frames.

By combining low-level OS device polling with timestamp cross-checks in the audio mixing loop, OBS Studio precisely identifies both hardware-driven and CPU-starvation underruns, outputting actionable timing data to developers and system administrators through its verbose console output.
