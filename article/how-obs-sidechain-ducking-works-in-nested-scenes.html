How OBS Sidechain Ducking Works in Nested Scenes

OBS Studio processes sidechain ducking triggers across nested scenes through a centralized audio graph, treating sources as globally accessible within the active rendering pipeline rather than isolating them to scene hierarchies. This article details how the audio engine registers ducking triggers across nested configurations, the dependencies on source activation states, and how execution order impacts audio dynamics.

Global Source Registration

OBS Studio maintains an internal registry of all audio sources defined within the current Scene Collection. When a Compressor filter is applied to an audio track to establish ducking, the "Sidechain/Ducking Source" dropdown pulls from this global list, regardless of whether a source resides in the root scene or deep within a nested scene.

Because of this flat referencing model, the filter does not need to traverse a traditional parent-child scene path to locate the control signal. As long as the target source and the trigger source exist within the active session, the compressor can point directly to the trigger's audio output buffer.

Scene Hierarchy and Activation Dependencies

Although referencing is global, audio signal generation is contingent on the scene rendering tree. OBS Studio evaluates audio processing based on the scenes that are actively contributing to the Program output (or are being monitored):

  • Active Scenes: When a nested scene containing the trigger source is active within the Program mix, its audio pipeline processes normally. The compressor reads the trigger source's volume levels, calculates the threshold exceedance, and reduces the gain of the target audio.
  • Inactive Nested Scenes: If a nested scene containing a sidechain trigger is switched out of the active output and its audio is cut, the trigger signal drops to zero. Consequently, the compressor releases the ducking effect, even if the parent scene remains active.
  • Muted Sources: If a source inside a nested scene is muted via the mixer, it outputs silence. A muted trigger cannot drive sidechain compression, even if the nested scene itself is currently active.

Processing Order and Latency

OBS Studio processes audio in fixed-duration frames (typically between 10ms to 20ms chunks depending on your sample rate). During each audio processing tick:

  1. All active sources generate and process their localized filter chains.
  2. The sidechain trigger source renders its audio output before gain attenuation calculations occur.
  3. The compressor on the ducked source queries the measured volume level of the trigger source from the current or immediately preceding audio buffer.
  4. The compressor applies the configured attack, hold, release, and ratio curves to attenuate the target audio stream.

Because this processing occurs on the shared audio thread per buffer frame, nested scenes do not introduce measurable sidechain latency compared to sources residing in the same scene. However, complex filter chains on either the trigger or the ducked source can cause micro-delays if heavy processing delays buffer delivery.

Nested Scene Ducking Pitfalls

  • Ghost Triggers: If a nested scene is embedded in multiple active scenes simultaneously, the sidechain source may process audio across all instances concurrently, which can lead to unexpected ducking behavior if scene volumes differ.
  • Scene Transitions: During crossfades or stinger transitions between scenes where the nested trigger is introduced or removed, ducking levels may fluctuate abruptly as the scene's rendering weight shifts from zero to full output.
