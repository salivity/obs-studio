OBS Studio FFmpeg RTMP Intranet Configuration

This article examines how OBS Studio initializes, configures, and routes live streams through the FFmpeg RTMP protocol wrapper when targeting private intranet media servers. It details the underlying libavformat options, the differences between OBS's standard streaming mode and its dedicated FFmpeg custom output, the injection of protocol-level parameters via the connection URL, and network optimizations required for robust low-latency local delivery.

OBS Studio and the FFmpeg RTMP Architecture

OBS Studio relies on two distinct internal systems for generating RTMP streams: the default obs-outputs module (which historically utilizes librtmp or a native RTMP protocol handler) and the direct FFmpeg integration provided via libavformat. When administrators push video to private local media servers—such as NGINX-RTMP, Simple Realtime Server (SRS), or MediaMTX—they can either rely on OBS's standard streaming engine or engage the explicit FFmpeg wrapper via the "Custom Output (FFmpeg)" interface.

When the FFmpeg protocol wrapper executes an RTMP push, it manages the underlying TCP socket connection, handles the RTMP handshake sequence (C0/C1, S0/S1, C2/S2), sends connect, releaseStream, FCPublish, and createStream command messages, and writes interleaved audio and video chunks over the network.

Configuring via Custom Streaming Service vs. FFmpeg Output

There are two primary ways to engage the RTMP protocol pipeline for private network streaming in OBS:

1. The Standard Service Route with URL Parameters

Navigating to Settings > Stream and choosing Custom... enables streaming to any standard intranet URL (e.g., rtmp://192.168.1.100/live/streamkey). In modern builds of OBS Studio, the underlying network handler permits FFmpeg protocol options to be appended directly to the URL as key-value query pairs:

rtmp://192.168.1.50:1935/live/streamKey?rtmp_buffer=100&timeout=5000000

2. Custom Output (FFmpeg)

For direct access to the FFmpeg AVFormatContext and protocol options, users configure:

  • Settings > Output > Output Mode: Advanced
  • Recording Tab > Type: Custom Output (FFmpeg)
  • FFmpeg Output Type: Output to URL
  • File path or URL: rtmp://<internal-ip>:1935/<app>/<streamkey>
  • Container Format: flv

This bypasses the standard OBS streaming engine entirely. It delegates the muxing directly to FFmpeg’s flv muxer and passes the connection handling directly to FFmpeg’s rtmp protocol wrapper (libavformat/rtmpproto.c).

Critical FFmpeg RTMP Protocol Parameters

When pushing to local servers, default WAN-focused timeouts and buffering configurations often introduce unnecessary latency or cause abrupt disconnects. The FFmpeg RTMP wrapper exposes several parameters (AVOptions) that can be applied within the connection string or the FFmpeg options field:

  • rtmp_buffer: Sets the client buffer time in milliseconds (default is 3000ms). For local intranet streams where packet loss is negligible, lowering this to rtmp_buffer=100 or 0 minimizes playback delay on the ingestion server.
  • rtmp_live: Forces the connection to explicitly specify that the feed is live (rtmp_live=live). This instructs the receiving media server not to expect seekable media files.
  • timeout: Defines the network socket timeout in microseconds. On an intranet, setting timeout=3000000 (3 seconds) ensures that OBS detects a severed connection or a restarted media container immediately, allowing auto-reconnect logic to engage without hanging.
  • tcp_nodelay: While handled at the OS socket layer, setting tcp_nodelay=1 disables Nagle's algorithm, reducing packet buffering and ensuring that video chunks are dispatched onto the private LAN immediately upon encoding.
  • rtmp_tcurl: Specifies the target connection URL explicitly. Some private media server configurations (e.g., specific auth modules or virtual hosts in NGINX) validate the tcUrl field against local ACLs.

Intranet Network and Ingestion Server Optimizations

Because private intranet servers do not face public Internet routing constraints, configuring the FFmpeg RTMP wrapper should align with LAN-specific characteristics:

  1. Chunk Size Negotiation: Standard RTMP uses 128-byte chunks by default, which creates high CPU overhead on high-bitrate local streams. Media servers like SRS or NGINX-RTMP typically negotiate chunk sizes up to 4096 or 65536 bytes. FFmpeg's RTMP wrapper honors server-side Window Acknowledgement Size and Set Chunk Size messages automatically, reducing CPU and packet header overhead on the local link.
  2. MTU and Fragmentation: Ensure that local networks with jumbo frames enabled are correctly aligned. If the stream sends large keyframes (I-frames), packet fragmentation can cause brief socket stalls if intermediate switches do not match MTU sizes between the OBS workstation and the ingestion host.
  3. Authentication Schemes: For intranet nodes requiring local credentials, FFmpeg formats RTMP authentication either within the URL path (rtmp://user:pass@192.168.1.10:1935/app/key) or by passing query parameters (?auth=token), which the wrapper compiles into the initial connect command dictionary.
