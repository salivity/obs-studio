How OBS Studio Handles High Packet Loss Over Wi-Fi

This article examines how OBS Studio mitigates network instability, addressing how it handles packet fragmentation and retransmission when streaming across high-packet-loss wireless connections. While OBS Studio delegates low-level packet reconstruction to the underlying transport protocols, its overall resilience depends heavily on the selected protocol—such as RTMP over TCP, or SRT and RIST over UDP—combined with internal frame-dropping mechanisms and dynamic bitrate controls.

Transport Protocol Architecture

OBS Studio does not implement an independent, proprietary network transport layer. Instead, it relies on open-source libraries to package and transmit encoded video frames. How a dropped or fragmented packet is retransmitted depends directly on the protocol chosen in the output settings.

RTMP (TCP-Based Delivery)

Traditional live streaming with OBS Studio uses RTMP, which runs over TCP.

  • OS-Level Handling: TCP guarantees in-order packet delivery. When a packet or an IP fragment is lost over Wi-Fi, the operating system's network stack handles the retransmission via standard TCP Automatic Repeat reQuest (ARQ).
  • Head-of-Line Blocking: Because TCP enforces strict ordering, a missing packet halts the delivery of subsequent packets. In high-loss environments, this causes latency to spike as the sender waits for retransmissions.
  • OBS Internal Dropping: OBS Studio monitors its internal send buffer. If TCP retransmissions stall the connection and the internal buffer fills up, OBS Studio will proactively drop entire encoded video frames to prevent infinite delay, resulting in visible stuttering or dropped frames on the broadcast.

SRT and RIST (UDP-Based Delivery)

To combat wireless instability, OBS Studio natively supports Secure Reliable Transport (SRT) and Reliable Internet Stream Transport (RIST), both of which operate over UDP.

  • Selective Retransmission (ARQ): Unlike TCP, SRT and RIST do not enforce strict byte-stream ordering at the OS level. When a UDP datagram containing fragmented video data is lost, the receiver detects the gap in sequence numbers and sends a Negative Acknowledgment (NAK) back to OBS.
  • Latency Buffers: OBS Studio retransmits only the specific lost packets flagged by NAKs. This process occurs within a user-configured latency buffer (typically 200ms to 2000ms). If a packet cannot be recovered before its playout timestamp expires, the protocol drops that specific packet rather than freezing the entire stream.

Packet Fragmentation and MTU Considerations

In wireless environments, physical layer interference often causes large network packets to be corrupted or fragmented across the IP layer.

  • IP Fragmentation Risks: If a video packet exceeds the network Maximum Transmission Unit (MTU)—typically 1500 bytes on standard Ethernet and Wi-Fi—the IP layer splits it into multiple fragments. If a single Wi-Fi drop occurs on any fragment, the entire datagram is invalidated.
  • UDP Protocol Sizing: Both SRT and RIST in OBS Studio default to packet payload sizes that fit comfortably within standard MTU limits (typically around 1316 bytes of payload plus headers) to prevent IP-level fragmentation before the data leaves the machine.

Dynamic Bitrate and Congestion Control

Under persistent wireless degradation, retransmissions alone cannot solve bandwidth saturation because retransmitting packets consumes extra throughput, further worsening congestion.

OBS Studio includes a feature called Dynamically change bitrate to manage congestion (Beta). When enabled:

  1. OBS monitors transport-layer congestion signals (socket write stalls in TCP or round-trip time and buffer inflation in SRT).
  2. Instead of allowing retransmissions to overflow the local outbound queue, OBS Studio throttles the video encoder to a lower target bitrate in real time.
  3. Once the packet loss clears and retransmission overhead drops, OBS scales the encoder bitrate back up to the configured maximum, stabilizing the wireless connection.
