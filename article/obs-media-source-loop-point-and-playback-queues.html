OBS Media Source Loop Point and Playback Queues

This article explains how OBS Studio handles video playback queues and decoder buffers when an active Media Source reaches its designated loop point. It examines the internal demuxing workflow, the flushing of video frame pipelines, timestamp resets, and how looping affects playlist-based media queues versus standalone files.

The Internal Demuxer and Queue Flushing

When an active Media Source in OBS Studio reaches its loop point (or the end of the file), the underlying FFmpeg demuxer triggers an internal seek command back to the file's start time. Because video frames are decoded ahead of time and stored in a playback queue (a buffer of decoded raw frames waiting to be rendered), this seek operation requires an immediate queue flush.

OBS Studio clears the existing frame queue to prevent stale frames from the end of the video from displaying after the seek completes. The decoder calls avcodec_flush_buffers() to clear internal pipeline states, dropping any pre-buffered B-frames or P-frames that rely on references from before the loop boundary.

Timestamp Synchronization and Discontinuity

During continuous playback, OBS Studio maps the media file’s Presentation Timestamps (PTS) to the scene's global rendering clock. When the loop point is reached:

  1. PTS Reset: The media source resets its internal PTS back to the starting timestamp (typically zero).
  2. Clock Resynchronization: The OBS rendering engine detects the timestamp discontinuity. Instead of interpreting the reset as a playback delay, it establishes a new time offset relative to the master audio/video clock.
  3. Audio-Video Alignment: Both audio and video packet queues are cleared simultaneously to avoid desynchronization artifacts, ensuring audio does not lag behind the restarted video track.

Standalone Media Sources vs. Multi-File Playback Queues

How the queue behaves depends significantly on whether the source is a native OBS Media Source or a queue-driven source such as the VLC Video Source.

  • Native Media Source (Single File): The native source treats looping strictly at the file level. The playback queue never advances to an external asset; it indefinitely cycles through decoding, buffering, rendering, and flushing the same asset's data streams.
  • VLC Video Source (Playlists and Queues): When using playlist-based playback, the loop setting can be applied at the track level or the playlist level. If track looping is active, the playlist queue is effectively blocked from advancing; the current file loops continuously while the remaining queue items remain idle. If playlist looping is enabled, reaching the end of a video does not flush and restart the same file—instead, the queue pops the next media item into the decoder pipeline, only flushing when the entire playlist reaches its end and restarts from the first item.

Performance Impact of the Loop Reset

Because the video playback queue is flushed and rebuilt at every loop point, there is a minor spike in demuxing and decoding activity at the transition point. If the video codec relies on long Groups of Pictures (GOPs) or high bitrates, the queue may experience a brief starvation period while waiting for the initial keyframe (I-frame) to decode, which can occasionally manifest as a micro-stutter on systems with high resource utilization.
