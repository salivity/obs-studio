How OBS Studio Handles Interleaved RTSP Streams

This article explains how OBS Studio captures IP surveillance camera feeds by processing Real-Time Streaming Protocol (RTSP) streams operating in interleaved mode over TCP. It covers the underlying role of FFmpeg's libavformat, the binary framing mechanism used to distinguish media from control packets, and how the resulting data is demuxed, decoded, and rendered into a live production scene.

RTSP Transport Modes: UDP vs. Interleaved TCP

IP surveillance cameras typically transmit video and audio using RTP (Real-time Transport Protocol) while controlling the session via RTSP. By default, RTSP establishes control over TCP (standard port 554), while media packets travel across separate, dynamically negotiated UDP ports.

In environments with strict firewalls, network address translation (NAT), or unstable Wi-Fi, separate UDP streams often suffer packet loss or get dropped entirely. Interleaved mode solves this by encapsulating RTP data and RTCP control messages directly into the existing RTSP TCP connection.

The Interleaved Binary Framing Format

When configured for interleaved transport, the IP camera does not broadcast separate UDP packets. Instead, it prepends a 4-byte binary framing header to every payload sent over the existing TCP socket, as specified in RFC 2326:

  1. Magic Byte (0x24 / $): An ASCII dollar sign marks the boundary of an interleaved packet.
  2. Channel Identifier (1 byte): Identifies the content type and stream index. Typically, channel 0 represents video RTP data, channel 1 represents video RTCP messages, channel 2 represents audio RTP data, and channel 3 represents audio RTCP messages.
  3. Payload Length (2 bytes): A 16-bit integer defining the exact size of the encapsulated payload that follows immediately after the header.

How OBS Studio Processes Interleaved Streams

OBS Studio does not maintain its own custom RTSP network demuxer. Instead, it delegates stream ingestion to FFmpeg via the internal obs-ffmpeg module, typically instantiated through the Media Source or VLC Video Source.

When capturing an RTSP stream, the ingestion pipeline follows these stages:

  1. Session Negotiation: When configured to use TCP (often by passing -rtsp_transport tcp to the network options), OBS instructs libavformat to send an RTSP SETUP request with the header Transport: RTP/AVP/TCP;interleaved=0-1. The surveillance camera acknowledges this, confirming that transport stream data will be multiplexed over the control connection.
  2. Packet Boundary Extraction: As stream bytes enter the network socket buffer, the parser searches for the $ (0x24) marker. It reads the subsequent 3 bytes to verify the channel and payload length, allowing it to accurately extract the framed payload without confusing RTSP text commands (such as OPTIONS or TEARDOWN) with binary media data.
  3. Payload Separation (Demuxing):
    • RTCP Packets: Sent to the internal session tracker to monitor packet statistics, synchronize audio/video clocks, and maintain the connection keep-alive state.
    • RTP Media Payloads: Stripped of their RTP packet headers (extracting sequence numbers, timestamps, and marker bits).
  4. Frame Assembly: For modern IP cameras, the RTP payload usually contains H.264 or H.265 Network Abstraction Layer (NAL) units. The demuxer reassembles fragmented units (such as FU-A packets) into complete video frames.
  5. Decoding and Rendering: Once an entire frame is reconstructed, it is passed to the selected decoder (software via libavcodec or hardware-accelerated decoders like NVENC, QuickSync, or VAAPI). The decoded raw video frames (typically YUV420p) are then converted into textures and handed to the OBS graphics subsystem for compositing on the canvas.

Network Latency and Buffering Considerations

While interleaved TCP guarantees that no frames are lost due to network drops, packet loss can lead to TCP retransmissions, creating head-of-line blocking. OBS Studio handles this through configurable buffer settings in the Media Source. Lowering the network buffer minimizes latency for real-time monitoring, but if the surveillance feed experiences connection drops, increasing the buffer ensures that interleaved video frames decode smoothly without stuttering or temporal artifacting.
