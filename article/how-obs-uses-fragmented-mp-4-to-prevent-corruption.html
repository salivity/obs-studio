How OBS Uses Fragmented MP4 to Prevent Corruption

This article explains how OBS Studio leverages the fragmented MP4 (fMP4) format to protect video recordings against corruption caused by sudden power loss or system crashes. By replacing the traditional monolithic MP4 structure with continuous, self-contained segments, OBS ensures that recorded footage remains fully playable right up to the second the interruption occurs.

The Problem with Standard MP4 Files

Standard MP4 files rely on a critical metadata block called the moov atom (movie atom). This index defines the file layout, frame rates, codecs, and timestamps required for media players to decode and play the video data (mdat atom).

In conventional recording workflows, the moov atom is constructed in system memory during the session and written to the storage drive only after the user stops the recording. If a power outage or system crash occurs while recording, this metadata is never committed to the disk. Without the moov atom, the operating system and media players cannot interpret the raw audio and video data, rendering the entire file unreadable and functionally corrupted.

The Mechanics of Fragmented MP4 (fMP4)

Fragmented MP4 solves this structural vulnerability by dividing the recording into a sequence of small, independent chunks. Instead of deferring metadata creation until the recording is completed, fMP4 operates on a continuous, two-part cycle:

  1. Movie Fragment Header (moof atom): Contains the playback metadata, frame offsets, and timing data specifically for the upcoming slice of media.
  2. Media Data (mdat atom): Contains the actual audio and video packets corresponding to that specific header.

OBS Studio periodically generates these paired moof and mdat fragments throughout the recording process. As soon as a fragment is compiled—typically covering a duration of one to two seconds—it is dispatched directly to the disk subsystem.

Preventing Corruption During Power Loss

When an unexpected power loss occurs, the benefits of fMP4 become evident in two distinct ways:

  • Independent Playability: Because each fragment carries its own metadata, the file does not require a finalized global index at the end of the container. Every fragment already written and synced to disk is complete and valid on its own.
  • Minimal Data Exposure: In the event of a sudden power loss, only the single fragment currently residing in the volatile write cache is lost. All preceding fragments written prior to the power failure remain intact, properly formatted, and fully functional.

When power is restored, any standard media player that supports the fMP4 specification can open the container, read the initialization header, and sequentially parse every completed fragment up to the moment of failure without requiring repair utilities or manual reconstruction.
