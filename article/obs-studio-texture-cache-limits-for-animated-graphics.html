OBS Studio Texture Cache Limits for Animated Graphics

OBS Studio does not impose an arbitrary, hardcoded software limit on individual texture caches allocated for high-resolution animated graphics. Instead, the maximum memory footprint and resolution constraints are governed by the underlying graphics API, the host GPU's VRAM, and the specific subsystem handling the asset, such as the Chromium Embedded Framework (CEF) or the native FFmpeg media pipeline. Understanding these technical thresholds is essential for preventing rendering stalls, dropped frames, and out-of-memory crashes during production.

Graphics Subsystem and Hardware Limits

At the core rendering level (libobs), OBS Studio uses either Direct3D 11 (on Windows) or OpenGL/Metal (on Linux and macOS). The fundamental ceiling for an individual texture surface is determined by the graphics hardware and driver capabilities:

  • Maximum Texture Dimensions: Under Direct3D 11 Feature Level 11_0 and modern OpenGL, the maximum supported 2D texture dimension is 16,384 × 16,384 pixels.
  • VRAM Capacity: Individual texture allocations cannot exceed the contiguous physical video memory available on the GPU. If an allocation request exceeds available VRAM, the graphics driver may spill to shared system memory, causing severe rendering latency, or fail the allocation outright, causing the visual source to disappear.

Memory Allocation in Media Sources and Stingers

When handling animated graphics through the native Image Source or Media Source plugins, OBS Studio handles caching differently depending on the asset type and user configuration:

  • Animated GIFs and APNGs: The standard image plugin decodes animated image frames into system memory (RAM) as uncompressed raw RGBA bitmaps. Because every frame requires Width × Height × 4 bytes, a 4K (3840×2160) animated image sequence running at 60 FPS consumes approximately 1.99 GB of system RAM per second of animation.
  • Stinger Transitions with Pre-Loading: Stinger transitions feature a "Cache Transition to RAM" setting. When enabled, OBS decodes and loads the entire video sequence into uncompressed RAM buffers before playback to avoid disk read latency. If the animation is excessively long or rendered at high resolutions, it will consume several gigabytes of RAM without an internal safety cap, risking an application crash if the system runs out of physical memory.

Browser Source (CEF) Constraints

For graphics rendered using the Browser Source—such as HTML5, WebGL, or Lottie animations—the memory boundaries are dictated by the underlying Chromium Embedded Framework rather than native OBS graphics routines:

  • Process Architecture: Browser sources execute in isolated child processes (obs-browser-page.exe).
  • Tile and Texture Caches: Chromium dynamically sizes its texture transfer cache based on the viewport resolution and total system memory. High-resolution canvas rendering or heavily layered DOM elements are constrained by Chromium's internal GPU rasterization limits, typically soft-capping VRAM utilization per render process to prevent host-system instability. Exceeding this budget causes the browser page to crash and display a blank canvas.

Mitigation and Best Practices

Because OBS Studio relies on host resources rather than fixed artificial limits, maintaining stable performance with high-resolution graphics requires manual optimization:

  • Render overlays, stinger transitions, and animated graphics at the exact native canvas resolution (e.g., 1920×1080 or 3840×2160) rather than downscaling oversized assets in real time.
  • Avoid caching long video clips to RAM; reserve memory caching strictly for short stinger transitions under two seconds in duration.
  • Utilize compressed video formats (such as ProRes 4444 or WebM with VP9/alpha) via the Media Source with hardware decoding enabled, rather than loading raw image sequences or uncompressed animated GIFs.
