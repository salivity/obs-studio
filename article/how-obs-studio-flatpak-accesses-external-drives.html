How OBS Studio Flatpak Accesses External Drives

OBS Studio distributed via Flatpak runs within a sandboxed environment designed to restrict access to the host Linux operating system for enhanced security. To read media assets or write high-bitrate video recordings directly to external drives, OBS Studio relies on a combination of XDG Desktop Portals and explicit filesystem permission overrides. This article explains the technical interaction between the Flatpak sandbox, the portal framework, and the Linux filesystem mount points that facilitate external storage access.

The Sandbox Isolation Model

By default, Flatpak isolates applications from the host filesystem using Linux kernel namespaces, cgroups, and bubblewrap. Standard mount locations where removable media mounts in modern desktop distributions—such as /media, /run/media, and /mnt—are invisible inside the OBS Studio container. This prevents the application from automatically discovering or modifying external storage devices unless explicitly authorized by the user or mediated by system portals.

Dynamic Access via the XDG File Chooser Portal

To handle standard file selection safely, OBS Studio implements the org.freedesktop.portal.FileChooser interface provided by the XDG Desktop Portal framework.

When a user initiates an action that requires browsing the filesystem (such as importing a media source or manually choosing an output destination), the workflow proceeds through several distinct steps:

  1. D-Bus Call: OBS Studio sends an Inter-Process Communication (IPC) request over the D-Bus session bus to the portal service.
  2. Host-Side Dialog: The host system's desktop portal implementation (such as xdg-desktop-portal-gtk, xdg-desktop-portal-kde, or xdg-desktop-portal-gnome) intercepts the request and displays a native file chooser dialog. Because this dialog executes on the host system outside the sandbox, it has full visibility into external hard drives and removable USB devices.
  3. Capability Hand-off via Document Portal: Once the user selects a target file or folder on the external drive, the portal service contacts the Document Portal daemon (xdg-document-portal). The chosen path is mounted into a virtual directory inside the sandbox, typically under /run/user/$UID/doc/, or an open file descriptor is passed directly back to OBS Studio.

This mechanism allows OBS Studio to read or write to the chosen location on the external drive without receiving broad, permanent read/write access to the entire storage volume.

Persistent Permissions for Unattended Output

While portals work seamlessly for interactive file selections, OBS Studio often requires unattended, permanent access to an external storage location for recording outputs, automated scene switching, or replay buffers. If the application cannot autonomously access an external directory upon startup, operations targeting that path will fail.

To bypass portal dialogs for routine recording tasks, users configure persistent filesystem overrides. These overrides modify the bubblewrap sandbox parameters before OBS Studio launches:

  • Command-Line Overrides: Flatpak provides the flatpak override utility. Executing flatpak override --user --filesystem=/run/media com.obsproject.Studio (or targeting /media or /mnt) exposes the mount directory to the sandbox.
  • Graphical Management: Applications like Flatseal provide a user interface to toggle the same permissions by appending filesystem paths directly to the application's local configuration metadata.

When these static filesystem permissions are set, the Flatpak runtime binds the external drive paths directly into the OBS Studio sandbox environment at launch. This grants OBS Studio standard POSIX read/write access to the external drive, allowing automated video encoding directly to high-capacity external disks without portal intervention.
