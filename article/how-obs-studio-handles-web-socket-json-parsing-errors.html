How OBS Studio Handles WebSocket JSON Parsing Errors

OBS Studio maintains high availability and stability during network communication by isolating its integrated obs-websocket server on dedicated background threads and wrapping JSON payload deserialization inside strict C++ exception-handling boundaries. When a client transmits malformed, truncated, or invalid JSON, the server intercepts the parser's syntax exceptions before they can propagate up the call stack, returns a formatted protocol error response back to the client, and keeps the underlying networking event loop fully operational.

Dedicated Thread Architecture

The obs-websocket plugin runs independently from the core OBS Studio graphics rendering and audio encoding pipelines. Network I/O and client session handling execute on dedicated worker threads driven by an asynchronous networking library (typically Asio via websocketpp). This architecture ensures that network operations, client stalls, or incoming payload processing can never block the main rendering pipeline or crash the entire application process.

Exception Boundaries Around JSON Deserialization

OBS Studio utilizes the modern nlohmann/json C++ library to process inbound and outbound data packets. In standard C++ operation, parsing invalid syntax with nlohmann::json::parse() throws a nlohmann::json::parse_error exception. If unhandled, this exception causes the executing thread to terminate via std::terminate.

To prevent crashes, obs-websocket wraps all incoming message processing in explicit try-catch blocks at the boundary where raw text frames are received:

  1. Message Reception: The WebSocket library reads a raw text frame from the network socket and delivers it to the message-handling callback on the worker thread.
  2. Controlled Parsing: The server invokes nlohmann::json::parse() inside a guarded execution block that specifically catches nlohmann::json::exception as well as generic std::exception types.
  3. Exception Interception: If a parse error occurs, the catch block intercepts the error, extracts the error message and byte offset, and halts further processing of that specific payload.

Protocol Error Handling and Client Isolation

Once an exception is trapped, the server avoids breaking the socket connection unless required by protocol integrity:

  • Error Responses: For standard malformed requests, the server constructs an error response frame using the OBS-WebSocket protocol specification. It marks the request as failed, sets an appropriate status code (such as a malformed payload or syntax error identifier), and sends this response directly back to the offending client.
  • Session Teardown for Protocol Violations: If the malformed payload violates the base WebSocket protocol (RFC 6455) or invalidates the handshake state, the server safely closes that individual client connection with a standard WebSocket close code (such as 1002 for Protocol Error or 1007 for Invalid Frame Payload Data).

Preserving the Event Loop

Because the parsing exception is handled locally within the scope of the individual message dispatcher, the stack unwinds cleanly to the worker loop. The thread's asio::io_context or equivalent event loop remains in a valid running state. The worker thread immediately returns to listening for subsequent network events from other connected clients, ensuring zero downtime for the streaming or recording environment.
