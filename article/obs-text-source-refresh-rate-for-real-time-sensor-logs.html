OBS Text Source Refresh Rate for Real-Time Sensor Logs

OBS Studio decouples its graphical rendering pipeline from external data ingestion, meaning custom text sources reading high-frequency sensor logs are bound by the canvas output framerate rather than the logging frequency of the sensor. While high-speed sensors might write telemetry data at rates exceeding 100 Hz to 1000 Hz, OBS Studio only samples, rasterizes, and displays that data at its configured video framerate (typically 30 or 60 FPS). Managing this disparity requires understanding how OBS handles internal render ticks, file I/O operations, text rasterization, and potential system bottlenecks.

The Render Loop vs. Ingestion Frequency

OBS operates on an internal graphics loop governed by the frame rate set in the video settings. During each frame tick:

  1. The graphics subsystem prompts active scene sources to update their states.
  2. The text source determines if its underlying data has changed.
  3. If new data is present, the source rebuilds its graphical representation.
  4. The compositor blends the resulting texture into the final frame.

Because OBS processes visual updates once per frame tick, any sensor log update occurring between frames is discarded visually. For example, if a log file updates at 200 Hz and OBS runs at 60 FPS, approximately three out of every four log updates will never be rendered to the screen.

File Polling and OS-Level Notification

Standard OBS text sources (such as Text (GDI+) on Windows or Text (FreeType 2) on Linux and macOS) load data from files using operating system file hooks or polling loops.

When configured to read from a text file, OBS leverages platform-specific file alteration monitors (such as ReadDirectoryChangesW on Windows or inotify on Linux). When a high-frequency sensor appends or overwrites the target file:

  • The operating system fires a change notification.
  • OBS schedules an internal read event to pull the new file content into a memory buffer.
  • If the write frequency is faster than the file system notification queue can process, notifications are often coalesced by the OS, causing OBS to read the file in micro-bursts rather than smooth intervals.

The Rasterization Bottleneck

The primary performance cost of reading high-frequency text is not the file read itself, but the rasterization and GPU texture upload process.

Every time the text content changes:

  • The text layout engine calculates glyph metrics and positions.
  • The font renderer rasterizes the vector glyphs into a CPU-bound bitmap.
  • The bitmap is uploaded across the PCIe bus as a new texture to the GPU.

Executing this pipeline at the full rate of a high-frequency sensor (e.g., 500 times per second) causes massive CPU spikes, lock contention on the rendering thread, and dropped frames. To protect the render pipeline, OBS caps text re-rasterization to occur no more than once per rendering cycle.

File Lock Contention

High-frequency sensor applications writing directly to a standard .txt or .log file frequently encounter file-locking collisions with OBS. If the logger opens the file with exclusive write access at the exact moment OBS attempts a read:

  • The read operation fails or throws an I/O exception.
  • OBS may temporarily display stale data or clear the text source entirely.
  • The logging application may stall, introducing latency into the sensor pipeline.

To mitigate this, logging tools must explicitly allow shared read operations (FILE_SHARE_READ on Windows) when opening the file handle.

Optimal Architectures for Sensor Visualization

For sensors updating faster than 60 Hz, relying on direct file reads through the default text source is inefficient. Better performance and lower latency can be achieved through alternative data pipelines:

  • Browser Source via WebSockets: Stream sensor telemetry directly to an embedded OBS Browser Source over a local WebSocket connection (ws://localhost). The browser's JavaScript engine can throttle UI updates using requestAnimationFrame(), bypassing disk I/O entirely.
  • Shared Memory / Named Pipes: Custom OBS plugins utilizing shared memory maps or IPC pipes eliminate disk read/write cycles, allowing the sensor app to push binary-formatted data directly to RAM.
  • OBS Scripting (Lua/Python): Use an embedded Lua script with an integrated timer (timer_add()) set to match the canvas frame interval (e.g., every 16ms for 60 FPS). The script polls the sensor data at the precise render frequency, preventing redundant intermediate disk queries.
