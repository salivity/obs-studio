How OBS Studio Detects Stale WebSocket Connections

This article explores how OBS Studio identifies and terminates stale TCP connections from remote mobile dashboards using WebSocket heartbeat mechanisms. When mobile clients disconnect abruptly without sending proper termination packets, OBS Studio uses a combination of RFC 6455 WebSocket control frames and application-layer heartbeats to monitor client responsiveness. Understanding this process helps developers build resilient dashboard remotes and avoid half-open socket memory leaks.

The Problem of Stale Mobile Connections

Mobile devices frequently transition across networks, enter aggressive power-saving sleep modes, or lose cellular and Wi-Fi signals instantly. Under standard TCP behavior, if a client disappears without transmitting a FIN or RST packet, the server assumes the connection is still valid. This creates a "half-open" state where OBS Studio continues allocating buffer memory and queueing event notifications for a client that no longer exists.

Protocol-Level Ping and Pong Frames

Modern versions of OBS Studio integrate obs-websocket directly into the core application, backed by low-level networking libraries (such as uWebSockets or QtWebSockets). At the transport layer, OBS Studio handles connection health through standard WebSocket control frames defined by RFC 6455:

  • Ping Frames (Opcode 0x9): The server periodically sends a lightweight ping frame over the active TCP connection to the mobile client.
  • Pong Frames (Opcode 0xA): Upon receiving a ping, the client’s WebSocket implementation must automatically respond with an identical payload inside a pong frame.

If the mobile client drops offline abruptly, the server's outgoing ping will fail to elicit a pong. Once an internal timeout window elapses without a response, the underlying network layer marks the TCP socket as dead, initiates server-side teardown, and notifies OBS Studio to close the connection.

Application-Layer Heartbeat Events

Beyond protocol-level frames, OBS Studio’s WebSocket protocol (v5.x) provides an application-level Heartbeat event designed for client-side state validation:

  • Subscription via Identify: During the initial handshake, mobile remotes can request the Heartbeat event subscription within their Identify message.
  • Status Broadcasts: When subscribed, OBS Studio broadcasts regular JSON pulses (typically every few seconds) containing runtime metrics such as whether OBS is streaming, recording, paused, or experiencing dropped frames.
  • Client-Side Timeout Handling: If a mobile remote stops receiving these events, the mobile operating system or application logic recognizes that the server is unreachable. The app can then cleanly sever the local socket and initiate a reconnection sequence.

Connection Teardown and Cleanup

Once a stale connection is detected—either via unacknowledged protocol pings or failed socket writes—OBS Studio executes a cleanup routine:

  1. Event Unsubscription: The client is removed from internal message dispatch lists, preventing event generation overhead for audio meters and scene updates.
  2. Socket Destruction: The server issues an internal close code (typically 1006 for abnormal closures) and deallocates the socket file descriptor.
  3. Log Notification: OBS Studio registers the termination in its log files, indicating the client identifier and the reason for disconnection.

Through these combined transport and application mechanisms, OBS Studio maintains low network overhead while ensuring ghost connections from mobile dashboards are purged efficiently.
