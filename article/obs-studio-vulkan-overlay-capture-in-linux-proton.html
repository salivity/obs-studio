OBS Studio Vulkan Overlay Capture in Linux Proton

Capturing games on Linux using OBS Studio while running through Valve's Proton compatibility layer relies heavily on Vulkan's modular layer system. Because Proton converts DirectX calls into native Vulkan API commands using DXVK and VKD3D-Proton, OBS Studio hooks into the rendering pipeline using Vulkan capture layers rather than traditional Windows hooks. This article explains how OBS Studio interfaces with Proton's Vulkan translation layer, how execution ordering dictates whether overlays appear in the stream, and how frames are transported directly to the capture software.

The Vulkan Layer Architecture

Vulkan provides a standardized mechanism known as validation and utility layers. Layers can insert themselves between the application and the underlying graphics driver to intercept, modify, or duplicate API calls.

OBS Studio utilizes this framework through dedicated capture plugins—most commonly obs-vkcapture or the integrated VK_LAYER_OBS_EXPORT_CAPTURE. When a game launches, the Vulkan loader reads system and user layer manifests (/usr/share/vulkan/implicit_layer.d/ or ~/.local/share/vulkan/implicit_layer.d/). If OBS game capture is invoked, the capture layer hooks key Vulkan entry points, primarily:

  • vkCreateSwapchainKHR
  • vkQueuePresentKHR
  • vkAcquireNextImageKHR

By intercepting vkQueuePresentKHR, OBS accesses the final rendered frame right before it is displayed on the screen.

Proton’s Passthrough to Host Vulkan

A common misconception is that running a game through Proton requires OBS to hook into a Windows-emulated process environment. In reality, Proton maps DirectX calls to Vulkan on the host system:

  1. Direct3D Execution: The Windows game makes DirectX 11 or 12 calls inside the Wine environment.
  2. Translation: DXVK (DirectX 9–11) or VKD3D-Proton (DirectX 12) translates these calls into standard Vulkan commands.
  3. Host Loader Execution: Proton utilizes Wine's Vulkan implementation, which directly calls the host Linux system's native Vulkan loader (libvulkan.so.1).

Because the translation results in native host Vulkan calls, the Linux-native OBS Vulkan capture layer attaches to the game process just as it would with a native Linux game.

Overlay Interception and Layer Ordering

The appearance of third-party overlays (such as the Steam Overlay, MangoHud, or Discord overlays) in the final OBS capture depends entirely on layer evaluation order in the Vulkan loader stack.

Vulkan executes layers sequentially:

  • Pre-call operations run from the application down toward the driver.
  • Post-call and presentation hooks run in reverse or based on where vkQueuePresentKHR is intercepted.

If MangoHud or the Steam Overlay loads before (closer to the application) the OBS capture layer in the swapchain presentation sequence, the overlay elements are already drawn into the frame buffer when OBS intercepts vkQueuePresentKHR. Consequently, the overlays appear in the OBS recording or stream.

Conversely, if the OBS capture layer executes before an overlay has composited its graphical elements onto the Vulkan swapchain image, OBS captures a clean frame consisting solely of the game render, omitting HUD metrics and notifications. Users control this behavior by adjusting environmental loading orders, such as launching applications via wrapper scripts that define layer order using the VK_LOADER_LAYERS_ENABLE environment variable.

Zero-Copy Frame Transfer

Once the frame is captured from the Vulkan swapchain, transferring high-resolution, high-framerate video data from Proton to OBS without performance degradation requires hardware acceleration.

The capture layer accomplishes this via DMA-BUF (Direct Memory Access Buffers) export:

  1. The capture layer creates an exportable image representation using Vulkan external memory extensions (VK_KHR_external_memory_fd).
  2. A file descriptor representing the GPU buffer is shared with OBS Studio via Unix domain sockets.
  3. OBS Studio imports the file descriptor directly into its own rendering pipeline using EGL or OpenGL/Vulkan interop extensions.

This method avoids copying frames from GPU memory to CPU system RAM and back to the GPU, minimizing Proton frame pacing drops and ensuring efficient video encoding.
