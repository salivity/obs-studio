SRT Rendezvous Packet Delivery Guarantees in OBS

Connecting two OBS Studio nodes directly via SRT (Secure Reliable Transport) in rendezvous mode provides predictable, low-latency transport over UDP while actively mitigating packet loss. This setup guarantees in-order packet delivery, selective retransmission of dropped frames, and strict timing preservation via Time-Based Packet Delivery (TSBPD). However, it does not guarantee absolute delivery under all conditions; delivery is strictly bounded by a configurable latency buffer, meaning severely delayed packets are intentionally dropped to preserve live broadcast synchronization.

The Role of SRT Rendezvous Mode

SRT rendezvous mode is a connection-negotiation mechanism designed for environments where both endpoints are behind firewalls or NATs without dedicated port forwarding. Both OBS Studio instances initiate handshake requests simultaneously. Once this bidirectional hole-punching succeeds, the rendezvous mechanism steps back, and the standard SRT transport protocol dictates all transmission parameters. Connection negotiation does not alter the underlying packet delivery guarantees, which remain identical to standard caller/listener SRT topologies.

Selective Retransmission (ARQ)

SRT uses an Advanced Repeat reQuest (ARQ) system built on top of UDP. Unlike standard UDP, which drops missing packets without recovery, SRT constantly tracks sequence numbers.

  • Negative Acknowledgments (NAKs): When the receiving OBS node detects a missing packet sequence, it issues a NAK back to the sender.
  • Targeted Resends: The sending node only retransmits the missing packets, avoiding unnecessary full-frame retransmissions and saving bandwidth.
  • Bandwidth Overhead Tracking: SRT monitors retransmissions to prevent saturating the available uplink during periods of high packet loss.

Timestamp-Based Packet Delivery (TSBPD)

In standard TCP/UDP video streaming, network jitter can cause packets to arrive in bursts or out of sequence. SRT solves this by appending a high-resolution timestamp to every packet header at the sending OBS node.

The receiving OBS instance buffers the incoming stream and reconstructs the packet intervals to match the exact spacing at which they were encoded. This ensures:

  • Strict In-Order Delivery: Applications consuming the SRT feed in OBS will never receive out-of-order packets.
  • De-Jittering: Network-induced delay variations are smoothed out before frames are handed off to the video decoder.

Bounded Latency and Too-Late Packet Drop (TLPKTDROP)

The most critical factor in SRT delivery guarantees is bounded latency. SRT prioritizes maintaining a fixed playout timeline over absolute data integrity.

When configuring SRT in OBS, a latency parameter (in milliseconds) is defined:

  1. The Retransmission Window: The sender and receiver hold packets in a buffer equivalent to the defined latency value. If a packet is lost, the receiver has this exact window of time to request and receive the retransmitted packet.
  2. Deterministic Drops: If a retransmitted packet cannot arrive before its scheduled playout time in the receiving buffer, the receiving node invokes Too-Late Packet Drop (TLPKTDROP). The packet is discarded permanently, and the stream moves forward to prevent video buffering or freeze.

Because of this mechanism, SRT does not guarantee 100% data arrival like TCP does. Instead, it guarantees time-bounded reliable arrival. If packet loss exceeds what can be resolved within the configured buffer window, data loss will occur to protect live real-time playback.

Cryptographic and Sequence Integrity

SRT integrates AES-128, AES-192, and AES-256 encryption. When configured in OBS Studio via the passphrase and pbkeylen URL parameters, SRT verifies the cryptographic integrity of incoming payloads. Corrupted or unauthorized packets injected into the UDP stream are identified at the socket layer and discarded before reaching the OBS rendering pipeline.
