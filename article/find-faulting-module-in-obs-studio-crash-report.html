Find Faulting Module in OBS Studio Crash Report

When OBS Studio unexpectedly terminates on Windows 11, it automatically generates a plain-text crash log detailing the execution state at the exact moment of failure. This guide explains how to locate, open, and analyze an OBS Studio crash report on Windows 11 to identify the specific faulting module and its corresponding memory address.

Step 1: Open the Crash Report in Windows 11

If OBS Studio is still open or can be relaunched:

  1. Open OBS Studio.
  2. Click on the Help menu in the top toolbar.
  3. Select Crash Reports, then click View Crash Reports.
  4. Double-click the most recent text file (named with the crash timestamp).

If OBS Studio cannot be launched:

  1. Press Win + R on your keyboard to open the Run dialog.
  2. Type %appdata%\obs-studio\crashes and press Enter.
  3. Open the latest .txt crash log file using Notepad.

Step 2: Locate the Fault Address and Primary Module

At the very top of the crash report, locate the header section immediately beneath the hardware and operating system details. Look for lines structured like this:

Unhandled exception: c0000005
Fault address: 7FFB2A1E14B2 (c:\program files\obs-studio\bin\64bit\obs.dll)
  • Fault address: The hexadecimal string (e.g., 7FFB2A1E14B2) is the exact memory address where the illegal operation occurred.
  • Faulting module path: The file path in parentheses directly indicates the executable or dynamic link library (.dll) executing the instruction at that address.

Step 3: Inspect the Crashed Call Stack

Scroll down until you see the section labeled with the thread that triggered the crash:

Thread 12A4 (Crashed)
Stack            EIP/Return Addr    Module                   Function
00000088929FE260 00007FFB2A1E14B2   obs.dll!os_event_wait+0x22
00000088929FE290 00007FFB1D89A410   obs-browser.dll!0x7ffb1d89a410
  1. Look for the top-most line of the stack under the crashed thread.
  2. The Return Addr / EIP column represents the specific instruction pointer address at that execution frame.
  3. The Module column displays the faulting module name followed by the offset (e.g., obs.dll!os_event_wait+0x22 or plugin_name.dll+0x14b2).

Step 4: Verify Against the Loaded Modules List

To find the base load address of the faulting module:

  1. Scroll down to the Loaded Modules section near the bottom of the report.
  2. Search for the module file name identified in Step 2 or Step 3.
  3. Observe the base address range: 
    7FFB2A1C0000 - 7FFB2A3B0000 obs.dll
  4. Subtracting the module's base address (7FFB2A1C0000) from the fault address (7FFB2A1E14B2) yields the relative virtual address (offset) within that module, which allows developers to pinpoint the exact line of compiled code responsible for the crash.
