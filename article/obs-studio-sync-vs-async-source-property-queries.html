OBS Studio Sync vs Async Source Property Queries

When developing plugins using the OBS Studio (libobs) API, properly querying and modifying source properties is essential for delivering a stable and responsive user experience. This article explains the technical differences between synchronous and asynchronous source property queries, highlighting how each approach affects thread execution, UI responsiveness, and overall plugin stability.

Understanding Source Properties in libobs

In OBS Studio, source properties (obs_properties_t) define the configurable elements of a source, such as dropdown menus, file paths, sliders, and checkboxes. These properties are generated via a source’s get_properties definition. Property queries occur whenever OBS needs to inspect, populate, or update the options presented in the user interface.

Synchronous Source Property Queries

A synchronous property query executes immediately on the calling thread, blocking further execution until the property data is fully resolved and returned. In most standard plugin implementations, get_properties or property modification callbacks run synchronously on the UI thread when a user opens the properties dialog or changes a setting.

  • Execution Flow: The caller requests the property list, the plugin function calculates or reads the required values directly from memory, and the populated obs_properties_t structure is returned immediately.
  • Benefits: Synchronous queries are simple to implement, deterministic, and eliminate the need for complex state management or synchronization primitives.
  • Drawbacks: If the query relies on slow operations—such as querying hardware drivers, scanning file directories, or pinging network devices—the calling thread will stall. Because this query often runs on the main UI thread, synchronous delays directly cause the OBS interface to freeze or stutter.

Synchronous queries are best suited for fast, lightweight operations where values are already cached in memory or defined statically (e.g., basic toggles, static dropdowns, or bounded numeric ranges).

Asynchronous Source Property Queries

An asynchronous source property query delegates the fetching of property data to a separate background or worker thread, allowing the calling thread to continue executing without delay.

  • Execution Flow: The initial query returns immediately with either placeholder data or a base set of properties. Concurrently, a background thread performs the time-consuming operation (such as enumerating network streams or scanning capture devices). Once the operation completes, the background thread safely posts an update back to the main thread or triggers a UI refresh to populate the actual values.
  • Benefits: Asynchronous queries keep the OBS user interface fully responsive, regardless of how long the underlying data retrieval takes. This is critical for plugins that interact with remote APIs, complex external hardware, or unpredictable I/O.
  • Drawbacks: Implementation complexity is significantly higher. Developers must manage worker threads, handle thread synchronization (using mutexes to prevent race conditions), and safeguard against edge cases, such as a user closing the properties window or destroying the source while a query is still in progress.

Key Differences

  • Thread Blocking: Synchronous queries block the calling thread (frequently the UI thread) until completion; asynchronous queries return control immediately and process tasks in the background.
  • Performance Impact: Synchronous operations with long latency cause noticeable UI freezes; asynchronous operations maintain smooth UI frame rates and user responsiveness.
  • Implementation Complexity: Synchronous queries require minimal code and simple linear logic; asynchronous queries require worker threads, thread-safe data structures, and lifecycle checks to avoid use-after-free crashes.
  • Data Availability: Synchronous queries guarantee that property data is complete upon function return; asynchronous queries require the UI to handle loading states or partial updates until data resolution completes.

Choosing the Right Approach

Choose synchronous queries when property generation depends purely on local memory, lightweight calculations, or static definitions where latency is negligible.

Choose asynchronous queries whenever the property state depends on external hardware probing, network requests, disk scanning, or any operation with non-deterministic execution times.
