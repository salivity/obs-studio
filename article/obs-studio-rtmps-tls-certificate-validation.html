OBS Studio RTMPS TLS Certificate Validation

OBS Studio secures live video streams transmitted over Real-Time Messaging Protocol Secure (RTMPS) by validating the distribution server's TLS handshake against trusted Certificate Authorities (CAs). Rather than maintaining an independent, proprietary list of certificates, OBS Studio relies directly on the underlying operating system's native certificate store and standard cryptographic libraries to authenticate endpoints. Understanding this validation mechanism is critical when broadcasting to private ingest servers, local relays, or custom distribution networks.

Operating System Trust Stores

When establishing an RTMPS connection, OBS Studio passes the connection pipeline through its networking backend (primarily powered by FFmpeg's libavformat and system-level cryptographic libraries). TLS certificate verification is delegated to the host environment:

  • Windows: OBS Studio references the Windows Certificate Store (specifically the "Trusted Root Certification Authorities" store via the CryptoAPI/Schannel interface or system-linked OpenSSL/mbedTLS setups).
  • macOS: The application relies on the macOS Keychain, validating the server against the "System Roots" and any user-trusted certificates stored locally.
  • Linux: Validation relies on the host distribution's standard CA bundle, typically located at /etc/ssl/certs/ca-certificates.crt or managed via standard package tools like ca-certificates.

Any server presenting a certificate signed by a globally recognized Root CA (such as Let's Encrypt, DigiCert, or Sectigo) will validate automatically without manual configuration in OBS Studio.

Validation for Custom and Private RTMPS Nodes

When streaming to a custom media server—such as an NGINX RTMP instance with TLS termination, MediaMTX, or SRS—the validation process requires the server's certificate chain to match the trust requirements of the broadcaster's operating system:

  1. Publicly Signed Certificates: If the custom node has a fully qualified domain name (FQDN) using a free or paid public CA, OBS Studio validates the connection seamlessly using the OS trust store.
  2. Private CA Certificates: If an organization issues certificates using an internal or corporate CA, the public root certificate of that private CA must be installed directly into the host machine’s local trust store. Once installed as a trusted root, OBS Studio will treat the custom node as secure.
  3. Self-Signed Certificates: Direct self-signed certificates are rejected by default because they do not chain back to a trusted root authority. To use a self-signed certificate with OBS Studio, the certificate must be manually imported into the operating system’s "Trusted Root Certification Authorities" (Windows) or set to "Always Trust" in Keychain Access (macOS).

Addressing TLS Handshake Failures

If an RTMPS stream fails to connect with errors such as Failed to connect to server or specific TLS handshake negotiation errors, the issue typically stems from certificate mismatches:

  • Hostname Mismatch: The stream URL entered in OBS (e.g., rtmps://stream.customdomain.com/live) must exactly match the Common Name (CN) or Subject Alternative Name (SAN) defined in the server's certificate. Connecting via an IP address when the certificate is issued to an FQDN will trigger a validation failure.
  • Incomplete Chains: If the streaming server does not send intermediate certificates alongside the server certificate, the host OS may fail to construct the trust chain to the root certificate. Custom RTMPS servers should always be configured with the full certificate chain (fullchain.pem).
